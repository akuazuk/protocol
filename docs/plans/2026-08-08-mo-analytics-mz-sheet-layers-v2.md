## 0. Что было непонятно в v1

В v1 «слой C = план vs КП» звучало так, будто КП участвуют во всей оценке МО.
По таблице владельца это **не так**.

**КП (клинические протоколы) задействованы только в строках с «Протокол = Да».**
Строки оформления по Инструкции №127 имеют «Протокол = нет» - там **нет**
проверки соответствия КП, только полнота/глубина записи.

Этот документ делает роль КП и шкалу 0 / 0.5 / 1 явными.

## 2. Полная карта таблицы → код / слой / КП

Колонка **КП** = нужна ли сверка с клиническим протоколом МЗ.
Колонка **№55 в таблице** = как строка фигурирует в оценке по постановлению
(0/0.5/1 или «отдельно не оценивается»).
Это **не** то же самое, что текущий бинарный `reg55_criteria` pass/fail в коде -
см. §5 про сходимость.

к факторам риска - доп. finding в зоне 2, но **не** перенос всей строки в «соответствие КП».

### 2.1 Когда «соответствие КП» считается

Только если одновременно:

1. Строка из таблицы с **Протокол = Да** (## 8–13).
2. Есть установленный диагноз (слоты `clinical_diagnosis` / `mis_diagnos`).
3. Подобран хотя бы один применимый КП (`protocol_suggest` / L1 match) с достаточным
   trust; иначе критерий = **n/a** или ceiling `weak`, а не ложный 0 «не соответствует КП».

**Нельзя** писать в UI «не соответствует КП» для жалоб, анамнеза, осмотра, даты -
там КП не участвует.

### 2.2 Подбор КП - инфраструктура зоны 2, не отдельный «балл МО»

| Компонент | Роль |
|--|--|
| `case_protocol_suggest` | найти КП по Dx (ICD-first / текст) |
| L1 `block_scores` exams/treatment | численное покрытие плана vs КП |
| История пациента | эпизод Dx для suggest; prior для коррекций 2c |
| Night/LLM | опционально уточняет 2a/2b |

Suggest score **не** колонка hero-дашборда. Это вход для критериев 8–13.

## 3. Три агрегата для дашборда (переименование v1 → v2)

| UI-имя | Зона | Что внутри | КП? |
|--|--|--|--|
| **Оформление (№127)** | 1 | критерии 1–7, шкала 0/0.5/1 | нет |
| **Диагноз** | 2a | критерий 8 + обоснование клиникой + МКБ в слотах | да (КП + классификации) |
| **План по КП** | 2b+2c | критерии 9–13; 11–12 требуют историю | да |

Safety - четвёртая плитка внимания, вне %.

Формулы агрегата v1 (пока калибруем):

```
zone1_pct = 100 * mean(scores of scored criteria 1–7)   # n/a вне знаменателя
zone2a_pct = 100 * score(criterion 8)   # или среднее подкритериев, см. §4
zone2b_pct = 100 * mean(scores of 9,10,13 and scored 11–12)
```

Band: bad &lt; 0.5 среднему (или есть нули по обязательным), weak &lt; 1.0 при пробелах,
ok = все обязательные на 1.

## 4. Как оценивать критерии зоны 2 (чтобы КП было прозрачно)

### 4.1 Диагноз (2a) - три проверки, один итог 0/0.5/1

| Подпроверка | Источник | Вес в «Как оценивать» |
|--|--|--|
| Dx указан (основной; сопутств. если есть) | слоты диагноза | без текста → 0 |
| Вытекает из клиники | жалобы+анамнез+осмотр+exam_data | нет опоры → макс 0.5 |
| Согласован с МКБ-10 / клин. классификацией / рамкой КП | код в слотах + directory/name + KP dx-class | код/класс совсем мимо → макс 0.5 |

Итог критерия 8:

- **1** - есть Dx, клиника поддерживает, кодирование/классификация ок;
- **0.5** - Dx есть, но слабая опора или слабый МКБ/класс;
- **0** - Dx отсутствует.

КП здесь: не «все назначения», а **нозология/классификация в рамках протокола**.

### 4.2 План обследования / лечения / кратность (2b)

Для каждого из 9, 10, 13:

- **0** - раздел отсутствует (нет текста рекомендаций / наблюдения);
- **0.5** - текст есть, но покрытие КП частичное (L1/block или suggest evidence);
- **1** - соответствует Dx и КП (кратность исследований/наблюдения учтена).

Если КП не подобран → не ставить 0 «не по КП»; ставить n/a или оценивать только
наличие текста (и помечать «КП не сопоставлен»).

### 4.3 Коррекции (2c) - история обязательна

- Нет prior clinical visit на складе → **n/a** (не 0).
- Prior есть, динамики/коррекции нет при показаниях → 0 или 0.5.
- Коррекция есть и согласуется с КП/динамикой → 1.

История пациента = условие применимости 2c + контекст для подбора КП эпизода.

## 5. Связь с текущим кодом №55 (pass/fail)

Сейчас `mz_2021_55.json` + `reg55_criteria` считают **бинарный** %
`100 × passed / applicable`.

Таблица владельца для многих строк зоны 2 задаёт шкалу **0 / 0.5 / 1** - это
ближе к `mo_rubric_mz` («Как оценивать»), чем к текущему reg55.

**Решение v2:**

1. **Primary методика отображения и слоёв** = рубрика 0/0.5/1 по таблице
   (`mo_rubric_mz` + доработки под §4).
2. Текущий бинарный №55 остаётся **вторичным чек-листом** («есть/нет поле»,
   alignment threshold) в `<details>`, пока не будет отдельного решения мигрировать
   reg55 на ternary.
3. В UI не писать «балл №55» как главный синоним «Как оценивать».

Исправления YAML относительно таблицы (фаза реализации):

- `exam_data.regulation` → `mz_2015_127`; `scored_by_55: false` (в №55 оценивается план).
- `diagnosis.how_to_evaluate` → текст таблицы (основной+сопутств., клиника, МКБ/классификации).
- `follow_up.regulation` → КП первичен; №127 только как доп. для кратности, если нужно.
- Явный флаг в YAML: `requires_protocol: true|false` на каждый критерий (сейчас
  выводится косвенно из `scored_by_55` / regulation - недостаточно ясно).

## 6. Дашборд «только внимание» (уточнение v1)

Hero-плитки:

1. **Оформление↓** - зона 1 bad/weak
2. **Диагноз↓** - зона 2a bad/weak
3. **План по КП↓** - зона 2b/2c bad/weak (подпись именно «по КП», не «план вообще»)
4. **Safety** - whitelist
5. **В очереди** critical / important

Тренд: 3 линии (Оформление / Диагноз / План по КП).

В подсказках плитки «План по КП»:

> Считается только при подобранном КП. Строки №127 (жалобы, осмотр…) сюда не входят.

Таблица документов: колонки **Оформл. · Диагноз · План КП · Attention**.
Не показывать suggest score как колонку качества.

## Приложение - шпаргалка одной фразой

- **Оформление** - Инструкция №127, **без КП**.
- **Диагноз** - клиника + МКБ/классификация + **рамка КП**.
- **План по КП** - обследования, лечение, кратность, коррекции; **КП обязателен**;
  коррекции ещё и **история**.
- **Safety** - вред, не методика «Как оценивать».
