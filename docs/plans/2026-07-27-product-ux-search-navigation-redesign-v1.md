## 1. Безопасный последовательный старт после задачи №1

### 1.1. Определить базу

Сначала прочитать:

```text
docs/plans/2026-07-27-kz-evaluation-quality-overnight-v1.md
```

Найти итоговый отчёт задачи №1, её ветку и commit SHA. Затем:

```bash
git fetch origin
git status --short
git log -10 --oneline --decorate
```

Выбрать базу по правилам:

1. Если результат задачи №1 уже merged в основную ветку — использовать актуальную
   `origin/main` или фактическую default branch.
2. Если задача №1 ещё не merged, но её ветка отправлена в `origin` — использовать
   точный remote SHA этой ветки.
3. Если ветка задачи №1 не опубликована или её итоговый SHA неизвестен — не начинать
   реализацию задачи №2. Зафиксировать блокер.

Не начинать задачу №2 от старого `HEAD` основного грязного worktree.

### 1.2. Создать отдельный worktree

Пример после проверки фактической базы:

```bash
UX_WORKTREE=/private/tmp/protocol-product-ux-redesign-v1
git worktree add -b codex/product-ux-redesign-v1 \
  "$UX_WORKTREE" <TASK_1_RESULT_SHA>
cd "$UX_WORKTREE"
```

Если ветка или каталог уже существуют, не перезаписывать их. Проверить состояние,
продолжить существующую задачу или создать безопасный суффикс `-v2`.

### 1.3. Зафиксировать baseline

В итоговом отчёте сохранить:

- базовый commit SHA;
- commit SHA задачи №1;
- `BUILD_VERSION`;

- результаты существующих frontend и search tests;
- Top-1/Top-3 выдачу контрольных запросов;
- число действий до открытия подходящего протокола;
- размеры viewport, на которых проводилась проверка.

## 2. Цель задачи

Превратить текущий интерфейс из общей технической демонстрации для нескольких ролей
в три понятных сценария:

1. врачу — быстро найти протокол или проверить КЗ;
2. методисту — увидеть риски, очередь и причины низкой оценки;
3. пациенту — загрузить заключение, понять результат и подготовить вопросы.

Редизайн считается успешным не по количеству новых компонентов, а по сокращению
когнитивной нагрузки, числа действий и вероятности ошибочного клинического выбора.

## 3. Доказанные проблемы текущего интерфейса

### P0 — безопасность и корректность поиска

Для запроса:

```text
I10 эссенциальная гипертензия
```

при неопределённой аудитории первым рекомендован протокол детского населения.
Прямой взрослый протокол расположен ниже. В выдаче также присутствуют слабо
релевантные протоколы по другим состояниям.

Обязательный инвариант:

> Нельзя показывать результат как рекомендуемый, если возрастная группа, особое
> состояние, условия помощи, применимость МКБ или актуальность документа не
> подтверждены.

### P0 — сломанный расширенный фильтр

Кнопка «Дополнительно» раскрывает почти пустую область с действием «Закрыть».
Либо отрисовать реальные фильтры, либо не показывать элемент до их готовности.

### P1 — смешение ролей

В одной верхней навигации смешаны:

- проверка КЗ врача/методиста;
- поиск протокола;
- пациентский сценарий «После приёма».

Кабинет методиста существует как технический режим `?mode=methodist`, а не как
полноценная рабочая оболочка.

### P1 — неверная классификация фильтров

В группе «Аудитория» находятся:

- взрослые;
- дети;
- беременные;
- неотложно;
- дополнительно.

Это разные измерения. «Неотложно» — условия помощи, «Беременность» — особый
клинический контекст, «Дополнительно» — действие интерфейса.

### P1 — лишние шаги и дублирование

В выдаче одновременно используются:

- «Шаг 3 из 4»;
- полный stepper;
- блок «Ваш путь»;
- несколько действий «Изменить»;
- отдельная кнопка возврата;
- список результатов и детальная карточка;
- много равнозначных CTA.

Базовый сценарий должен быть:

```text
запрос -> результаты -> протокол
```

Уточнение показывать только при реальной неоднозначности.

### P1 — технический язык проверки КЗ

Пользователю предлагается самостоятельно выбирать L0/L1/L2. До загрузки файла
показывается несколько длинных методических и юридических абзацев, а после выбора
уровня остаются конкурирующие CTA.

### P1 — слабая информационная иерархия

- внутренний slug `bolezni-sistemy-krovoobrashcheniya` показывается пользователю;
- статус «Рекомендуем» не соответствует фактической применимости;
- результат перегружен вторичными действиями;
- светлые пастельные границы местами дают слабый визуальный контраст;
- в стилях встречаются служебные размеры шрифта около 10 px;
- верхние вкладки имеют высоту около 40 px, что мало для рекомендуемой touch target;
- на mobile в форме поиска присутствует большой пустой вертикальный участок;
- «Голосовой ввод» выглядит незавершённым элементом без понятного состояния.

### P2 — пациентский сценарий

На мобильном экране почти весь первый viewport занимает повторное объяснение
«Как это работает». Форма загрузки находится ниже. Выбор шуточного тона вопросов
находится в основном медицинском сценарии и может снижать доверие.

## 4. Целевая информационная архитектура

### 4.1. Рабочее пространство врача

```text
Для врача
├── Найти протокол
├── Проверить КЗ
└── Недавние
```

Главная навигация должна использовать названия задач, а не внутренние технологии.

### 4.2. Рабочее пространство методиста

```text
Для методиста
├── Обзор качества
├── Очередь случаев
├── Критические нарушения
├── Динамика
├── Протоколы и источники
├── Качество поиска
└── Настройки оценки
```

Для desktop использовать левую боковую навигацию. На mobile — drawer или отдельные
экраны, а не горизонтальную ленту мелких вкладок.

### 4.3. Пациентское пространство

```text
Для пациента
├── Разобрать заключение
├── Подготовить вопросы
└── История проверок
```

Пациентский интерфейс должен оставаться отдельным маршрутом и не выглядеть третьей
рабочей вкладкой врача. В общей оболочке допустима ссылка «Пациентам», но не
равнозначная вкладка внутри clinical workspace.

### 4.4. URL и состояние

Использовать прямые, восстанавливаемые URL:

```text
/doctor/search
/doctor/review
/doctor/recent
/methodist/overview
/methodist/cases
/methodist/search-quality
/patient
```

Если полный router нельзя безопасно внедрить за итерацию, создать совместимый слой
маршрутизации поверх существующих URL и hash-state. Старые ссылки не ломать.

Запрос, применённые фильтры и выбранный результат должны восстанавливаться из URL.

## 5. Workstream A — исправить correctness до restyle

### A1. Applicability gates

До ранжирования или как жёсткий post-filter учитывать:

- взрослый / ребёнок;
- беременность и послеродовой период;
- амбулаторно / стационар / неотложно;
- специальность;
- прямое и иерархическое совпадение МКБ;
- статус и актуальность протокола;
- конфликт между запросом и population metadata.

Не использовать один мягкий score для условий, которые являются взаимоисключающими.

### A2. Статусы результата

Минимальные статусы:

```text
Точное совпадение
Подходит по коду МКБ
Возможное совпадение
Требуется уточнение
Не подходит по аудитории
Устаревший документ
```

Слово «Рекомендуем» разрешено только выше явного порога применимости и уверенности.

### A3. Объяснимость

Карточка результата должна объяснять:

- какой код совпал;
- для какой аудитории документ;
- какие условия помощи;
- почему документ расположен на этой позиции;
- почему требуется уточнение;
- год и статус актуальности.

### A4. Regression tests

Добавить dataset с ожидаемыми ограничениями. Минимум:

```text
I10 эссенциальная гипертензия
J20.9 острый бронхит
E11.9 сахарный диабет 2 типа
M32.9 системная красная волчанка
детская гипертензия
гипертензия при беременности
неотложная помощь при боли в груди
неоднозначная жалоба без возраста
```

Проверять не только наличие правильного результата, но и отсутствие недопустимого
Top-1.

## 6. Workstream B — новый поиск и фильтры

### B1. Первый экран

Показывать:

1. одну строку или компактную многострочную область поиска;
2. autocomplete диагнозов и МКБ;
3. быстрые фильтры «Взрослый», «Ребёнок», «Беременность»;
4. кнопку «Все фильтры»;
5. недавние запросы;
6. примеры только для нового пользователя.

Не требовать обязательного выбора аудитории до ввода запроса. Если аудитория
критична и не может быть определена, запрос принять и показать короткое уточнение.

### B2. Модель фильтров

```text
Возрастная группа:
  взрослый | ребёнок

Особые состояния:
  беременность | послеродовой период

Условия помощи:
  амбулаторно | стационар | неотложно

Дополнительно:
  специальность | пол | возраст | тип документа | актуальность
```

Выбранные фильтры отображать chips над выдачей. Обязательны:

- удаление одного chip;
- «Сбросить все»;
- счётчик активных фильтров;
- восстановление после reload/back;
- keyboard navigation;
- понятное mobile-представление.

### B3. Voice input

Если голосовой ввод реально поддерживается:

- сделать кнопку с понятной иконкой и текстом;
- показать состояния idle / listening / processing / error;
- дать возможность отредактировать транскрипт;
- обеспечить доступное имя.

Если он не поддерживается полностью — скрыть feature flag до готовности.

- год и статус документа;
- основание совпадения;

Не показывать filesystem path, внутренний slug и технические имена pipeline.

Вторичные действия:

- PDF;
- проверить КЗ;
- подготовить пациентскую памятку;

Не сжимать desktop split view до узкой двухколоночной версии.

## 15. Критерии приёмки

Задача не считается завершённой, пока:

1. детский протокол не может стать рекомендуемым Top-1 для взрослого запроса без
   явного подтверждения детской аудитории;
2. «Дополнительно» содержит работающие фильтры либо скрыто feature flag;
3. простой поиск не требует четырёх обязательных шагов;
4. внутренние slug/path не показываются пользователю;
5. на каждом этапе есть один визуально главный CTA;
6. обычный пользователь не обязан выбирать L0/L1/L2;
7. patient upload доступен в начале mobile-сценария;
8. врачебная, пациентская и методическая навигация логически разделены;
9. запрос и фильтры восстанавливаются после reload/back;
10. нет critical/serious accessibility violations на ключевых экранах;
11. нет horizontal overflow на 390 px;
12. добавлены regression и browser tests;
13. создан отчёт «до/после» с воспроизводимыми командами;
14. изменения закоммичены и отправлены в `origin`.
