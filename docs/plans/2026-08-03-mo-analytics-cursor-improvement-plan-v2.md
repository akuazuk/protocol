# МО Аналитика: план улучшений для Cursor (v2)

Дата: 2026-08-03
Статус: ready_for_execution
Область: `/methodist/mo`, `/api/methodist/mo/*`, дневной склад `/var/data/medical_exams`
Ограничение: разработка не имеет прямого доступа к production-БД МИС. Все изменения строятся на API-контрактах, обезличенных fixtures и опубликованных защищённых срезах.

## 1. Целевой результат

После выполнения плана методист должен:

1. За 10 секунд понять, свежи ли данные, сколько случаев требует внимания и почему.
2. За 2–3 клика пройти путь «аномалия → группа → случай → исходное МО → решение».
3. Всегда видеть различие между `0`, «нет данных», «не оценивается» и «ошибка расчёта».
4. Открывать МО с жалобами, анамнезом, осмотром, диагнозом и рекомендациями даже тогда, когда raw parquet не опубликован, но существует защищённый дневной CSV.
5. Работать с таблицами без пустых строк, ложных нулей, прыгающих колонок и непонятных кодов.
6. Получать одинаковые числа на KPI, графике, таблице, экспорте и PDF.

## 2. Референсные принципы

План использует не визуальное копирование чужих продуктов, а проверенные продуктовые принципы:

- NHS рекомендует применять таблицы именно для сравнения и сканирования данных, добавлять `caption`, корректные заголовки и `scope`, а ширину по возможности оставлять адаптивной: https://service-manual.nhs.uk/design-system/components/table
- Epic Healthcare Intelligence делает акцент на текущих данных, едином источнике истины, self-service срезах, сравнении с группами и переходе от аналитики к действию: https://www.epic.com/software/healthcare-intelligence/
- Salesforce Health Cloud объединяет клинические и административные данные, care gaps, ответственных, направления и замкнутые рабочие процессы: https://help.salesforce.com/s/articleView?id=ind.hc_care_orchestration.htm&language=en_US&type=5
- ONC SAFER требует проверяемой идентификации пациента, надёжной передачи клинической информации, контроля интерфейсов, конфигурации и AI-функций: https://healthit.gov/clinical-quality-and-safety/safer-guides/
- ONC рекомендует показывать нужную информацию нужному пользователю в подходящий момент и встраивать decision support в реальный клинический workflow: https://healthit.gov/clinical-quality-and-safety/

## 3. Правила выполнения в Cursor

### 3.1. Git

1. Не работать в грязной `main` и не удалять пользовательские файлы.
2. Перед каждой фазой: `git fetch origin`, новая ветка `codex/mo-<phase-name>` от актуальной принятой ветки.
3. Один смысловой commit на фазу; не смешивать UI, миграцию данных и ops в одном commit.
4. До push: targeted tests, затем весь набор `tests/test_mo_*.py`.
5. Push только feature-ветки. Создать PR с чек-листом, скриншотами и примерами обезличенных API-ответов.
6. Merge и deploy выполнять только после зелёного CI. Не force-push в `main`.

### 3.2. Данные и безопасность

1. Не копировать production CSV, parquet, токены и ПДн в Git, логи, fixtures или скриншоты.
2. Fixtures должны использовать вымышленные ФИО, идентификаторы и клинические тексты.
3. Клинический текст доступен только защищённому endpoint с токеном методиста; агрегатные endpoints его не возвращают.
4. В UI и API не отдавать filesystem paths, content hashes и внутренние ключи.
5. Любой экспорт клинического текста регистрировать в журнале доступа.

### 3.3. Definition of Done для каждой фазы

- есть код, тесты, состояние loading/empty/error/partial;
- есть keyboard и mobile/tablet проверка;
- отсутствуют ошибки console;
- числа сверены между API и UI на одном fixture;
- добавлена запись в execution log;
- приложены до/после скриншоты без ПДн.

## 4. Фаза 0 — зафиксировать контракты и baseline

### Задачи

1. Создать `tests/fixtures/mo_analytics/` с четырьмя обезличенными наборами:
   - нормальный свежий день;
   - частичный день;
   - пустой день;
   - смешанный день с `0`, `null`, `not_applicable`, `scoring_error`.
2. Зафиксировать JSON Schema для основных ответов:
   - health/freshness;
   - overview/month;
   - yesterday;
   - cases и case detail;
   - dimensions;
   - reports.
3. Добавить manifest метрик: имя, формула, знаменатель, единица, допустимость `null`, версия scorer.
4. Записать baseline: количество запросов на экран, p50/p95, размер JSON, ошибки console, число пустых DOM-контейнеров.

### Приёмка

- fixture может полностью отрисовать все экраны без БД;
- неизвестное поле допускается, удаление обязательного поля ломает contract test;
- `null` ни в одном преобразовании не становится `0`.

## 5. Фаза 1 — оболочка и навигация

### Изменения

1. Сгруппировать левое меню:
   - **Мониторинг:** Обзор, Вчера, Безопасность;
   - **Работа:** Очередь, Все случаи, Врачи;
   - **Аналитика:** Специальности, Диагнозы, Качество данных;
   - **Управление:** Отчёты, Журнал доступа, Настройки.
2. Показывать счётчики только там, где они помогают действию: P0/P1, просроченные, новые.
3. Сделать sidebar сворачиваемым и запоминать состояние; на планшете — off-canvas.
4. Добавить breadcrumbs для drill-down: `Обзор / Терапия / J00–J99 / Случай`.
5. Сохранить глобальные фильтры при переходе между экранами; явно показывать область их действия.
6. Командную палитру расширить поиском экранов, врача, диагноза, сохранённого среза и быстрых действий.
7. Удалить синюю рамку у программно сфокусированного `<main>`, сохранив видимый focus ring у интерактивных элементов.
8. Добавить «Назад к результатам» в drawer с восстановлением scroll position и выбранной строки.

### Приёмка

- любой раздел доступен максимум за два действия;
- после закрытия случая пользователь возвращается к той же строке и странице;
- Tab-навигация остаётся видимой, но рабочая область не обводится синей рамкой;
- URL воспроизводит страницу, фильтры, сортировку и drill-down.

## 6. Фаза 2 — визуальная система

1. Оставить спокойную клиническую палитру: зелёный как бренд/действие, красный только для P0/опасности, янтарный для P1/риска, синий для нейтрального выбора и ссылок.
2. Не кодировать статус только цветом: текст + иконка + цвет.
3. Уменьшить декоративные тени и glass-эффекты; повысить контраст текста и границ.
4. Ввести единые токены плотности, высоты строк, радиусов, таблиц, chart grid и tooltip.
5. Использовать моноширинные цифры для KPI, процентов и дат.
6. В KPI показывать: значение, знаменатель, дельту, направление «лучше/хуже», дату актуальности и tooltip с формулой.
7. Добавить skeleton только на первую загрузку; при фильтрации сохранять старое содержимое с индикатором обновления, чтобы экран не прыгал.
8. Проверить WCAG AA, масштаб 200%, prefers-reduced-motion и светлую/тёмную темы.

## 7. Фаза 3 — таблицы, заполненность и правильность данных

### Единый компонент таблицы

Создать конфигурационный renderer вместо отдельных строковых шаблонов:

```text
column = key, label, formatter, sorter, width, align, nullable,
         permission, responsivePriority, exportable
```

### Обязательные функции

1. `caption`, `scope="col"`, `scope="row"`, sticky header и первая смысловая колонка.
2. Серверная сортировка, фильтрация и пагинация; виртуализация при >500 строк.
3. Управление колонками с сохранением по пользователю и отдельными preset: «Методист», «Руководитель», «Врач».
4. Empty-state должен объяснять причину: нет данных, фильтры исключили всё, день не загружен, нет прав, ошибка API.
5. Форматирование:
   - `null` → «Нет данных»;
   - `not_applicable` → «Не оценивается»;
   - `scoring_error` → «Ошибка оценки»;
   - реальный `0` → `0%`;
   - дата → `ДД.ММ.ГГГГ`, исходный ISO остаётся в `datetime`/tooltip.
6. Для длинных причин: 2 строки + раскрытие, полный текст доступен клавиатурой.
7. На узком экране важные колонки остаются таблицей, вторичные переходят в раскрываемую карточку строки.
8. Экспорт использует тот же query/semantic layer, что таблица, и возвращает metadata: фильтры, scorer version, дата данных.

### Проверки заполненности

Для каждого endpoint добавить invariant tests:

- `total = rows + excluded + unscored` по документированному знаменателю;
- все `doctor_key` разрешаются в `dim_doctor` или маркируются «Врач не определён»;
- display diagnosis не содержит hash/внутренний идентификатор;
- score соответствует scorer version;
- ссылки на случаи существуют в текущей выборке;
- таблица не принимает произвольные HTML-строки из API.

## 8. Фаза 4 — графики и интерактивная аналитика

### Общие правила

1. Каждый график имеет заголовок-вопрос, единицу, период, `n`, дату данных и состояние качества.
2. Tooltip показывает значение, знаменатель, сравнение и объяснение методики.
3. Клик по точке/столбцу добавляет filter chip и обновляет таблицу случаев.
4. Для каждого графика есть доступная табличная альтернатива и выгрузка PNG/CSV.
5. Не строить линии через отсутствующие дни; partial-дни визуально штриховать.
6. Не использовать 3D, gauges ради декора, pie с множеством категорий и rainbow-палитры.

### Рекомендуемые визуализации

- Executive overview: bullet/KPI cards с целью, фактом и доверительным интервалом.
- Динамика качества: small multiples по четырём индексам, чтобы не смешивать разные шкалы.
- Врачи: funnel plot или scatter `объём × дельта к ожидаемому`, доверительный интервал, запрет рейтинга при малом `n`.
- Замечания: Pareto — случаи + накопленная доля.
- Специальность × МКБ: heatmap, цвет = score/defect rate, подпись = `n`, серый = недостаточно данных.
- Поток данных: compact funnel «получено → допущено → оценено → требует работы → закрыто».
- Очередь: aging buckets и SLA burn-down, а не декоративная круговая диаграмма.
- Качество источника: календарная heatmap по дням с missing/partial/revised.
- Case timeline: источник → scorer → действия методиста → передача врачу → решение.

## 9. Фаза 5 — карточка случая и формирование МО

1. Источники клинического текста искать в безопасном порядке:
   - точный дневной raw parquet;
   - quarantine parquet только с явной пометкой качества;
   - `secure_cases/YYYY/MM/mo_YYYY-MM-DD.csv`;
   - другие дни только как ограниченный fallback по точному идентификатору.
2. Сначала точное совпадение `mis_id`, затем `visit_id`; при нескольких документах выбирать оцениваемый и наиболее полный, но показывать список всех документов визита.
3. Не передавать путь к исходному файлу клиенту.
4. В drawer разделить:
   - шапка визита;
   - исходное МО;
   - четыре индекса;
   - замечания с evidence/source;
   - решение методиста;
   - история действий.
5. Для каждого замечания показывать: severity, правило, доказательство из МО, почему важно, уверенность, scorer version и действия «подтвердить / ложное / нужны данные».
6. Если текста нет, не показывать пустую карточку: указать проверенные источники, дату среза и действие «Открыть в МИС».
7. PDF и экран должны строиться из одного payload и иметь одинаковые значения.

### Приёмка

- fixture только с secure CSV возвращает `has_source_text=true`;
- жалобы и анамнез отображаются без filesystem path;
- при двух документах выбирается правильный scored document;
- клинический текст не попадает в агрегатные endpoints и browser console.

## 10. Фаза 6 — CRM/workflow методиста

1. Статусы оформить как state machine с разрешёнными переходами, а не свободной строкой.
2. Обязательные поля для передачи врачу: причина, evidence, severity, срок, ответственный.
3. Добавить представления «Мои», «Новые P0», «Просроченные», «Ждём врача», «Ложные срабатывания».
4. Bulk actions предварительно показывают число случаев и последствия.
5. Добавить SLA, напоминания, историю изменения и audit trail.
6. Сохранять feedback методиста как обучающий сигнал отдельно от исходной оценки.
7. Отображать reopen rate, false-positive rate, median time to resolution и долю закрытого цикла.
8. Care-gap подход применять только к рабочим задачам: аналитический сигнал должен иметь владельца, срок и конечное решение.

## 11. Фаза 7 — API и semantic layer

1. Вынести формулы в `mo_metrics.py`; фронтенд не пересчитывает медицинские KPI.
2. Каждый ответ содержит:
   - `data_through`, `generated_at`, `source`, `revision`;
   - `scorer_version`, `methodology`;
   - `quality_status`, `partial`, `warnings`;
   - `filters_applied`.
3. Ввести строгий тип metric value: `value`, `state`, `numerator`, `denominator`, `unit`.
4. Одинаковые filters/date boundaries для overview, cases, dimensions и export.
5. Добавить request id, structured logs и timing без ПДн.
6. Кэшировать агрегаты по fingerprint фильтров; case detail не кэшировать публично.
7. Добавить endpoint `/capabilities`, чтобы UI скрывал недоступные функции, а не падал.

## 12. Фаза 8 — свежесть, reconciliation и наблюдаемость

1. Health разделить на компоненты: warehouse, daily report, secure source, pipeline heartbeat, API schema, CRM store.
2. `degraded` должен возвращать машинно-читаемые reason codes.
3. Пропущенный `report.json` отличать от отсутствующих данных: warehouse может быть свежим, а reconciliation — degraded.
4. Добавить ежедневную сверку:
   - report ↔ warehouse;
   - warehouse ↔ cases API;
   - scored rows ↔ score axes/findings;
   - secure daily source ↔ case document coverage.
5. Показать в UI карточку «Качество публикации»: последний успешный run, лаг, revision, coverage клинического текста.
6. Алертировать только actionable события: stale >1 день, partial, mismatch >0.5%, document coverage ниже порога, schema mismatch.

## 13. Фаза 9 — производительность и доступность

Цели:

- first useful render ≤2.5 с на типичном ноутбуке;
- overview API p95 ≤400 мс;
- case detail p95 ≤700 мс без генерации PDF;
- смена локального фильтра ≤250 мс;
- первоначальный JS без vendor chart ≤250 КБ gzip.

Изменения:

1. Lazy-load charts по текущей странице.
2. Abort предыдущих запросов при смене фильтра.
3. Не перерисовывать все ECharts при изменении одного filter chip.
4. Ограничить число DOM-строк и tooltip payload.
5. Добавить axe/keyboard tests, контраст, reduced motion и screen-reader labels.

## 14. Фаза 10 — тестирование, deploy и rollback

### Автотесты

- unit: formatters, metric states, source selection, status transitions;
- contract: JSON Schema и invariants;
- integration: fixture warehouse + secure CSV + API;
- visual: desktop 1440, laptop 1280, tablet 768, dark mode;
- accessibility: keyboard path и automated WCAG scan;
- smoke: health → overview → cases → case detail → PDF.

### Deploy

1. Merge PR после CI и клинической приёмки на обезличенной выборке.
2. Deploy staging/canary с feature flags:
   - `MO_SECURE_CSV_SOURCE`;
   - `MO_UI_NAV_V2`;
   - `MO_TABLE_V2`;
   - `MO_SCORER_V4_PRIMARY` отдельно от UI.
3. Smoke production с токеном методиста без вывода ПДн.
4. Сравнить 20 агрегатных метрик со старой версией; расхождения документировать.
5. Rollback = предыдущий image/release + отключение flags; данные CRM не откатывать разрушительно.

## 16. Финальная приёмка продукта

Релиз считается готовым, когда:

- health `ok/fresh`, а degraded имеет понятную причину;
- ≥99% свежих оцениваемых случаев открывают исходное МО или объяснимый source-gap;
- все таблицы корректно различают состояния данных;
- каждый KPI имеет формулу, знаменатель и дату;
- все графики кликабельны и имеют табличный эквивалент;
- P0/P1 проходят замкнутый цикл до решения;
- нет ПДн в URL, логах, аналитике, fixtures и скриншотах;
- deploy воспроизводим из Git, rollback проверен;
- пользовательский тест: 5 методистов выполняют ключевые сценарии без подсказки, success rate ≥90%.
