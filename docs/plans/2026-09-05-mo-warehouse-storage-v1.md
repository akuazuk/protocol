# Хранение склада МО: что менять сейчас, а что только при росте

Статус: active. Дата: 2026-09-05.

## Контекст

Проверка перед промышленной эксплуатацией включала пункт «перенести склад МО с
файлов и SQLite на PostgreSQL и устранить гонки JSONL-аппендов». Прежде чем
двигать данные, состояние склада измерено на самой прод-VM `protocol-app`
(`europe-central2-a`), а гонка аппендов проверена экспериментом на прод-ядре.
Оба замера изменили вывод, поэтому план разделён на «делаем сейчас» и
«триггеры для PostgreSQL».

## Что реально в проде (2026-09-05)

`/var/data/medical_exams` - 2.7 ГБ.

| `warehouse/mo_lab.sqlite` | 171 МБ | `fact_mo_lab` 449 227 | wal |

JSONL: 200 файлов, основные группы - `kz_l1_*_cases.jsonl` (42),
`kz_l1_*_state.jsonl` (42), `kz_l1_*_llm_grades.jsonl` (35), `judges.jsonl` (32),
`shadow.jsonl` (28).

Два вывода из таблицы:

1. `mo_warehouse.sqlite` - пустой файл, ни одной ссылки в коде
 (`rg mo_warehouse.sqlite` даёт только `mo_analytics.sqlite` в deploy-скриптах).
 Это остаток ранней схемы.
2. Все живые базы уже в WAL. То есть читатели не блокируют писателя, а писатель -
 читателей. Главный аргумент «SQLite не выдержит параллельного доступа» для
 текущего контура не подтверждается: писатель один (ночной конвейер), читатель
 один (веб), объёмы - сотни тысяч строк, а не десятки миллионов.

## Гонка JSONL-аппендов: проверено, гонки нет

Гипотезу проверяли прямым экспериментом, а не рассуждением. Скрипт запускал
8 процессов, каждый дописывал 60 строк в один файл, размер строки - 100 байт,
20 КБ и 500 КБ.

| Среда | Результат |
|---|---|
| macOS (потоки и процессы) | 0 битых строк из 480 |
| Прод-ядро Linux 6.1.0-51-cloud-amd64, Python 3.11.2, ext4 | 0 битых строк из 480 на всех трёх размерах |
| То же, образец «один handle + write в цикле» (как в `grade_kz_llm.py`) | 0 битых строк из 480 |

Причина ожидаемая: режим `"a"` открывает файл с `O_APPEND`, и ядро вычисляет
позицию и пишет одной неделимой операцией. Блокировка файла здесь не добавляет
корректности, зато добавляет точку отказа и сериализует запросы.

Поэтому `flock` по всем аппендам **не вводим**. Вместо него закрыты три
настоящих дефекта - см. следующий раздел.

## Сделано (в этой итерации)

| Что | Где | Зачем |
|---|---|---|
| Единый модуль записи/чтения JSONL | `clinical_knowledge/jsonl_io.py` | одна строка уходит в ядро ровно одним `os.write`: `O_APPEND` неделим только внутри одного write, а буферизация Python может разорвать длинную строку на несколько |
| Чтение, устойчивое к обрыву | `iter_jsonl`, `is_valid_jsonl_line` | обрыв процесса посреди записи оставляет неполную строку в конце файла; строгий разбор превращал её в постоянную ошибку всего файла |
| Экранирование переводов строки | `encode_line` | `\n` внутри значения разрывал одну запись на две при чтении |
| Ошибка на частичной записи | `append_line` | кончилось место на диске - строка обрезана, и это ошибка, а не тишина |
| `durable=True` с `fsync` | `append_line` | для аудита и согласий; для массовой телеметрии `fsync` на событие слишком дорог |
| Чокпоинты переведены на модуль | `feedback_store.append_feedback_event`, `patient_feedback_store._append_jsonl`, `analysis_archive.save_snapshot`, `POST /api/brief-feedback` | было четыре независимые реализации записи |
| Битая строка не уходит в выгрузку | `collect_feedback_export_lines` | проверка JSON стояла только в ветке с `since`; выгрузка без `since` уносила обрывки дальше по конвейеру |
| `brief_feedback` пишет в `feedback_dir()` | `rag_server.py` | жёсткий `ROOT/data/ml/feedback` игнорировал `ML_FEEDBACK_DIR`, и в проде события ложились внутрь контейнера и исчезали при каждом деплое |

Тесты: `tests/test_jsonl_io.py` (11 тестов). Проверка «одна запись - один
syscall» подменяет `os.write` и считает вызовы, иначе регрессия буферизации
прошла бы незамеченной.

## Триггеры перехода на PostgreSQL

Переход стоит нескольких недель работы и меняет ночной конвейер, поэтому
запускается не по расписанию, а по факту:

1. Появляется вторая машина, которой нужен тот же склад на запись
 (SQLite по сети - отдельный класс отказов).
2. `mis_data` переходит за ~20 млн строк или база за ~10 ГБ.
3. Нужен одновременный конкурентный писатель, кроме ночного конвейера.
4. Нужны PITR и восстановление на момент времени, а не снапшот диска раз в сутки.
5. Появляются роли и построчный доступ на уровне СУБД для внешнего аудита.

До этого момента SQLite в WAL на одной VM - осознанный выбор, а не долг.

| Метрика | Было | Стало | Цель |

| Реализаций записи JSONL в прод-путях | 4 | 1 | 1 |

| Файл ломается из-за одной неполной строки | да | нет | нет |
| Обрывки записей в выгрузке без `since` | попадают | отбрасываются | отбрасываются |
| События `brief_feedback` выживают деплой | нет | да | да |
| Записей с `fsync` там, где нужен аудит | 1 из 2 контуров | доступно через `durable=True` | все аудит-пути |

## Риски

| Риск | Мера |
|---|---|
| `os.write` мимо буфера меняет поведение при заполненном диске | частичная запись теперь поднимает `OSError` с явным текстом вместо молчаливого обрезания |
| `iter_jsonl` скрывает порчу данных, пропуская строки | пропуски суммарно пишутся в лог с именем файла и номером первой битой строки |
| Смена каталога `brief_feedback` рассыпает историю по двум местам | старый файл лежит в репозитории и читается вручную; новых записей туда не будет |
| Отказ от `flock` окажется ошибкой при смене ФС (например, NFS) | у `O_APPEND` на сетевых ФС гарантий нет; при переезде склада на сетевой том шаг 9 обязателен |
