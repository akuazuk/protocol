## 1. Контекст

Оценка текущего МО почти всегда смотрит **только этот визит**: текст КЗ, слоты,
подобранный КП, findings ночи. История есть, но это три полки счётчиков
(`same_doctor` / `same_specialty` / `other`) и finding «первый контакт» у 75 %.
Лаборатория есть в `mo_lab.sqlite` с 2025-12, клеится к `patient_key`, но в
оценку входит только окно −14/+1 и помечена «черновик».

Отсюда ошибки шкалы, которые не лечатся порогом 0.5:

- терапевт повторяет I10 и тот же план, что месяц назад - зона плана молчит,
  если КП не подобран;
- кардиолог уже вёл этого пациента, терапевт пишет «впервые»;
- СОЭ 42 от прошлой недели не попала в текст - скорер окна −14/+1 это видит
  как shadow, итог не меняет;
- «первый контакт» - замечание, хотя это контекст.

Владелец: **по каждому ID клиента вести свою базу** - все доступные данные,
все визиты по всем специальностям и отдельно по каждой, все анализы. Последний
визит оценивать **на фоне этой базы**, не изолированно.

Разбор сейчас - drawer с прокруткой (`#case-review-pane`): зоны, семейства,
shadow, brief, findings, критерии, история, лаб, КП, служебное, форма из 8
полей. Методист не углубляется - он скроллит.

## 2. Что уже есть в проде (не изобретать заново)

| Кусок | Где | Чего не хватает |
|--|--|--|
| `patient_key` = sha256(patient_id)[:20] | `mo_daily.patient_key_for` | сырой id на складе не храним - так и оставляем |
| Лента визитов | `fact_mo_case(patient_key, visit_date)` + индексы | нет среза «по специальности» как объекта, нет эпизода МКБ, нет плана прошлого визита |
| Бандл истории | `mo_patient_history_bundle.py` | три списка stub-строк (дата, врач, код, %); тексты плана/осмотра не в бандле; кэш `fact_mo_patient_history_cache` есть, UI его почти не показывает |
| Лаб клиента | `mo_lab.sqlite` / `fact_mo_lab` | полная история на диске; в разбор едет только −14/+1, cap 400 строк; отклонения - shadow |
| Сверка лаб | `mo_lab_shadow.py`, `lab_abnormal_findings.py` | не в `overall_grade` |
| Динамика рубрики | `exam_correction` / `treatment_correction` | только если prior-текст попал в скорер; 58 % имеют prior, в UI это три числа |
| Волна K редизайна | `/cases/{id}/timeline` за 180 дней | ещё не сделана; этот план её расширяет до паспорта, не до «ленты на 180 дней» |

**Физически отдельный sqlite-файл на каждого пациента не делаем.** Это уже
отклонено в плане истории v2 и остаётся в силе: десятки тысяч файлов, id в
имени = PHI, нельзя спросить «все терапевты», ночной upsert не атомарный,
бэкап `protocol-data` ломается. «Своя база клиента» = **логический паспорт**:
полный объект на `patient_key`, строки в общих таблицах, материализованный
снимок для чтения за &lt; 200 мс.

Если позже понадобится выгрузка одного клиента для аудита - отдельный
read-only export по `patient_key`, не runtime.

## 3. Что меняется в проде

1. У каждого клиента на складе появляется **паспорт**: покрытие, специальности,
   эпизоды МКБ, индекс анализов, открытые отклонения, последние назначения.
2. Ночной score последнего визита читает паспорт **до** зон и итога.
3. Разбор случая - **пять шагов углубления**, на экране один шаг. Прокрутки
   «всего сразу» нет.
4. Пункт меню «Пациент» открывает тот же паспорт, не три счётчика.

Оценки без паспорта (ловушка 0.5, вынос №55, `safety_band`) остаются узким
PR H3-prep и этому плану не мешают.

## 4. Логическая база клиента

### 4.1 Объект `patient_passport`

Один JSON на `patient_key`. В API и логах нет `patient_id`, ФИО, ДР текстом.
Возраст в годах - только если уже есть на визите, без даты рождения.

```text
patient_passport
  key, updated_at, engine, coverage
  specialties[]          все специальности клиента
  visits_all[]           индекс всех визитов (без полных текстов)
  visits_by_specialty{}  тот же индекс, нарезанный
  episodes[]             корень МКБ → первая/последняя дата, кто вёл, последний план
  labs                   индекс дат/панелей + open_abnormal[]
  meds_recent[]          назначения из последних визитов (текст слота лечения)
  signals_for_score      готовые признаки для оценки ТЕКУЩЕГО визита
```

`coverage`: первая и последняя дата визита, n визитов, n специальностей,
n лабораторных дат, n панелей за 12 месяцев, причина пустоты
(`no_key` / `no_visits` / `ok`).

`specialties[]` (одна плитка = одна специальность):

| Поле | Зачем |
|--|--|
| `specialty` | ключ линзы |
| `n_visits` | сколько раз клиент здесь был |
| `last_visit_date`, `last_mis_id` | вход в шаг 3 |
| `last_diagnosis_code`, `last_grade` | «чем закончилось» |
| `n_doctors` | один врач или конвейер |
| `known_icd_roots[]` | чем эта специальность уже занималась |

`visits_*[]` - индекс, не документ:

`mis_id`, `visit_id`, `visit_date`, `specialty`, `doctor_key`,
`diagnosis_code`, `diagnosis_text` до 80 знаков, `overall_grade`,
`zone2b_kp_status`, `has_plan_text`, `plan_fingerprint` (нормализованный
хэш слота лечения+обследования, не PHI в открытом виде).

Полный текст МО **не** кладём в паспорт. Его по-прежнему отдаёт
`/cases/{id}`. Паспорт - карта, не архив КЗ.

`episodes[]`: корень МКБ (I10, E11, J06) → `first_date`, `last_date`,
`n`, `specialties[]`, `last_plan_fingerprint`, `last_mis_id`. Это основа
признака «повтор без коррекции».

`labs`:

- `dates[]` - все даты анализов клиента на складе (не только −14/+1);
- `panels_12m[]` - `{date, type_name, n_indicators, has_abnormal}` без значений;
- `open_abnormal[]` - отклонения, которые ни один визит после даты анализа
  не отразил в тексте (цитата показателя, без ФИО);
- значения показателей грузятся **только на шаге «Анализ»**, не в список.

`signals_for_score` считается относительно **текущего** визита
(`as_of_mis_id` / дата / специальность / код / текст плана / текст МО):

| id | Смысл | Куда в оценку |
|--|--|--|
| `repeat_same_spec_same_icd_same_plan` | тот же корень МКБ у той же специальности, план не изменился | зона плана `слабо`, если есть prior; не требует КП |
| `repeat_same_doctor_same_icd` | этот врач уже ставил этот код | контекст; порог МКБ мягче (уже есть) |
| `first_contact_this_specialty` | в этой специальности визитов не было | контекст, не дефект |
| `cross_spec_active_episode` | другой специалист вёл тот же корень за 180 дней, текущий текст это не упоминает | зона диагноза `слабо` |
| `lab_abnormal_open` | отклонение после прошлого визита, в текущем тексте нет | зона диагноза / важно |
| `lab_result_after_last_plan` | прошлый визит назначил обследование, результат уже на складе, в «Данные обследований» пусто | зона плана / оформления |
| `lab_chronic_overdue` | у эпизода E11/I10 нет ожидаемой панели дольше порога (справочник, не выдумывать) | контекст до разметки; primary после H1 |
| `prior_high_alert_open` | в недавних назначениях high-alert / два НПВП | риск |

Пустой паспорт (`no_key`) - оценка как сейчас, без штрафа «нет истории».

### 4.2 Схема склада (общие таблицы, не N баз)

```sql
fact_mo_patient_passport (
  patient_key TEXT PRIMARY KEY,
  first_visit_date TEXT,
  last_visit_date TEXT,
  n_visits INTEGER,
  n_specialties INTEGER,
  n_lab_dates INTEGER,
  coverage_reason TEXT,
  passport_json TEXT NOT NULL,   -- объект §4.1 без сырого id
  engine TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

fact_mo_patient_specialty (
  patient_key TEXT NOT NULL,
  specialty TEXT NOT NULL,
  n_visits INTEGER,
  last_visit_date TEXT,
  last_mis_id TEXT,
  last_diagnosis_code TEXT,
  last_overall_grade TEXT,
  PRIMARY KEY (patient_key, specialty)
);
```

Индексы: `(last_visit_date)`, `(specialty, last_visit_date)`.
Визиты остаются в `fact_mo_case`. Лаб остаётся в `mo_lab.sqlite`.
Кэш `fact_mo_patient_history_cache` после волны P1 не читаем - один паспорт.

Пересчёт: при upsert дня ночь обновляет паспорта **только затронутых**
`patient_key` (из вставленных строк). Полный rebuild - отдельная команда на
GCE, окно вне 01:00-04:30.

### 4.3 Как оценивается последний визит

Порядок скорера (менять `mo_zone_scores.py` / publish findings, не v3/v4):

```text
1. Собрать / прочитать паспорт as-of даты визита
2. Посчитать signals_for_score
3. Зоны как сейчас + сигналы паспорта
4. Итог overall_grade
5. Записать context[] отдельно от findings
```

Дополнение к шкале (не отменяет H3-prep про 0.5 и №55):

| Сигнал | Итог не выше | Замечание |
|--|--|--|
| `lab_abnormal_open` P1 + не отражено | Важно | дефект, цитата показателя |
| `repeat_same_spec_same_icd_same_plan` | С оговоркой, зона плана слабо | дефект динамики, КП не нужен |
| `cross_spec_active_episode` | С оговоркой, зона диагноза слабо | «кардиолог вёл I10 03.09 - в тексте нет» |
| `lab_result_after_last_plan` | С оговоркой | дефект, если слот обследований пуст |
| `first_contact_this_specialty` | не двигает итог | строка контекста |
| `repeat_same_doctor_same_icd` | не двигает итог | строка контекста + мягче МКБ |

«Хорошо» после паспорта значит: нет риска, диагноз не пустой/не безопорный,
оформление не «плохо», **и** нет открытого отклонения анализа, **и** нет
копии плана при повторном эпизоде той же специальности. Это как раз то
«хорошо», которое методист подтвердит.

Флаги (по умолчанию выключены, кроме контекста):

- `MO_PASSPORT=1` - строить и отдавать паспорт;
- `MO_PASSPORT_IN_SCORE=0` - сигналы пишутся shadow, пока нет выборки H1;
- после 40 меток на `lab_abnormal_open` и `repeat_*` - `=1` решением владельца.

## 5. Интерфейс: углубление шагами, не прокрутка

### 5.1 Принцип

На экране **один шаг**. Крошки сверху. Назад - предыдущий шаг, не скролл.
Документ МО не смешивается со служебным. Список случаев остаётся слева /
под крошками и не пропадает (уже требование волн W1/G).

Пять шагов:

```text
1. Пациент     карта клиента
2. Линза       все / одна специальность / анализы
3. Визит       оценка последнего (или выбранного) визита
4. Доказательство   одно правило, одна цитата
5. Решение     три вердикта + комментарий
```

Переходы только вперёд/назад и по клику в карте. Никакого
`case-workspace-decision-scroll` с десятью блоками подряд.

Ширина ≥ 1280: слева столбец шагов (5 строк), центр - содержимое шага,
справа при шагах 3-5 - текст текущего МО (свой скролл, не общий).
1024: шаги на весь экран; текст МО - кнопка «Документ» открывает тот же
шаг как панель, не вкладку-простыню.

### 5.2 Шаг 1. Пациент

Заголовок: «Клиент · N визитов · M специальностей · первая-последняя дата».
Если ключа нет: «Нет ключа пациента - оцениваем только этот визит» и сразу
кнопка на шаг 3. PHI не печатаем; поиск по `patient_id` остаётся в шапке
кабинета, в паспорте id нет.

Плитки специальностей (не таблица на всю ленту): название, N, последняя
дата, последний МКБ, последняя оценка. Клик - шаг 2 с этой линзой.

Плитка «Анализы»: N дат, N панелей за 12 мес., N открытых отклонений.
Клик - шаг 2, линза «анализы».

Плитка текущего визита (если вошли из списка): специальность, дата, оценка,
одна фраза причины. Кнопка «К оценке» - сразу шаг 3.

Контекст одной строкой, не карточкой: «этот код у этого терапевта уже был
12.08; открыто отклонение СОЭ 20.09».

Пустые состояния честные: «визитов других специальностей нет», «анализов на
складе нет» - не скелетон навсегда.

### 5.3 Шаг 2. Линза

**Специальность или «все».** Список визитов этой полки: дата, врач (без
лишних колонок), МКБ, оценка, «план тот же / изменён» если есть эпизод.
Не больше 12 строк на экран, дальше «Ещё 12» - это пагинация шага, не
прокрутка бесконечной ленты.

Клик по строке - шаг 3 (если это не текущий - тот же инспектор, другой
`case_id`, крошки сохраняют пациента).

**Анализы.** Даты панелей, метка «отклонение» / «в тексте текущего МО» /
«не в тексте». Клик по дате раскрывает **этот** день (значения) на том же
шаге, не уводит вниз страницы. Второй клик закрывает. Кнопка «учесть в
оценке» не нужна - скорер уже проставил сигнал; методист видит цитату.

### 5.4 Шаг 3. Визит

Один экран, без `details`.

1. Итог крупно: слово шкалы + одна причина (`overall_grade_reason_ru`).
2. Три чипа зон: полоса и **первая причина** из рубрики / паспорта
   («осмотр краткий», «план как 12.08», «КП не подобран - не штрафуем»).
3. «Что не так» - только дефекты, максимум 5, порядок Риск → Диагноз →
   План → Оформление. Клик по дефекту - шаг 4 с этим id.
4. Строка контекста (не дефект).
5. КП одной строкой. Клик - шаг 4, сущность `kp`.
6. Кнопки: «Доказательство», «Решение», «Документ» (правая колонка / панель).

Семейства %, deep, №55, LLM, CRM-история на этот шаг не выводятся.

### 5.5 Шаг 4. Доказательство

Один объект за раз: finding **или** критерий рубрики **или** сигнал паспорта
**или** пункт №55 **или** статус КП.

Блок: правило (русская фраза) · цитата ≤ 240 знаков · почему это дефект /
контекст / черновик · `evaluator_version` / engine. Стрелки «предыдущее /
следующее» по списку дефектов шага 3.

Сюда же попадают слои, которые раньше скроллились: таблица 0/0.5/1,
№55, судья («машина и судья разошлись»), off-label серым. Каждый - отдельная
карточка в ленте доказательств, не простыня.

### 5.6 Шаг 5. Решение

Три вердикта (Оформление / Диагноз / План), комментарий, «Сохранить»,
«МО в PDF». Статус CRM, ответственный, срок - не на этом шаге (Очередь).
После сохранения - возврат к списку, строка выделена, шаг сбрасывается.

### 5.7 Входные точки

| Откуда | Куда |
|--|--|
| Найти МО, клик по строке | шаг 3 текущего визита, крошки знают пациента |
| Обзор / чип оценки | список, затем как выше |
| Меню «Пациент» + поиск id | шаг 1 |
| Клик по специальности на шаге 1 | шаг 2 |
| Клик по дефекту | шаг 4 |
| Prev/Next по выборке списка | шаг 3 соседа, паспорт пересобирается если другой клиент |

URL: `page=case&case_id=&step=1..5&lens=all|spec:<name>|labs&proof=`.
Обновление шага - `history.pushState`, Назад браузера = предыдущий шаг.

### 5.8 Чего в UI больше нет

- общий скролл правой колонки разбора;
- 20 блоков `details` «на всякий случай»;
- три числа истории как замена паспорту;
- P0-P3 и второе «Критично» на этих шагах;
- кольца % семейств на шаге 3.

## 6. Метрики

| Метрика | Сейчас | Цель |
|--|--|--|
| Паспорт собран у случаев с `patient_key` | нет объекта | ≥ 95 % клинических с ключом |
| Время `/patients/{key}/passport` | - | &lt; 200 мс тёплый, &lt; 500 мс холодный |
| Время шага 3 (`/cases/{id}` без полного лаб-дампа) | 0.15 с шапка / лаб+история в том же ответе | шапка из списка + паспорт &lt; 400 мс |
| `first_contact` как карточка «Что не так» | ~75 % | 0 (контекст) |
| Повтор того же корня + тот же план у специальности | не считается | считается, видно на шагах 1-3 |
| Открытое отклонение анализа в итоге | shadow | после H1 - двигает зону/итог |
| Прокручиваемых блоков на шаге 3 | 8-12 | 0 (фиксированный экран) |
| Шагов до «что не так» из списка | скролл | 1 (сразу шаг 3) или 2 (паспорт→визит) |
| Сценарий S4 (что уже было + анализы) | три числа | шаг 1 + линза за ≤ 3 клика |
| PHI в git / логах / паспорте | запрещено | `patient_key` only |

Калибровка шкалы (два верхних `overall_grade` ≤ 75 %, `zone1=weak` ≤ 40 %)
остаётся за H3-prep + этим паспортом. Без паспорта «Хорошо» честно редкое;
с паспортом «Хорошо» значит ещё «нет открытого отклонения и нет копии плана».

## 7. Волны реализации

| Риск | Митигация |
|--|--|

| Параллельный PR в `mo-app.js` | новый файл `mo-steps.js`; overlap проверить |
