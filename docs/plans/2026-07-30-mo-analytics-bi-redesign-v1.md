## 1. Контекст и цель

Модуль «МО Аналитика» (`/methodist/mo`) должен быть рабочим инструментом руководителя и методиста:
открыл утром - за 10 секунд понял, что было вчера, где просадка, кого проверять, и что изменилось
за месяц. Сейчас это одностраничный HTML на 1214 строк с самодельными CSS-полосками вместо графиков,
частью неработающих фильтров и оценкой, которая измеряет в основном «заполненность полей», а не
качество медицинской работы.

Цель плана: перевести модуль на уровень современных BI-систем (Metabase / Looker / Superset по
удобству, но с медицинской предметной логикой), и одновременно радикально пересобрать оценку МО,
чтобы цифра «71.6%» означала что-то клинически осмысленное.

Термины: **МО** - медицинские осмотры и консультативные заключения (КЗ) из БД МИС Kravira.
**Случай (case)** - одна запись протокола `mis_protocol`. **МТД** - month-to-date, с 1 числа по вчера.

## 3. Диагноз: почему «во многих отчётах не подтягиваются данные»

Пять независимых корневых причин. Их надо чинить все, иначе редизайн ляжет на пустые данные.

### Причина 1. Артефакты пайплайна не доставляются в прод

`data/medical_exams/` в `.gitignore` (строка 43-45), в `render.yaml` диск `/var/data` смонтирован,
но каталог `medical_exams` там никто не создаёт. Ежедневный пайплайн пишет только на локальный Mac:
`reports/YYYY/MM/DD/report.json`, `secure_cases/`, `public/latest.json`, `warehouse/*.sqlite`.
В прод исторически загружали вручную месячный bulk (`scripts/deploy/render_mis_protocol_data.sh`).

Следствие: «Вчера», «Отчёты», «Свежесть», MTD в проде не работают by design.

### Причина 2. API вообще не читает витрину

`clinical_knowledge/mo_backend.py::_records()` при каждом запросе заново читает и склеивает
месячные JSONL + CSV + дневные `kz_l1_*_cases.jsonl` в память. `mo_analytics.sqlite` -
write-only. CRM живёт в третьем файле `mo_methodist.sqlite`.

Следствие: нет ни SQL-агрегатов, ни быстрых срезов, ни сопоставимости «вчера» и «месяц»,
плюс O(месяц) работы на каждый чих UI.

### Причина 3. Оси и findings не сохраняются в витрину

`upsert_warehouse` (`mo_daily.py:767-819`) пишет только `fact_mo_case`, `dim_doctor`,
`fact_mo_daily`. Значит любые графики «по осям», «по причинам замечаний», «по диагнозам»,
«по филиалам» физически не могут строиться из витрины, а из JSONL строятся частично.

### Причина 4. Backfill исторических дней потерял оценки

`scripts/backfill_mo_warehouse.py` берёт `case.get("overall_pct")` и **не** смотрит
`deep.overall_pct`, тогда как UI-слой (`mis_kz_quality.py::_flat_case`) смотрит.
Отсюда NULL за 01-25.07 в витрине при непустых числах на дашборде - расхождение витрина / UI.

### Причина 5. Контракт фронт / бэк рассинхронизирован

| Что делает UI | Что делает сервер |
|---|---|
| посылает `?month=2026-07` | параметр не объявлен, FastAPI его отбрасывает, берётся текущий месяц |
| посылает `?period=month` | не поддерживается, нужны `periods` / `date_from` / `date_to` |
| посылает `?compare_period=previous` | обработчика нет вообще, сравнение не считается |
| ждёт `avg_coverage`, `avg_confidence` | overview их не считает |
| «Вчера» = браузерное UTC-вчера | пайплайн живёт в Europe/Minsk, у полуночи расхождение на день |
| встроенная панель в `doctor/index.html` | таблицы остаются `hidden`, месяцы зашиты `2026-07` / `2026-01` |
| кнопка «Экспорт среза» | отдаёт только `.json`, не CSV/XLSX |
| `#density` в настройках | не подключён к JS |

Плюс дневной приём валится молча: гейт `validate_export` пропускает ночную недогрузку
(2 строки, 0% врачей) - `doctor_missing` и `volume_anomaly` это только warning, а не blocking.

## 5. Целевая архитектура данных

### 5.1. Один склад, три слоя

```text
MIS (MariaDB)
  -> [ETL день] raw/mo_YYYY-MM-DD.parquet  (как сейчас)
  -> [Scoring]  cases.jsonl + axes + findings
  -> [Warehouse] mo_analytics.sqlite   <-- единственный источник для API
       fact_mo_case, fact_mo_case_axis, fact_mo_finding, fact_mo_daily,
       fact_mo_doctor_daily, dim_date, dim_doctor, dim_specialty, dim_branch,
       dim_diagnosis, dim_service, dim_document_kind, dim_finding
  -> [Публикация] mo_public.sqlite (без ПДн) + public/*.json  -> /var/data/medical_exams (Render)
  -> [CRM] crm_case_state / crm_case_event / saved_view (в том же файле, отдельная схема)
```

Решения:

1. **Витрина становится обязательным слоем чтения.** `mo_backend` переводится на SQL. Чтение JSONL
   остаётся только как fallback при отсутствии витрины (для локальной отладки), с явным флагом
   `source: "jsonl_fallback"` в ответе и жёлтой плашкой в UI.
2. **Один файл витрины** вместо двух (`mo_analytics.sqlite` + `mo_methodist.sqlite`). CRM-таблицы
   переезжают в него, старый файл читается один раз при миграции.
3. **Семантический слой метрик** - новый модуль `clinical_knowledge/mo_metrics.py`: одно определение
   каждой метрики (средняя оценка, доля дефектных, P0-плотность, полнота №55, покрытие проверки),
   которое используют и «Вчера», и «Месяц», и тренды, и экспорт. Никаких повторных формул в
   обработчиках.
4. **Публикация в прод**: пайплайн после успешного дня собирает обезличенный `mo_public.sqlite`
   (без `patient_id`, ФИО, свободного текста; только агрегаты + хешированные case-токены) и
   заливает его на диск Render вместе с `public/*.json`. Скрипт `scripts/ops/publish_mo_snapshot.sh`
   + шаг в launchd. Прод-API читает `MO_DATA_ROOT=/var/data/medical_exams`.
5. **Идемпотентность**: ключ дня = `(visit_date, revision)`, upsert по `mis_id`; при `--force`
   удаляются производные строки дня во всех fact-таблицах перед вставкой.

## 6. Радикально новая оценка МО (scorer v4)

### 6.1. Что не так сейчас

1. **Три параллельных скорера**: L1 (`compliance_engine`, продакшн `overall_pct`), deep-eval v2
   (`kz_deep_eval.py`, оси A/B/C/D), v3 (`kz_evaluation_engine.py`, только shadow). Три разных числа,
   единого гейта нет.
2. **Ось A - это подсчёт непустых полей** (len >= 3 символов). То есть «качество» = «врач что-то
   написал». Это надо называть «полнота оформления», а не оценкой качества.
3. **Соответствие протоколу - подстроки.** `_match_any` ищет вхождение строки требования в текст.
   Синонимы, словоформы, отрицания не учитываются. При этом 0 из 477 протоколов имеют
   подтверждённые методистом правила, пригодные для штрафа - значит проверка либо шум, либо
   advisory-заглушка.
4. **Средняя по врачу без поправки на состав пациентов.** Терапевт с потоком ОРВИ и онколог
   сравниваются напрямую.
5. **Порог «требует внимания» = 70%** даёт 64.6% случаев. Это не приоритизация, а шум.
6. **LLM-очередь никогда не выполняется автоматически** - `llm_queue.json` пишется, но тянуть его
   надо руками через API.
7. **Мульти-КЗ на визит**: берётся только самая «богатая» запись, остальные выпадают из знаменателя.

### 6.2. Принципы v4

1. **Оценка = дефекты, а не проценты.** Первичная величина - список дефектов с весом и
   доказательством. Процент выводится из дефектов, а не наоборот.
2. **Severity-first приоритизация.** Врач/случай попадает в работу не потому что «меньше 70%»,
   а потому что есть дефект P0/P1 (безопасность, пропущенный красный флаг, невыполненный
   обязательный критерий №55, противоречие диагноз/лечение).
3. **Разделение четырёх независимых индексов** (не смешивать в один средний процент).
   Веса зафиксированы владельцем 2026-07-30:

   | Индекс | Вес | Что измеряет |
   |---|---|---|
   | Оформление | **0.25** | структурная полнота записи, объективно проверяемо (сегодняшняя ось A) |
   | Клиническая согласованность | **0.35** | диагноз <-> обследования <-> лечение <-> МКБ |
   | Безопасность | **0.30** | красные флаги, ЛВ-взаимодействия, дубли НПВС, STOPP/Beers |
   | Регуляторика | **0.10** | приказ №55 и локальные требования |

   Безопасность поднята с 0.05 до 0.30: пропущенный красный флаг важнее незаполненного поля.
   Итоговая «Оценка МО» - взвешенная, но в UI всегда показываются все четыре индекса и вклад каждого.
   Веса лежат в конфиге (`config/mo_score_weights.yaml`), версионируются вместе со `scorer_version`.
4. **Trust-gated протокол.** Штраф за несоответствие протоколу только если правило подтверждено
   методистом (trust A/B). Иначе - `advisory` с явной пометкой «требует проверки методиста»,
   и такие случаи идут в отдельную очередь наполнения базы правил, а не в оценку врача.
5. **Case-mix поправка.** Для врача считаем ожидаемую оценку по составу его случаев
   (специальность x тип документа x глава МКБ x первичный/повторный) и показываем
   **дельту к ожидаемой**, а не сырую среднюю. Ранжирование только по дельте, с 95% ДИ,
   малые n (< 20 за период) не ранжируются, а помечаются «мало данных».
6. **Калибровка на человеке.** Золотая выборка >= 300 случаев, двойная разметка методистами,
   арбитраж, метрики Spearman / QWK / recall по вредным дефектам. Порог приемки: Spearman >= 0.7,
   recall по P0 >= 0.9.
7. **LLM как замкнутый контур.** Ночной бюджетируемый прогон LLM-тира по очереди (worst-N +
   случайная выборка для контроля), результат пишется как `tier: L2/LLM` рядом с детерминированной
   оценкой, расхождение > 20 п.п. поднимает случай в очередь методиста.
8. **Провенанс обязателен.** Каждый дефект: цитата из записи (span), ссылка на пункт протокола/приказа,
   объяснение «почему это важно» из `dim_finding`. Без провенанса дефект не показывается как
   основание для оценки.
9. **Все КЗ визита учитываются**: для визита с несколькими записями считается агрегат визита,
   в знаменателях фиксируется и число записей, и число визитов.
10. **Версионирование**: `scorer_version` в каждой строке; смена версии не переписывает историю
    молча, а требует пересчёта с новой ревизией и отражается в UI («методика v4, с 2026-08-XX»).

### 6.3. Что показываем как «подробная оценка за вчера»

Экран «Вчера» должен отвечать на вопросы в этом порядке:

1. Данные полные? (принято строк / ожидалось по медиане дня недели, лаг, флаги качества, ревизия)
2. Сколько записей, сколько оценено, сколько исключено и почему (по типам документов)
3. Четыре индекса + дельта к предыдущему дню и к среднему по этому дню недели за 8 недель
4. Топ дефектов дня (с числом случаев и severity) с переходом в список случаев
5. P0/P1 случаи списком - имя врача, филиал, диагноз, дефект, кнопка «взять в работу»
6. Кто выбивается: врачи с дельтой к ожидаемой ниже -10 п.п. (только n >= 5, иначе скрыто)
7. Что изменилось в структуре потока (специальности, филиалы, типы документов)
8. Качество источника: parse_ok, заполненность врача/филиала/МКБ, расхождение дат

### 6.4. Что показываем как «подробная оценка за месяц»

1. MTD KPI + прогноз на конец месяца + сравнение с прошлым месяцем и с тем же периодом прошлого месяца
2. Динамика по дням (4 индекса + объём) с zoom и выделением аномальных дней
3. Тепловая карта специальность x глава МКБ (средняя оценка, размер = объём)
4. Рейтинг врачей по дельте к ожидаемой (с ДИ, фильтр по n)
5. Парето дефектов месяца (какие 20% дефектов дают 80% потерь)
6. Воронка исключений (source -> eligible -> оценено -> с дефектами -> в работе -> закрыто)
7. Прогресс работы методиста: взято, закрыто, подтверждено, ложные срабатывания (и их доля -
   это метрика качества самой оценки)
8. Соответствие №55: доля выполненных критериев, топ невыполненных

## 7. Дизайн: цель и правила

### 7.1. Общий язык дизайна

- **Layout**: слева свернутая иконочная навигация с подписями при раскрытии, сверху sticky-панель
  контекста (период, сравнение, ключевые фильтры), справа контент в сетке 12 колонок.
  Панель фильтров - выезжающая, но самые частые фильтры (период, филиал, специальность) всегда видны.
- **Плотность**: три режима (комфорт / компакт / плотно) с сохранением в профиль. Управляет
  высотой строк таблиц, размером шрифта карточек и высотой графиков (`#density` наконец подключаем).
- **Тема**: светлая и тёмная, `prefers-color-scheme` + переключатель, тема графиков синхронна теме UI.
- **Токены**: `frontend/web/shared/mo-tokens.css` - цвета, радиусы, тени, шкала отступов (4/8/12/16/24/32),
  типографика (`--font-display`, `--font-ui`, табличные цифры `font-variant-numeric: tabular-nums`),
  семантические цвета: `--sev-p0`, `--sev-p1`, `--sev-p2`, `--good`, `--warn`, `--bad`, `--neutral`.
  Цвет никогда не единственный носитель смысла: рядом иконка/подпись/паттерн.
- **Микровзаимодействия**: skeleton при загрузке, плавная (150-200 мс) смена состояний,
  `prefers-reduced-motion` отключает анимации, toast для действий, оптимистичное обновление CRM.
- **Кнопки**: единый набор - primary (заливка), secondary (обводка), ghost (только текст),
  danger, icon-button с tooltip, split-button для экспорта (CSV / XLSX / PNG / ссылка),
  chip-кнопки для быстрых периодов, segmented control для сравнения. У каждой - состояния
  hover / active / focus-visible / disabled / loading. Размеры: 32 / 36 / 40 px.
- **Пустые состояния**: не «Нет данных», а причина + действие («За 29.07 отчёт не сформирован.
  Запустить приём данных» / «Фильтры исключили все записи. Сбросить фильтры»).
- **Русский язык везде**: `Avg %` -> «Средняя оценка», `Core %` -> «Оценка по ядру полей»,
  `Δ к янв.` -> «Изменение к январю», `Visit ID` -> «Визит», `P0` -> «Критично (P0)»,
  `medical_exam` -> «Медосмотр», `diagnostic` -> «Диагностика», `non_clinical` -> «Не клиническая запись».
  Технические коды - только в tooltip и в экспорте.

### 7.2. Библиотека графиков

Выбор: **Apache ECharts 5**, self-hosted в `frontend/web/shared/vendor/echarts.min.js`.

Почему:
- полноценная интерактивность из коробки: tooltip с несколькими сериями, `dataZoom` (brush + колесо),
  legend toggle, click-события для drill-down, `markLine`/`markArea` для целей и аномалий;
- нужные типы: line/area, stacked bar, boxplot, heatmap, treemap, sankey (воронка исключений),
  gauge, scatter с регрессией (case-mix), waterfall (вклад осей);
- темизация JSON (светлая/тёмная), SVG-рендер для чёткой печати и экспорт в PNG;
- встроенный `aria.enabled` - генерирует текстовое описание графика для скринридера;
- нет обязательного CDN. Сейчас Chart.js тянется с `cdn.jsdelivr.net` - это внешняя зависимость
  прода, её тоже переводим на self-host.

Правило: график без tooltip, без подписи оси и без возможности «кликнул -> отфильтровал» в модуль
не принимается.

### 7.4. Поиск и фильтры

- **Единая строка поиска** с debounce 250 мс (сейчас поиск срабатывает только на `change`),
  поддержка: ФИО врача, код/название МКБ, номер визита, филиал, текст диагноза, код дефекта.
  Подсказки с группировкой по типу сущности и клавиатурной навигацией.
- **Командная палитра `Ctrl/Cmd+K`**: перейти к экрану, применить сохранённый срез, «показать
  вчера», «только P0», «мой список».
- **Фильтры**: период (пресеты: вчера, 7 дней, месяц, прошлый месяц, произвольный),
  сравнение (нет / предыдущий период / тот же период прошлого месяца / тот же день недели),
  филиал, специальность, врач, тип документа, тип визита, глава МКБ, severity, статус CRM,
  ответственный, наличие дефекта, диапазон оценки (слайдер), только с дефектами.
  Все - серверные, все отражаются в URL, все показываются чипами с крестиком и счётчиком.
- **Сохранённые срезы**: имя, область (личный / общий), закрепление в навигации, ссылка-шара.
  Серверные (таблица `saved_view`) с localStorage-фолбэком.
- **Экспорт**: split-button - CSV (UTF-8 BOM для Excel), XLSX, PNG графика, ссылка на срез.
  Экспорт учитывает **все** фильтры, а не текущую страницу.
- **Каждый фильтр даёт объяснение**: наведение на «Требует внимания» показывает
  «есть дефект P1 или оценка ниже ожидаемой на 15 п.п.», а не молчит.

## 8. API: целевой контракт

Новое или переработанное (`/api/methodist/mo/*`):

| Endpoint | Назначение | Ключевое |
|---|---|---|
| `GET /summary` | KPI за период + сравнение | параметры `period`, `date_from/to`, `compare` (реализовать наконец), возвращает все 4 индекса, покрытие, надёжность, MTD-прогноз |
| `GET /daily/{date}` | подробный отчёт за день | заменяет `daily-report`, добавляет ожидаемое по дню недели, флаги гейта, ревизию |
| `GET /timeseries` | серии по дням/неделям | `metrics=overall,doc,clin,safety,reg,volume`, `granularity` |
| `GET /breakdown` | универсальный срез | `dimension=doctor|specialty|branch|icd_chapter|document_kind|finding`, `measures=...`, ДИ и case-mix дельта |
| `GET /heatmap` | двумерный срез | `rows=specialty&cols=icd_chapter` (сейчас `spec_chapter_heat` считается, но не отдаётся) |
| `GET /findings` | каталог дефектов + агрегаты | русские названия из `dim_finding`, тренд по каждому |
| `GET /cases` | список случаев | серверная сортировка/пагинация, `severity`, `has_finding`, `score_min/max` |
| `GET /cases/{id}` | карточка случая | оси, дефекты с span и ссылкой на протокол, история CRM, соседние случаи визита |
| `POST /cases/bulk-action` | массовые действия | как сейчас + `undo_token` |
| `GET /freshness` | свежесть и здоровье | + `expected_rows`, `partial`, `source: warehouse|jsonl_fallback` |
| `POST /exports` | экспорт | `format=csv|xlsx|json`, без ограничения 200 строк |
| `GET /meta` | справочники и словарь метрик | русские подписи, определения метрик, версия методики - UI не хардкодит |

Контрактные тесты на каждый endpoint (`tests/test_mo_backend.py` расширяем): форма ответа,
русские подписи, отсутствие ПДн в публичном контуре, поведение при пустой витрине.

## 10. Риски и как их снимаем

| Риск | Вероятность | Митигация |
|---|---|---|
| Обезличенный снапшот в прод унесёт ПДн | средняя | тот же `_public_smoke`, плюс явный allowlist полей, плюс тест на запрет `patient_id`/ФИО/свободного текста в `mo_public.sqlite` |
| Переход на SQL сломает текущие ответы API | средняя | контрактные тесты на старую форму, флаг `MO_BACKEND_SOURCE=warehouse|jsonl`, поэтапное включение |

| Пересчёт истории затрёт данные без возможности сравнить | средняя | бэкап витрины перед пересчётом, старые значения в отдельных колонках, отчёт о расхождении по дням, возможность откатить одной командой |
| Расход LLM выйдет из-под контроля | средняя | учёт по каждому вызову, soft-лимит с предупреждением, hard-лимит с остановкой очереди, дневной и месячный отчёт |
| Case-mix модель окажется слабой | средняя | не показываем ранжирование, если R^2 < 0.3; fallback на «в пределах ожидания / ниже / выше» без чисел |
| ECharts утяжелит страницу | низкая | сборка нужных модулей, lazy-загрузка по вкладке, бюджет < 400 КБ gzip |
| Blocking-гейт по объёму заблокирует легитимный тихий день (праздник) | средняя | сравнение с медианой того же дня недели, ручной `--accept-low-volume`, алерт вместо тишины |
| Витрина расходится с JSONL | средняя | ночная сверка «витрина против JSONL» + метрика расхождения в «Качестве данных» |
| Mac офлайн - нет данных за день | высокая | catch-up уже есть; добавить в UI явную причину «приём не выполнялся, компьютер был офлайн» вместо пустого экрана |

### 11.1. Целевые значения: светофор вместо одной цифры

Одна цифра «норма 85%» вредна: её начинают догонять формально. Поэтому цель - коридоры по каждому
индексу плюс жёсткие абсолютные пороги там, где компромисс недопустим.

**Абсолютные пороги (не обсуждаются, нарушение = инцидент):**

| Показатель | Порог |
|---|---|
| Красный флаг без маршрутизации (`C_red_flag_unrouted`) | **0 случаев** |
| Доля случаев с дефектом P0 | **< 0.5%** |
| Обязательные критерии приказа №55 | **>= 95%** выполнено |

**Коридоры по индексам (цвет карточки в UI):**

| Индекс | Зелёный | Жёлтый | Красный |
|---|---|---|---|
| Оформление | >= 90 | 80-90 | < 80 |
| Клиническая согласованность | >= 80 | 65-80 | < 65 |
| Безопасность | >= 95 | 90-95 | < 90 |
| Регуляторика | >= 95 | 85-95 | < 85 |

**Композитная «Оценка МО»:** первый месяц после включения v4 - только измерение baseline, цель
не выставляется (иначе методика подстраивается под цель). Далее ступенчато: baseline + 3 п.п.
за квартал до достижения 85, затем удержание. Значение цели квартала хранится в конфиге и
рисуется на графиках как `markLine`, в gauge - как коридор.

**Цели по потоку и по врачам:**

| Показатель | Цель |
|---|---|
| Доля случаев с дефектом P1 и выше | < 15% |
| Доля врачей с дельтой к ожидаемой ниже -10 п.п. | < 10% |
| Доля дефектов, признанных методистом ложными | < 20% (иначе методика шумит) |
| Время до взятия P0-случая в работу | < 1 рабочий день |

## 12. Каталог отчётов (расширенный)

Отчёт - это не просто экран, а артефакт, который можно отправить, распечатать и обсудить.
Все отчёты формируются из семантического слоя (раздел 5.1), то есть цифры в них по определению
совпадают с дашбордом.

| # | Отчёт | Кому и когда | Содержание | Формат |
|---|---|---|---|---|
| 1 | **Утренний брифинг за вчера** | руководителю в 07:00 автоматически | одна страница: 4 индекса с дельтами, P0-случаи списком, топ-3 дефекта, полнота данных | Telegram-сообщение + HTML/PDF по ссылке |
| 2 | **Недельная сводка** | понедельник, после перезаписи прошлой недели | неделя против предыдущей, филиалы, выбивающиеся врачи, что улучшилось/ухудшилось | HTML/PDF |
| 3 | **Месячный отчёт (MTD и закрытый месяц)** | руководителю и на медсовет | всё из раздела 6.4 + прогноз + выполнение целей | HTML/PDF/XLSX |
| 4 | **Карточка врача** | для разговора руководителя с врачом | динамика за период, дельта к ожидаемой, топ дефектов, 3 конкретных примера с цитатами из записей и ссылками на протокол, что именно исправить | PDF на 1-2 страницы |
| 5 | **Карточка филиала / специальности** | владельцам направлений | то же в разрезе подразделения, сравнение с клиникой | |

| 7 | **План обучения** | методисту раз в месяц | какие темы протоколов нарушаются чаще всего, сколько врачей затронуто, приоритет по потерям | XLSX |
| 8 | **Качество самой оценки** | контроль методики | доля ложных срабатываний по каждому коду дефекта (по решениям методиста), точность/полнота, где методика шумит | таблица + heatmap |
| 9 | **Эффект вмешательства** | руководителю | как изменилась оценка врача после обратной связи: до/после даты взятия случая в работу, с контрольной группой | график before/after |

## 13. Фильтры, поиск и пресеты (расширенный)

### 13.1. Дополнительные измерения фильтрации

К списку из раздела 7.4 добавляются:

| Фильтр | Зачем |
|---|---|
| Время визита (утро / день / вечер) и день недели | проверить гипотезу «к концу смены качество падает» |
| Тип визита: первичный / повторный | у них разные обязательные блоки, сравнивать вместе некорректно |
| Возрастная группа пациента | педиатрия и гериатрия имеют свои требования (STOPP/Beers) |
| Вид оплаты (`pay_type`) и услуга | платный поток против прочих |
| Объём записи (знаков) | сверхкороткие записи - отдельная патология качества |
| Шаблонность (см. 13.2) | копипаста между пациентами |
| Наличие конкретного дефекта (мультивыбор по коду) | «покажи все записи без обоснования диагноза» |
| Решение методиста: подтверждён / ложное срабатывание / не размечен | контроль качества методики |
| Ревизия и версия методики | «что изменилось после пересчёта» |
| Диапазон оценки и диапазон дельты к ожидаемой | двойные слайдеры |
| Исключающие фильтры (НЕ терапия, НЕ филиал X) | сейчас невозможно |

### 13.2. Детектор шаблонности (новая функция)

Считаем сходство текстов записей одного врача (MinHash по шинглам, порог 0.85) в пределах периода.
Записи-близнецы для разных пациентов - сильный признак формального заполнения. Даёт:
новый дефект `E_template_copy` (severity P2), фильтр «шаблонные записи», отчёт 14.
Обязательно с провенансом: показываем обе записи рядом с подсветкой совпадающих фрагментов,
чтобы решение принимал человек, а не порог.

### 13.3. Пресеты-«рецепты» (быстрые кнопки)

Готовые срезы одним нажатием, они же доступны через `Ctrl/Cmd+K`:

- «Критичное за 7 дней» (P0 + P1, не закрыто)
- «Врачи ниже ожидания» (дельта < -10 п.п., n >= 20)
- «Нет диагноза по МКБ»
- «Шаблонные записи»
- «Красные флаги без маршрутизации»
- «Мои назначенные» / «Просроченные»
- «Изменилось после пересчёта»
- «Новые дефекты этой недели»

### 13.4. Поиск с операторами

Помимо обычного поиска - синтаксис для опытных пользователей с автодополнением и подсказкой:

```text
врач:Иванов мкб:I10 дефект:красный_флаг период:7д оценка:<60
филиал:Центральный тип:первичный сортировка:дефекты
```

Разбор на сервере, невалидный запрос не роняет страницу, а показывает подсказку «что не понял».
Строка запроса всегда отражается в URL и может быть сохранена как срез.

## 14. Интерактивность

Требования, без которых модуль не считается BI-системой:

1. **Cross-filtering.** Клик на элементе любого графика фильтрует все панели экрана. Активные
   выборы показываются чипами, «Сбросить» возвращает исходный срез.
2. **Синхронный zoom и курсор** на всех временных графиках: brush по датам в одном - применяется ко всем,
   hover показывает вертикальную линию и значения по всем метрикам на эту дату.
3. **Drill-down с хлебными крошками**: клиника -> специальность -> врач -> случай -> дефект -> пункт
   протокола, с кнопкой «назад к срезу» и сохранением состояния в URL.
4. **Сравнение двух срезов side-by-side**: два периода, два филиала, два врача - одинаковые панели рядом
   с подсветкой различий.
5. **Аннотации на временной шкале**: методист может оставить заметку на дате («14.07 сменился шаблон
   в МИС», «отпуск врача») - она видна на всех графиках и объясняет аномалии. Хранится в витрине.
6. **Живой статус приёма данных**: плашка «идёт приём за 30.07, этап: оценка» с обновлением,
   вместо тишины и пустого экрана. Источник - `state/pipeline.json` через `/freshness`.
7. **Действия прямо из графика**: выбрал точки brush-ом на scatter врачей - назначил проверку
   пакетом, с undo.
8. **Explain-панель у каждой метрики**: «как считается», «что входит», «почему у этого случая столько»
   с водопадом вклада осей и цитатами. Плюс блок «что сделать, чтобы стало лучше».
9. **Горячие клавиши** в очереди: `j`/`k` - навигация, `x` - выбрать, `a` - назначить, `Enter` - открыть,
   `u` - отменить действие.
10. **Экспорт визуала**: PNG/SVG графика в один клик и копирование в буфер для презентаций.

## 15. Роли, доступ и честность сравнения

Решение владельца: ФИО врачей видны всем пользователям модуля. Поэтому вводим не ограничение
доступа, а защиту от несправедливых выводов и прозрачность:

1. **Журнал доступа**: кто и когда открывал карточку врача и выгружал персональные срезы
   (таблица `access_log`, экран для роли `admin`). Требование обычной гигиены при работе с
   персональными данными сотрудников.
2. **Правила ранжирования** прямо в интерфейсе: рейтинг только по дельте к ожидаемой, только при
   n >= 20 за период, с доверительным интервалом; при пересечении ДИ врачи считаются неразличимыми
   и показываются одной группой, а не строкой выше/ниже.
3. **Запрет «голого» топ-худших** без контекста: рядом с любым рейтингом обязателен объём, состав
   случаев и число дефектов, признанных ложными.
4. **Право на объяснение**: в карточке врача видно, из каких конкретных случаев и дефектов сложилась
   оценка, и есть кнопка «оспорить» - создаёт задачу методисту с обоснованием.
5. **Кабинет врача (новая функция, фаза 5)**: врач видит свои записи, свои дефекты с цитатами и
   рекомендации, что исправить. Самообслуживание снижает нагрузку на методиста и превращает
   контроль в обучение.

## 16. Стабильность и эксплуатация

### 16.1. Техническая надёжность

| Мера | Детали |
|---|---|
| Версия схемы витрины | `schema_version` + миграции с авто-апгрейдом; несовместимая схема не молчит, а сообщает |
| Индексы | по `visit_date`, `doctor_key`, `specialty_key`, `severity_max`, `(visit_date, document_kind)`; сейчас индексов почти нет, при 92k+ строк это уже заметно |
| Транзакции | день пишется в витрину одной транзакцией, полудня не бывает |
| Бэкап | копия витрины перед пересчётом и перед миграцией, хранение 7 копий |
| Ретеншн и размер | план архивации: детальные `fact_mo_finding` старше 12 месяцев уезжают в архивный файл, агрегаты остаются; регулярный `VACUUM` |

| Health-эндпоинт | `GET /api/methodist/mo/health`: витрина открывается, схема актуальна, есть вчерашний день, число строк, лаг, источник данных |
| Watchdog | 08:00 нет вчерашнего дня - предупреждение, 10:00 - эскалация; проверка идёт из отдельного launchd-джоба, не из самого пайплайна |
| Circuit breaker для LLM | таймауты, ретраи с backoff, отключение тира при серии ошибок, чтобы не срывать ночной прогон |
| Фича-флаги | новый UI и новая методика за флагами, откат одним переключателем без деплоя |
| Ошибки фронта | `window.onerror` и `unhandledrejection` пишутся в лог сервера, чтобы «у меня пусто» стало воспроизводимым |
| Смоук после деплоя | к `render_wait_version.sh` добавляется проверка `/mo/health` и наличия вчерашнего дня |

### 16.2. Сверка данных (ежедневно, автоматически)

Три числа должны совпадать: строк в источнике МИС, строк в витрине, строк в дашборде за тот же день.
Расхождение больше 0.5% - алерт и запись в отчёт 12. Это единственный надёжный способ поймать
«отчёты не подтягивают данные» до того, как это заметит пользователь.

### 16.3. Пересчёт истории по методике v4

1. Бэкап витрины и артефактов.
2. Прогон v4 по всем дням с 01.07.2026 (последовательно, с ограничением нагрузки), запись в новые
   колонки: `overall_pct` (v4), `overall_pct_v3` (сохранённое старое), `scorer_version`.
3. Отчёт о расхождении: распределение дельт по дням, специальностям и врачам, топ-20 случаев с
   максимальным изменением с объяснением причины.
4. Переключатель методики в UI на 30 дней: «показать по методике v3 / v4» для сверки.
5. Только после приёмки отчёта v4 становится значением по умолчанию.

**Данные.** Новая таблица `fact_llm_usage`: `run_id`, `date`, `tier` (L2 / full / gold-labeling),
`model`, `case_id`, `prompt_tokens`, `completion_tokens`, `cost_usd`, `latency_ms`, `status`,
`retry_count`. Плюс `llm_cost_usd` в `fact_mo_case` для стоимости конкретного случая.
Цены моделей - в конфиге `config/llm_pricing.yaml` с датой действия, чтобы пересчёт был честным.

**API.** `GET /api/methodist/mo/llm-usage?period=...` - расход по дням, по моделям, по тирам.

**UI (раздел «Расходы» на экране отчётов):**

- расход за сегодня, за месяц, прогноз до конца месяца;
- стоимость одного проверенного случая и динамика этой стоимости;
- сколько случаев очереди продренировано и сколько осталось;
- доля вызовов с ошибкой и повторов (переплата за ретраи);
- окупаемость: сколько подтверждённых дефектов найдено на единицу затрат.

**Защита.** Soft-лимит (предупреждение в Telegram при превышении дневной медианы в 3 раза),
hard-лимит (остановка ночного прогона, задача методисту), обязательная запись расхода **до**
обработки результата, чтобы упавший вызов тоже учитывался.

## 19. Регламент исполнения: как пройти план без остановок

Раздел описывает механику работы, чтобы длинная автономная сессия не разваливалась на середине,
каждый коммит был корректным, а прод обновлялся предсказуемо.

### 19.1. Топология рабочих копий (важно, иначе сломается ночной приём данных)

| Копия | Путь | Ветка | Назначение |
|---|---|---|---|
| Боевая | `~/CURSOR/Protocol/protocol` | всегда `main` | из неё **launchd запускает ежедневный приём МО**; разработку здесь не ведём |
| Рабочая | `~/CURSOR/Protocol/protocol-work-mo` | `feature/mo-bi-*` | здесь пишем код и тесты |

Создание рабочей копии один раз (не в `/private/tmp`, его чистит macOS при перезагрузке):

```bash
cd ~/CURSOR/Protocol/protocol
scripts/ops/git_task_start.sh mo-bi --pc=imac --worktree="$HOME/CURSOR/Protocol/protocol-work-mo"
cd ~/CURSOR/Protocol/protocol-work-mo
```

Правило: после каждого успешного promote в `main` боевая копия догоняется
`git -C ~/CURSOR/Protocol/protocol merge --ff-only origin/main`, иначе launchd будет крутить старый код.

### 19.2. Разовая гигиена до начала (иначе guard будет падать всегда)

`scripts/ops/git_deploy_guard.sh` считает грязным **любой** непустой `git status --porcelain`,
включая untracked. В боевой копии сейчас ~13 неотслеживаемых артефактов
(`data/catalog/lex_shards/`, probe-отчёты, `постановление_МЗ_2021_55.pdf` и т. п.).

Порядок: полезные артефакты - в `.gitignore` или в `data/ml/reports/` с правилом игнора,
мусор - удалить, PDF нормативов - в отдельный каталог вне репозитория.
Проверка: `scripts/ops/check_repo_hygiene.sh` и `git status --porcelain` пустой в рабочей копии.

### 19.3. Единица работы (атомарный цикл)

Один пункт плана = один цикл = один коммит = один инкремент `BUILD_VERSION`.

```bash
cd ~/CURSOR/Protocol/protocol-work-mo
scripts/ops/git_safe_pull.sh                      # 1. синхронизация

# 2. тест сначала (red), затем код (green)
python3 -m pytest tests/test_mo_daily_pipeline.py tests/test_mo_backend.py -q

# 3. поднять BUILD_VERSION: YYYY-MM-DD-rN-краткое-описание (N++ в рамках дня)

# 4. только явные пути, никогда git add -A
git add clinical_knowledge/mo_daily.py tests/test_mo_daily_pipeline.py rag_server.py
git commit -m "feat(mo): ..."

# 5. push + fast-forward promote в main + ожидание версии в проде
scripts/ops/deploy_promote_main_after_push.sh \
  --prod-url=https://protocol-bimy.onrender.com --wait-version

# 6. догнать боевую копию (для launchd)
git -C ~/CURSOR/Protocol/protocol merge --ff-only origin/main
```

Когда `--wait-version` нужен, а когда нет:

| Изменение | Ожидание деплоя |
|---|---|
| серверный код, API, шаблоны, `rag_server.py` | **да**, `--wait-version` (до 15 минут) |
| только `docs/**`, планы | `--no-wait-version`, деплой догонит сам |
| только локальный пайплайн (`clinical_knowledge/mo_*`, launchd) | `--no-wait-version`, но обязательно шаг 6 |
| фронтенд `frontend/web/**` | **да**, плюс проверка страницы в браузере |

### 19.4. Проверка после каждого пуша (три обязательных сигнала)

```bash
curl -fsS https://protocol-bimy.onrender.com/api/version      # версия == локальной BUILD_VERSION
curl -fsS https://protocol-bimy.onrender.com/health/live      # healthCheckPath Render
curl -fsS -H "X-Methodist-Token: $METHODIST_TOKEN" \
  https://protocol-bimy.onrender.com/api/methodist/mo/health  # появится в фазе 7 (16.1)
```

Если версия не совпала за 15 минут: посмотреть, не отменил ли Render сборку из-за более нового
коммита; убедиться, что `origin/main` содержит нужный SHA (`git rev-parse origin/main`);
не пушить поверх, пока не понятна причина.

### 19.5. Правила, которые нельзя нарушать

1. **Никогда не коммитить** `data/medical_exams/**`, `.env`, выгрузки МИС, ПДн, PDF нормативов.
   Перед каждым коммитом: `git status --porcelain | rg -v '^\?\?'` - только ожидаемые файлы.
2. **`git add -A` запрещён** в этом репозитории.
3. Запрещены `git reset --hard`, `git clean -fd`, `git checkout -- <file>`, force-push в `main`.
   Для отката: новый коммит с обратным изменением или `git restore --source=HEAD` **только** по
   явно перечисленным путям и только после бэкапа.
4. **`BUILD_VERSION` меняется в каждом осмысленном коммите**, формат
   `YYYY-MM-DD-rN-описание`, иначе guard заблокирует деплой.
5. **Окна тишины для тяжёлых локальных прогонов**: 05:50-07:30 (основной приём),
   09:55-10:15 (retry), понедельник 10:55-11:30 (weekly), плюс каждый час пара минут на hourly.
   Пайплайн под `fcntl`-локом: второй экземпляр не запустится, поэтому свои прогоны
   ставить вне окон и проверять `pgrep -f run_mo_daily_report`.
6. **VPN**: `~/CURSOR/bin/vanya_vpn.sh ensure-off` перед любым SQL к МИС,
   `ensure-on` перед Gemini и сильными моделями.
7. **Прод не ломаем**: новый UI и новая методика за фича-флагами, старый экран доступен до
   приёмки фазы; удаление старого кода - отдельным коммитом после приёмки.
8. Ветка одна на задачу, `feature/mo-bi-<этап>`; не переиспользовать ветку под другой этап.

### 19.6. Как не останавливаться

- **Список задач ведётся по пунктам плана**, ровно один в работе; после каждого пуша - отметка.
- **Чекпоинт = зелёный пуш.** Не накапливать больше одного пункта в рабочем дереве: если что-то
  ломается, потери ограничены одним пунктом.
- **Ошибка не останавливает план**: фиксируем последнее зелёное состояние, записываем проблему
  в журнал (19.7) и переходим к следующему независимому пункту; заблокированный пункт помечаем
  `blocked` с причиной.
- **Решения по ходу не ждут владельца.** Если нужен выбор, не описанный в разделе 11: принимается
  разумный дефолт, фиксируется в журнале строкой «принято агентом, требует подтверждения»,
  работа продолжается. Останов допустим только при риске ПДн, денег или необратимой потери данных.
- **Порог качества не снижается**: пункт считается сделанным только при зелёных тестах и
  выполненном критерии приёмки из таблицы фазы. Нет теста - пункт не закрыт.
- **Сводка каждые 5 закрытых пунктов**: что сделано, какая версия в проде, что дальше.
