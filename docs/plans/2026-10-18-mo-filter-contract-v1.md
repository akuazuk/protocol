# Контракт фильтров и кликов (v1)

Статус: **active**
Дата: 2026-10-18
Родитель: [2026-10-18-mo-accuracy-ux-program-v1.md](2026-10-18-mo-accuracy-ux-program-v1.md)
Волна: C. Числа ниже сняты 2026-10-17 с прода и склада, окно клинических визитов 2026-01-01 - 2026-10-16. После догрузки склада они сдвинутся. Тест CI держит фикстуру, живая сверка на релизе переписывает столбец «факт».

Правило. Контрол назван так, как параметр запроса. Если клик меняет два параметра, шапка «Найти МО» показывает оба. Ноль допустим только если SQL тоже ноль и пустое состояние объясняет, какой это ноль.

## Запертые параметры «Найти МО»

Каждый запрос списка ставит `document_kinds=clinical_visit` и `score_eligible_only=1`. Чужие значения из адреса игнорируются. Консультация, диагностика и профосмотр в этот список не попадают, даже если у них тот же врач и та же дата.

Период по умолчанию - «Месяц», не год: 1-е число месяца вчера по вчера, Минск. На 2026-10-18 это `2026-10-01` - `2026-10-17`: 6993 клинических, важно 95, критично 0, нет оценки 0. «С начала года» до вчера включает и `2026-10-17`. Таблица года в этом документе по-прежнему обрезана `2026-10-16` (56821), день 17-го в неё не смешан.

Команды периода в палитре после волны B вызывают `applyPeriodPreset`, как кнопки шапки. Чип оценки при команде очереди не меняется.

453 - только клинические. Другие виды документов этого врача в «Найти МО» не входят. Это не поломка поиска.

Поиск. SQLite `LIKE` не нижний регистр для кириллицы. Варианты строки: все строчные, заглавная первая буква всей строки, заглавная у каждого слова и у части после дефиса, весь капс. Поле и подсказка пользуются одним путём. Число из чипа врача и число из полного ФИО в поиске обязаны совпадать.

Чего поиск не умеет и не обещает: ФИО пациента, опечатку, синоним диагноза. Пустой результат по фамилии пациента - не баг регистра. Пустое состояние: «В складе нет ФИО пациента. Ищите врача, диагноз, МКБ или номер визита.»

## Клики, которые легко врут

| Откуда | Что обещает подпись | Какой параметр считается верным |
|---|---|---|
| Чип оценки на Обзоре и в «Найти МО» | Эта оценка записи | `overall_grade` этой метки. Не полоса очереди |
| Лента оценок за день | Этот день и эта оценка | дата дня и `overall_grade`. Не соседний день из-за часового пояса Минска |
| Кольцо зоны | Зона и сегмент хорошо или плохо | `zone1` / `zone2a` / `zone2b` и полоса. Для плана «плохо» ещё статус КП, если сегмент про несоответствие подобранному протоколу |
| Воронка КП | Подобран, не подобран, без сравнения | `zone2b_kp_status`, не текст диагноза |
| Тепловая карта специальности | Неделя, специальность, слабые оценки | специальность, границы недели, `poor|important|critical`, не только `poor` |
| Топ замечаний | Этот код | `finding_code`, не поиск по куску заголовка |
| Кнопка врача «плохая» в сегодняшнем коде | Слово «Плохие» | Фактически `poor|important|critical`. Волна B переименовывает кнопку. До переименования контракт фиксирует фактический параметр, чтобы тест не закрепил кривое имя |
| Полоса врача на графике зоны | Доля зоны bad | врач плюс `zone*_band=bad`. Не оценка записи |
| Очередь «Только критично» | Критичное замечание очереди | правила `signal_band_for_finding`, не `overall_grade=critical` |
| Отчёт дня «с критичным замечанием» | P0 | число P0, не чип «Критично» |
| Лекарства, клик по типу | Этот тип сигнала | код семейства. Экран не фильтрует оценку записи сам |
| Анализы, клик | Код лабораторного сигнала | код, и список всё равно только клинические визиты |
| «Нужен разбор» в «Найти МО» | Срез очереди внутри списка | не равен чипу «Важно» |

## Слои внимания на окне

Для расшифровки, не для отдельного фильтра в меню:

| `attention_primary` | Визитов |
|---|---:|
| none | 47829 |
| zone2b | 8012 |
| safety | 750 |
| zone1 | 156 |
| zone2a | 74 |

Все 750 safety в текущем складе имеют оценку «Важно». Зона диагноза `bad` на всём окне - 74, и все они в «Важно». Оформление `bad` - 12144, но в «Важно» из них попадают только те, кого раньше поднял риск или диагноз. Фильтр «оформление плохо» поэтому намного шире чипа «Важно». Подпись фильтра говорит «оформление», не «важные записи».

## Как устроен тест волны C

CI не ходит на GCE и не открывает прод.

1. Маленькая sqlite-фикстура: несколько врачей, один с дефисом в ФИО, один визит каждой оценки, один Major, один дубль НПВП, один пустой диагноз, один P2 без P1, одна консультация того же врача.
2. Тест списка: консультация не возвращается; полное ФИО в нижнем регистре возвращает клинический визит; чип «Критично» на фикстуре возвращает только визит с полосой critical, если он есть в фикстуре правила, и ноль, если фикстура собрана по старому складу.
3. Тест клика: функция, которая из клика собирает query, для каждой строки таблицы выше даёт записанный параметр. Подпись кнопки врача в тесте равна новым словам волны B. Пока волна B не влита, тест живёт рядом с PR волны B, а не ломает текущий main заранее.
4. Отдельный файл ожиданий `tests/fixtures/mo_filter_contract_window.json` хранит числа этого документа. Его не сравнивают с продом в CI. Скрипт сверки для человека на GCE читает тот же файл и печатает только расхождения счётчиков.

Живая сверка на релизе, без персональных полей в выводе:

- шесть чисел оценок;
- I10, филиал, специальность, оформление плохо;
- один врач: фамилия, два слова, полное ФИО, и то же число у чипа врача;
- очередь «только критично» против SQL полосы очереди, не против чипа оценки;
- после волны F - новое число «Критично» вместо гипотезы.

## Риски

- Заморозка чисел 56821 в CI заставит обновлять фикстуру при каждой догрузке. Поэтому в CI фикстура крошечная, а большие числа только в ручной сверке.
- Часовой пояс. Граница дня в клике по ленте - дата Минска, не UTC. Тест границы: визит 00:30 Минска не уезжает на предыдущий день.
- Филиал и специальность сравниваются как на складе, без «похожести». Лишняя запятая или другое тире в названии филиала - отдельная строка, не повод для нечёткого поиска в этой волне.
