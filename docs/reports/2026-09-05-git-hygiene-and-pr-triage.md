# Git: чистка репозитория и разбор PR/веток

Дата: 2026-09-05. Фаза 4 программы production readiness.
Ветка: `cursor/production-readiness-agent1-pc1`.

## Итог одной строкой

`.git` уменьшился с **4.2 ГБ до 221 МБ (-95%)**. Перезапись истории
(`git filter-repo`) и force-push **не потребовались и не выполнялись**: ни один
PR, коммит и ни одна ветка не пострадали.

## Почему 4 ГБ - и почему это была не история

План исходил из того, что репозиторий раздут историей больших файлов и лечится
только `filter-repo` + force-push. Замер показал другое. При 690 МБ
отслеживаемых файлов в HEAD объём давали два источника, **оба вне истории
проекта**:

| Источник | Объём | Что это |
|---|---|---|
| `tmp_pack_*` в `.git/objects/pack/` | 1.3 ГБ | три брошенных временных пакета от прерванной упаковки, 27 июля |
| `refs/codex/turn-diffs/checkpoints/...` | 980 МБ | один блоб `corpus_vector_index/vectors.npy`, который держал живым ref агентского чекпоинта |

Проверка, что второй блоб не принадлежит истории:

```bash
git log --all --oneline -- corpus_vector_index/vectors.npy   # пусто
```

Ни один коммит проекта этот файл не содержит. Путь закрыт `.gitignore:120`, но
чекпоинты агента снимают рабочее дерево **вместе с игнорируемыми файлами**,
поэтому `.gitignore` от такого попадания не защищает. Файл и сейчас лежит на
диске (989 МБ) - он нужен локально, просто не должен попадать в git.

Это и есть главный вывод фазы: **раздувал репозиторий не проект, а инструменты
агентов**. Поэтому лечение - удаление локальных служебных ref, а не перезапись
истории.

## Что сделано

1. Независимый бэкап `~/protocol-full-2026-09-05.bundle` (1.2 ГБ),
   `git bundle verify` - «records a complete history». Именно bundle, а не
   прежний зеркальный клон: локальный клон делает hardlink-и, то есть общие
   inode с `.git`, и полноценной страховкой не был.
2. Удалены три `tmp_pack_*` (и их hardlink-копии в зеркале).
3. Удалены 2 ref-а `refs/codex/*`. На `origin` их нет, история проекта их не
   использует.
4. `git reflog expire --expire-unreachable=now --all` + `git gc --prune=now`.
5. `git fsck --connectivity-only` - ошибок нет.
6. Удалены 4 брошенных worktree релиза в `/private/tmp` (detached HEAD, без
   изменений).
7. Удалены 36 локальных веток, полностью влитых в `origin/main`, включая
   `codex/main-sync` (её `AGENTS.md` запрещает переиспользовать).

Проверка после чистки: 1122 коммита, 4725 отслеживаемых файлов, `origin/main`
(`5ba53536`) на месте.

## Обслуживание на будущее

`scripts/ops/git_repo_maintenance.sh` (есть `--dry-run`) повторяет пункты 2-5.
Мусор возвращается сам собой - чекпоинты пишутся при каждой сессии агента,
поэтому скрипт стоит прогонять периодически, а не однократно.

## Почему перезапись истории не нужна

После чистки `.git` = 221 МБ при 690 МБ файлов в HEAD, то есть история
дешевле рабочего дерева. Файлы, которые план предлагал вычистить из истории,
имеют по 1-3 версии за всё время:

| Путь | Версий в истории |
|---|---|
| `corpus_chunks_parts/*` | 3 |
| `structured_index.json`, `embeddings.json` | 2 |
| `corpus.json`, `chunks.json` | 1 |

Выигрыш от `filter-repo` - десятки МБ. Цена - сломанные 9 открытых PR, 108
локальных веток, 31 ветка на `origin` и обязательное переклонирование на всех
машинах. Соотношение не в пользу перезаписи, поэтому force-push не делался.

Снятие с трекинга `corpus_chunks_parts/` тоже отложено: сейчас это единственный
локальный fallback корпуса (`rag_server.py:95`, прод читает корпус из
`/var/data/protocol_corpus`), объём `.git` оно не уменьшит, а вопрос «какой
корпус считать единственным» разбирается в фазе 11 вместе с происхождением
данных. Барьер против повторного раздувания уже стоит:
`check-added-large-files --maxkb=2048` в `.pre-commit-config.yaml`.

## Спасённая незакоммиченная работа

Два worktree в `/private/tmp` содержали изменения, которых нет больше нигде, а
`/private/tmp` macOS очищает при перезагрузке. Сохранено в
`~/Protocol_Private/worktree-rescue-2026-09-05/` (patch + архив untracked +
базовый SHA):

- `protocol-task-mo-wrong-dx-search-pc1` - **278 строк в 17 файлах** плюс 7
  untracked: новые модули `clinical_knowledge/mo_content_search.py`,
  `mo_dx_support.py` с тестами, планы и handoff. Ветка не опережает `main`, то
  есть работа существовала только в рабочем дереве;
- `protocol-task-mo-drugs-labs-scoring-pc1` - 1 изменённый файл, ветка на 8
  коммитов впереди `main`.

Worktree не удалялись. Решение по этой работе (довести и оформить PR либо
отбросить) - за владельцем.

## Ветки: почему осталось 108

После удаления влитых осталось 108 локальных веток. Проверка по содержимому,
а не по предку (репозиторий использует squash-merge, при котором влитая ветка
всё равно выглядит невлитой):

```bash
git diff origin/main...<branch> --name-only
```

Пусто оказалось только у одной ветки (`codex/main-sync`, удалена). У остальных
97 есть содержимое, которого в `main` нет, - удаление уничтожило бы работу без
разбора. При `.git` в 221 МБ ветки ничего не стоят, поэтому массового удаления
не делалось; разбор - по мере закрытия соответствующих PR.

Все, кроме #192, не двигались с августа. Ни один не merge-ready: у семи

**#186 требует внимания в первую очередь.** Он добавляет
`docs/public_realition/`, который фаза 1 вынесла из репозитория как
непродуктовый материал. Теперь этот путь закрыт `.gitignore` и проверяется
`scripts/ops/check_no_phi_staged.py`, который подключён шагом CI, - то есть PR
#186 в текущем виде **упадёт на CI**. Это не случайная поломка: PR-ы,
собранные до фазы 1, могут возвращать в репозиторий то, что из него
намеренно убрано.

PR не закрывались: закрытие чужой работы - решение владельца репозитория, а
#148 и #113 содержат код, который при закрытии будет потерян.
