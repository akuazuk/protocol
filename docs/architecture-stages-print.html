Protocol: архитектура по этапам

Навигатор клинических протоколов Минздрава РБ и ориентировочная проверка консультативных заключений (КЗ).

Документ описывает текущую реализацию (MVP), целевую интеграцию с МИС и Минздравом через стандарт FHIR BY / ЦИСЗ, а также предложения по масштабированию на тысячи КЗ в сутки.

Версия документа: 2026-06-02 · Сборка приложения: 2026-06-01-r59 · Не является ТЗ и не заменяет нормативные акты Минздрава.

1. Назначение и границы системы

MVP Protocol - веб-сервис и API для двух сценариев:

  1. Поиск протоколов - подбор официальных КП Минздрава РБ по диагнозу, МКБ-10, жалобам и рубрикам каталога.
  2. Проверка КЗ - ориентировочная сверка консультативного заключения с фрагментами протоколов и формализованными правилами; отчёт для врача и методслужбы.

Не входит: установление диагноза, замена очного приёма, МЭЭ, юридически обязательная экспертиза, прямая запись в медицинскую карту (на этапе пилота).

Два контура intelligence: (1) LLM - языковая модель для синтеза, уточнения запроса и дополнения ответа; (2) детерминированный слой clinical_knowledge/ - парсинг, правила из протоколов, scoring без «магии» модели.

2. Этап 0. Корпус протоколов и справочники

2.1. Источник данных

Официальный каталог PDF на minzdrav.gov.by (раздел «Стандарты обследования и лечения»). Синхронизация скриптом download_minzdrav_protocols.py в каталог minzdrav_protocols/ (~478 PDF, 24 рубрики).

2.2. Индекс каталога

index.csv - метаданные: рубрика, год в имени файла, признак постановления МЗ. Используется для UI-бейджей, статистики презентации и фильтрации.

2.3. Справочники

  • protocols.json, protocol_meta.json - реестр путей и метаданные.
  • data/catalog/ - 85 нозологий, 482 автоизвлечённых правила, отчёт покрытия 100% PDF.
  • data/protocol_summaries/ - YAML/JSON карточки протоколов (~465 summaries) для навигации и расширения правил.
  • config/ - требования к КЗ, веса scoring, red flags.

5. Этап 3. Runtime: rag_server.py (FastAPI)

5.1. Стек

Python 3.11+, FastAPI, uvicorn. Учётные данные для вызова языковой модели задаются только в конфигурации сервера (переменные окружения или защищённое хранилище секретов) и не передаются в браузер.

5.2. Загрузка при старте

Фоновый поток load_data(): JSONL-чанки, protocols, meta, summary chunks, BM25. Endpoint /health отвечает до полной готовности RAG (важно для health-check при облачном развёртывании и в Kubernetes).

5.3. Гибридный retrieve

Функция retrieve(): лексика + BM25 + routing boost + фильтр аудитории + опциональный embed-rerank через LLM. Результат - топ фрагментов по протоколам.

6. Этап 4. Проверка КЗ (pipeline)

Модуль consult_review_pipeline.py - оркестрация с SSE-прогрессом для UI.

PDF/TXT/DOCX → извлечение текста → МКБ-10 + якорь рубрики врача → retrieve (RAG по allowlist протоколов) → match_protocol_cards + run_rule_checker → build_compliance_report (детерминированно) → LLM: синтез критериев и дополнение (если включено) → structured_analysis + report_html + report_markdown

Флаг CONSULT_STRUCTURED_ANALYSIS=1 включает полный структурный разбор. Fast mode на production сокращает второй проход RAG и таймауты.

7. Этап 5. Frontend (index.html)

Монолитный SPA (~12k строк): inline CSS + vanilla JS, без bundler.

  • Вкладка по умолчанию: «Проверка КЗ» (#consult-review).
  • Вторая вкладка: «Поиск протоколов» (#search).
  • Демо: ?presentation=1 - overlay для показа руководству.
  • SSE для потоковой проверки КЗ; lazy-load развёрнутых выдержек протоколов.
  • Читаемые ссылки на PDF протоколов (beautify_protocol_title).

Дополнительно: docs/mvp-presentation.html, consult_review.html.

8.1. Поток «Поиск протоколов»

Запрос → МКБ (icd_mkb.py + LLM) → retrieve → LLM формирует список протоколов с confidence → опционально protocol-detail.

8.2. Поток «Проверка КЗ»

Файл → pipeline → детерминированный compliance + RAG + LLM → отчёт с цитатами из официальных PDF.

9. Будущая интеграция с МИС и Минздравом

Этап 2 Согласно FHIR BY и регламенту МИС ОЗ - ЦИСЗ (v1.4, FHIR 5.0.0):

9.1. Разделение ответственности

СистемаЧто проверяет
ЦИСЗПрофили FHIR, структура Bundle, справочники НСИ, OAuth 2.0, импорт пакета

9.2. Точка встраивания в МИС

См. docs/deployment-belarus.md: сервер в контуре оператора/Минздрава, корпус на диске/S3, LLM - разрешённый API или on-premise модель в РБ, ПДн не выносить в публичный интернет.

10. Масштабирование: тысячи КЗ в сутки

При полной проверке каждого КЗ с LLM + RAG нагрузка растёт линейно. Ниже - меры ускорения и снижения стоимости.

10.1. Технические оптимизации

МераЭффект
Детерминированный fast pathСначала rule_checker + requirement_checker без LLM; LLM только при пограничных баллах или по запросу
Кэш consult-reviewCONSULT_REVIEW_CACHE - повторные проверки того же текста/хеша
Очередь + воркерыCelery/RQ: асинхронная обработка пакетов; API возвращает job_id, МИС опрашивает статус (аналог poll ЦИСЗ)
Отключение embed-rerankНа batch-режиме: только lex + BM25 (уже есть флаг в CI)
Предварительный digestСокращение текста КЗ до ключевых секций перед LLM (уже частично в pipeline)
Горизонтальное масштабированиеНесколько инстансов API за балансировщиком; корпус read-only на shared disk
Инкрементальный corpusНе перезагружать весь RAG при деплое - hot-reload index.csv

10.2. Ориентиры производительности (пилот)

  • Детерминированный разбор одного КЗ (без LLM): секунды.
  • Полная проверка с LLM: десятки секунд - минуты (зависит от длины и fast mode).
  • Целевой batch: 100% КЗ - только детерминированный скоринг; 5-15% - углублённо с LLM.

11. Методика выборочного контроля качества КЗ

Цель: выявить врачей/подразделения с систематически слабыми КЗ без проверки каждого документа LLM.

11.1. Уровни выборки

УровеньОхватМетод
L0 - скрининг100% КЗТолько детерминированный скоринг (без LLM): оформление, МКБ, обязательные поля, red flags. < 1 с на документ.
L1 - выборка10-20% КЗСлучайная + стратифицированная по врачу, рубрике, итоговому L0-баллу.
L2 - углублённо2-5% КЗПолный pipeline с RAG + LLM; эталон для методслужбы.
L3 - ручной аудит0.5-1%Эксперт методслужбы по списку «красных» врачей из L0-L2.

11.2. Критерии отбора «проблемных» врачей

  • Средний балл L0 за месяц < 70% при n ≥ 10 КЗ.
  • Доля КЗ с критическими issues (red flags) > 15%.
  • Тренд: снижение балла 3 месяца подряд.
  • Выбросы: единичные КЗ < 50% при обычно нормальном профиле - в L2, не автоматическая санкция.

11.3. Агрегаты для Минздрава (без ПДн)

Учреждение, рубрика, период, средний % по блокам, доля «зелёных/жёлтых/красных» зон. Без ФИО пациентов; идентификатор врача - только внутри контура учреждения.

11.4. Хранение результатов

Таблица kz_quality_scores: hash текста, author_id (из токена МИС), timestamp, L0_score, flags, optional L2_job_id. Retention по политике ИБ.

12. Вариант: блокировка ЭЦП до нормы соответствия

Опция для МИС Не юридическое требование Protocol, а настраиваемая политика учреждения, согласуемая с Минздравом и юристами.

12.1. Режимы (config в МИС)

РежимПоведение
informТолько предупреждения; ЭЦП всегда доступна (текущий пилот).
soft_gateПри балле < порога (напр. 70%) - диалог «Подписать всё равно?» + запись override в журнал.
hard_gateКнопка ЭЦП неактивна, пока L0 ≥ порога или методист не снял блок (workflow).
critical_onlyБлок только при critical red flags (безопасность, противопоказания).

12.2. Техническая реализация в МИС

  1. МИС вызывает POST /api/consult-review?mode=fast или лёгкий POST /api/consult-compliance-screen (только L0).
  2. Ответ: overall_compliance_pct, blocks, critical_issues[], gate_allowed: bool.
  3. МИС применяет локальную политику → разрешает/блокирует вызов ЕСИФЮЛ.
  4. При override - запись в audit log (врач, время, причина).

12.3. Риски и смягчение

  • Ложные срабатывания - порог только по L0; спорные случаи - soft_gate.
  • Юридическая нагрузка - формулировка «ориентир методслужбы», не МЭЭ.
  • Сопротивление врачей - пилот в одном отделении, обучение, прозрачные критерии из протоколов с цитатами.

13. Тестирование и качество

  • CI: Ruff + pytest (~55 модулей), миникорпус tests/fixtures/chunks.mini.jsonl.
  • Eval: eval/golden_queries.jsonl → data/quality_benchmark.json для UI.
  • Regression KZ: tests/test_regression_kz_compliance.py, fixtures в tests/fixtures/consultations/.

14. Заключение

Protocol сегодня - монолитный MVP с двумя контурами: LLM для поиска и синтеза и детерминированный clinical_knowledge для воспроизводимой проверки КЗ. Корпус привязан к официальным PDF Минздрава РБ.

Интеграция с МИС через FHIR BY логична до подписи ЭЦП: ЦИСЗ проверяет упаковку данных, Protocol - клиническое соответствие протоколам. Масштаб на тысячи КЗ достижим за счёт L0-скрининга, выборочного L2 и очередей; блокировка ЭЦП - опциональная политика учреждения, не обязательная часть MVP.
