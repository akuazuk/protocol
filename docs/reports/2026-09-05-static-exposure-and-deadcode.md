# Раздача статики и мёртвый код

Дата: 2026-09-05. Фаза 5 программы production readiness.
Ветка: `cursor/production-readiness-agent1-pc1`.

## Главное: по '/' отдавались бизнес-план и устройство инфраструктуры

По `/` монтируется **корень репозитория**, а фильтр `SafeStaticFiles` работал
как список запрещённого: перечислял запрещённые каталоги (`data`, `tests`,
`scripts`, …) и расширения (`.py`, `.md`, `.env`, …). При таком устройстве
любой файл с неучтённым расширением или в неучтённом каталоге публичен по
умолчанию. `.pdf`, `.docx`, `.png` в списке не значились, каталоги `archive/`,
`frontend/`, `deploy/`, `epam/`, `config/`, `ml/`, `patient-app/` - тоже.

Проверка на живом сервере до правки - все с кодом **200**:

| Путь | Размер | Что это |
|---|---|---|
| `archive/docs/konkurs/06_ROI_Kravira.pdf` | 226 КБ | финансовая модель |
| `archive/docs/konkurs/03_Biznes_plan_*.pdf` | 3.4 МБ | бизнес-план |
| `archive/docs/konkurs/_templates/*.docx` | - | заявки конкурса |
| `deploy/gcp-app/Caddyfile` | 409 Б | устройство инфраструктуры |
| `deploy/gcp-app/Dockerfile` | 2.2 КБ | внутренние пути и переменные |
| `deploy/launchd/*.plist.in` | - | расписание фоновых задач |
| `epam/scheme_mis_protocols.docx` | 19 КБ | схема интеграции с МИС |
| `embeddings.json` | 3.7 МБ | данные |
| `Procfile` | 77 Б | конфигурация запуска |

Всего публично отдавались **139 файлов**, из них 75 в `archive/` и 33 в
`frontend/`. Показателен `embeddings.json`: в списке запрещённых файлов
значился `semantic_embeddings.json`, а `embeddings.json` - нет. Ровно тот
случай, когда список запрещённого пропускает то, о чём забыли.

### Исправление: список разрешённого

`_is_blocked_static_path` заменена на `_is_allowed_static_path`. Отдаётся ровно
то, что перечислено, всё прочее - 404. Новый файл в репозитории теперь по
умолчанию закрыт.

Разрешено:

- `protocols.json` - каталог протоколов;
- `docs/<файл>` **глубины 1**, расширения `.html .pdf .png .svg .json` -
  презентация, `architecture-*`, `ministry-brief`, `pre-sign-checklist`,
  `presentation-stats.json` (его `mvp-presentation.html` читает относительной
  ссылкой). Подкаталоги `docs/` (`plans`, `reports`, `konkurs`, `deploy`,
  `handoff`, `methodist`, `product`, `schemas`) наружу не идут;
- `frontend/web/shared/*.svg|png` - только логотипы.

Про логотипы стоит пояснить, иначе исключение выглядит лишним: print-HTML
ссылается на них относительным путём `../frontend/web/shared/...`, потому что
те же файлы Chrome рендерит в PDF через `file://`
(`scripts/build_architecture_pdf.py`), а абсолютный путь там не разрешится.
Поэтому ссылки не переписывались на `/protocol-logo-*.svg` - вместо этого
разрешены сами картинки.

Остальные CSS/JS/SVG интерфейса раздаются отдельным списком
`_SHARED_STATIC_ASSETS` и в корневом mount не нуждаются.

### Проверка

`tests/test_static_exposure.py` - 47 тестов, три группы:

1. закрытое закрыто (25 путей, каждый до правки отдавался или был бы доступен);
2. нужное интерфейсу работает (11 путей) - иначе «безопасную» правку легко
   довести до неработающего UI;
3. обход фильтра не проходит: `..`, `%2e%2e`, `%2f`, двойные слэши, смена
   регистра (`/DOCS/`, `/Archive/`), выход из разрешённого каталога.

Плюс два теста проходят по **всему** списку отслеживаемых файлов: ни один файл
вне ожидаемого набора не должен быть публичным, и ни один файл запрещённого
типа (`.py`, `.md`, `.yaml`, `.docx`, `.jsonl`, …) - тоже. Это ловит не
известные случаи, а будущие: файл, добавленный завтра, публичным незаметно не
станет.

Тесты проверены мутацией - при отключённом фильтре они падают, то есть
защищают реально, а не проходят вхолостую.

## Мёртвый код

### Пакет конкурса перенесён в archive/

22 файла (`konkurs_*.py`, `build_konkurs_pdf.py`, `fill_konkurs_docx.py`,
`requirements-konkurs.txt`) переехали из `scripts/` в
`archive/scripts/konkurs/`. Это самодостаточный кластер: модули импортируют
только друг друга, а результат складывают в `archive/docs/konkurs/`, то есть
документы конкурса уже в архиве, а сборщики оставались в рабочем каталоге.

Единственная внешняя зависимость - `build_architecture_pdf` (нужен и
архитектурным PDF, поэтому остаётся в `scripts/`); в
`archive/scripts/konkurs/build_konkurs_pdf.py` добавлен путь к рабочему
`scripts/`. Проверено: `--help` отрабатывает с кодом 0. Ссылки в пяти
документах обновлены.

### Дубль логотипа

`frontend/web/shared/protocol_logo_curves_transparent.svg` был **байт в байт**
равен `protocol-logo-wordmark.svg` (11384 Б) и не упоминался ни в одной
разметке - его держали живым только маршрут в `rag_server.py` и запись в
`backend/frontend_paths.py`. Файл удалён вместе с маршрутом и записью.

### Скрипты без ссылок: список, а не удаление

`scripts/ops/find_orphan_scripts.py` строит индекс содержимого всех
отслеживаемых файлов и проверяет, упоминается ли каждый скрипт где-нибудь,
кроме себя: 40 файлов без единой ссылки, 23 - только со ссылками из
`archive/` или из завершённых планов и отчётов.

Массового удаления **не делалось**, и вот почему. У метода есть слепое пятно:
запуск через `python -m <пакет>`. Например `services/llm_worker/__main__.py` и
`services/mis_bridge/__main__.py` попали в «сироты», хотя это трёхстрочные
точки входа, а Dockerfile-ы вызывают полные пути
(`python -m services.llm_worker.grade_day`). Удалять их - ломать запуск ради
трёх строк. Похожая история возможна с любым скриптом, который вызывает cron на
GCE: такой вызов в репозитории не виден.

Поэтому 63 файла остаются как **разобранный список для владельца**: команда
`python3 scripts/ops/find_orphan_scripts.py` воспроизводит его в любой момент,
и по каждому файлу видно, откуда на него ссылаются. Проверять надо против
crontab на GCE, а не только против репозитория.
