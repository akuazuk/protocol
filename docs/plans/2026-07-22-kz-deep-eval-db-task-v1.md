## 0. Цель

Поднять оценку консультативных заключений (КЗ) с эвристической шкалы до **клинически
валидной, объяснимой и защитимой перед регулятором** оценки, которая:

1. **правильно оценивает КЗ** по осям документирования, клинического соответствия и
   безопасности;
2. **находит потенциальные ошибки/неточности** в двух самых важных местах:
   - **определение болезни** (диагноз не следует из жалоб/анамнеза/осмотра; диагноз не
     кодируется по МКБ; пропущен «красный флаг»; диагноз не соответствует обследованию);
   - **лечение** (назначение не по протоколу МЗ РБ; вне Республиканского формуляра;
     опасные лекарственные взаимодействия; high-alert-препарат без дозы/контроля;
     противопоказание при диагнозе; доза вне диапазона);
3. **опирается на всё доступное**: клинические протоколы МЗ РБ, коды МКБ, Постановление
   №55, Республиканский формуляр ЛС, материалы сайта Минздрава РБ, и **мировой опыт**
   (методики, базы взаимодействий, гайдлайны) - см. раздел 2.

Оценка нужна и как **число/статус**, и как **список конкретных находок** (что не так, где,
ссылка на протокол/пункт №55/МКБ/формуляр) для методиста и врача.

### 2.4. Методики оценки (на чём строим рубрику и грейдер)
- **PDQI-9 / PDSQI-9** (Physician/Provider Documentation Quality Instrument) - 9 атрибутов
  качества записи (актуальность, точность, полнота, полезность, организованность,
  понятность, сжатость, синтез, согласованность/«cited»), Likert/бинарно. Валидирован;
  для **коротких** консультативных заметок надёжность ниже - нужны якоря и обучение
  разметчиков. → ось A (документирование).
- **SaferDx Instrument** (Singh) - скрининг диагностических ошибок по 5 этапам
  диагностического процесса: (1) встреча врач-пациент (сбор/осмотр/назначение тестов),
  (2) выполнение и трактовка тестов, (3) наблюдение/отслеживание во времени,
  (4) факторы направления/субспециальности, (5) факторы пациента. → детектор «ошибка
  определения болезни».
- **MedCheckLLM** (guideline-in-the-loop) - извлечь Dx → подобрать гайдлайн → превратить
  в чек-лист → LLM сверяет запись с чек-листом → человек подтверждает. **Это ровно наша
  архитектура** (`kz_checklist` + RAG + `review_one_visit_full`). → грейдер.
- **LLM-as-judge best practices (2026)**: рубрика с явными уровнями; **атомарные бинарные
  пункты**; chain-of-thought; few-shot с одним concordant + одним discordant примером;
  human-in-the-loop для низкой уверенности. GPT-o3-mini/Claude достигают ICC ~0.82 с
  экспертом при валидной рубрике. → LLM НЕ финальный судья, а масштабируемый «второй ридер».
- **CRICO/ISMP/NICE**: «Big Three» диагностических ошибок (онко, сосудистые катастрофы,
  инфекции/сепсис) = наши red_flags; high-alert-препараты; safety-netting.

### 2.5. Доступная LLM-модель (проверено через Render, Oregon US)
`ListModels` с ключом проекта на Render (локально API геоблокирован) на 2026-07-23:

## 3. Целевая модель оценки КЗ (что считаем и что ищем)

Итог по каждому КЗ - структура:

```
KZ_evaluation = {
  scores: {
    documentation (ось A, PDQI-9-lite),
    clinical_concordance (ось B, протокол МЗ + МКБ),
    safety (ось C, red flags + препараты),
    regulatory_55 (reg55_criteria),
    overall (калиброванный, с risk-gate)
  },
  findings: [                       # ГЛАВНОЕ: конкретные находки
    {kind: "diagnosis_error"|"treatment_error"|"doc_defect"|"safety",
     severity: P0|P1|P2|P3,
     message, evidence(цитата из КЗ), source_ref(протокол/№55/МКБ/формуляр/DDInter),
     confidence, needs_human}
  ],
  status, percentile_in_specialty
}
```

### 3.1. Детектор ошибок ОПРЕДЕЛЕНИЯ БОЛЕЗНИ (приоритетно)
1. **Диагноз не обоснован**: нет связки жалобы+анамнез/осмотр → диагноз (SaferDx этап 1;
   №55 п. 4.2.10). Детерминированно (поля) + LLM-суждение о логической связи.
2. **Код МКБ невалиден/отсутствует/не соответствует тексту диагноза**: валидировать код
   через WHO ICD-API (локально); сверять название кода с текстом Dx (семантически).
3. **Диагноз ↔ обследование не бьются**: для Dx протокол требует обязательный метод, а его
   нет в КЗ (ось B, `required_exams` + `kz_checklist.must_have`).
4. **Пропущен red flag / «нельзя исключить» без маршрутизации** (Big Three) → P0.
5. **Диагноз-специфичные критерии не выполнены** (`diagnostic_criteria` протокола).
6. **Подозрительный/неполный диагноз** («?», «под вопросом») без плана дообследования → P0.

### 3.2. Детектор ошибок ЛЕЧЕНИЯ (приоритетно)
1. **Назначение не соответствует протоколу** по данному Dx (нет обязательной группы, или
   назначена группа вне протокола) - ось B, `treatment` протокола.
2. **Препарат вне Республиканского формуляра** РБ (флаг: не входит в формуляр → пометка,
   не всегда ошибка, но повод для внимания).
3. **Опасное лекарственное взаимодействие** между назначенными ЛС - DDInter 2.0
   (severity major/contraindicated) → P0/P1.
4. **High-alert-препарат без дозы/длительности/контроля** (ISMP) → P0.
5. **Противопоказание препарат ↔ диагноз/состояние** (drug-disease, DDInter DDSI).
6. **Доза вне диапазона / дубль терапии** (openFDA/DailyMed dosing; DDInter therapeutic
   duplication).

### 3.3. Risk-gate
Любой необработанный **P0** → cap итогового балла (45-55%) + `manual_review_required`.
P3 (формальные) не топят клинически хорошую запись.

### 3.4. Цепочка клинической согласованности (ядро точной оценки)
Главный принцип: **скор строится не по одному «общему впечатлению», а по проверке связей
между звеньями записи**. Каждая связь - отдельный измеримый параметр (атомарный бинарный
пункт с весом), что даёт максимально гранулярный и объяснимый балл. Звенья и колонки данных:

```
жалобы(complaints) + анамнез(anamnesis_doctor/auto) + осмотр(objective_status)
        │
        ▼  [L1] обоснованность: следует ли Dx из субъективных+объективных данных?
диагноз(clinical_diagnosis / diagnosis_main_text) + код(mkb_code_main)
        │
        ├─ [L2] кодирование: код валиден (ICD-API) и ≈ тексту Dx; mkb_code_agreement с mis_diagnos
        ├─ [L3] обследование: exam_recommendations/exam_data покрывают required_exams протокола по Dx
        └─ [L4] лечение: treatment_recommendations соответствуют treatment протокола по Dx
```

Для каждой связи считаем **три исхода**: `ok` / `gap` (пропуск) / `contradiction`
(противоречие). Противоречие (например, лечение антибиотиком при вирусном Dx; обследование
не по профилю Dx; жалобы без отражения в диагнозе) весит строже, чем пропуск.

### 3.5. Параметрическая рубрика (максимум измеримых параметров)
Скор считается по **~25-30 атомарным параметрам**, сгруппированным в оси. Каждый параметр:
`{id, ось, вес, значение (0/частично/1), evidence, source_ref}`. Набор (не финальный,
калибруется в §7):

**Ось A - Документирование (PDQI-9-lite, детерминированно + LLM «синтез/полезность»)**
- A1 жалобы заполнены и осмысленны (не «on»/шаблон); A2 анамнез; A3 объективный статус;
- A4 витальные показатели там, где уместны (t/АД/ЧСС/ЧД/ИМТ по профилю); A5 дата визита
  распознана и согласована (`visit_date`, `date_mismatch=0`); A6 врач/специальность указаны;
- A7 читаемость/структурность (LLM); A8 отсутствие копипаста/противоречий во времени (LLM);
- A9 план ведения сформулирован (обследование и/или лечение и/или маршрутизация);
- A10 манипуляции задокументированы, если проводились (`manipulations`, слот 24).

**Ось B - Клиническое соответствие (протокол МЗ + МКБ)**
- B1 Dx обоснован субъект.+объект. данными (§3.4 L1, LLM+детерм.);
- B2 код МКБ присутствует (`mkb_code_main`); B3 код валиден (локальный МКБ-10 RU + ICD-API);
  B4 код ≈ текст Dx; B5 согласие inline-кода и `mis_diagnos` (`mkb_code_agreement`);
- B6 обязательные обследования по Dx покрыты (`required_exams`/`must_have`) - сверка **и по
  тексту** (`exam_recommendations`/`exam_data`), **и по реально оказанным услугам**
  (`service_codes`/`service_names` из mis_data → канон через term_catalog);
- B7 диагностические критерии протокола выполнены (`diagnostic_criteria`/`clinical_criteria`);
- B8 лечение соответствует протоколу (`treatment.drug_groups/drugs/procedures/surgery`:
  обязательные группы есть, нет «чужих» групп);
- B9 дообследование назначено при неполном/сомнительном Dx («?»);
- B10 условные обследования выполнены при показаниях (`conditional_exams`: «если X → нужен Y»);
- B11 маршрутизация/наблюдение по протоколу (`follow_up`/`routing`/`hospitalization`:
  назначена повторная явка/направление/госпитализация, когда протокол требует).

**Ось C - Безопасность (red flags + препараты + пациент)**
- C1 red flags по жалобам/Dx обработаны или замаршрутизированы (`red_flags` условия +
  `global_red_flags` протокола; Big Three) - иначе P0;
- C2 нет опасных лекарственных взаимодействий (DDInter major/contra) - иначе P0/P1;
- C3 high-alert-препарат имеет дозу/длительность/контроль (ISMP);
- C4 нет противопоказания препарат↔диагноз/состояние (`contraindications`/
  `global_contraindications` протокола + DDInter drug-disease);
- C5 назначение уместно по **возрасту** (`patient_age_years`: STOPP/START/Beers у пожилых,
  педиатрические ограничения) и при беременности;
- C6 доза в диапазоне / нет дубля терапии (best-effort: дозы в протоколе не извлечены -
  openFDA/формуляр); C7 safety-netting (когда вернуться/тревожные симптомы, `follow_up`).

**Ось D - Регуляторика РБ**
- D1 соответствие №55 (`regulatory_compliance_pct`, дефекты P0-P3);
- D2 требования №127 для медосмотров (когда `kz_kind=certificate`), наблюдение по главам МКБ;
- D3 экспертиза ВН/листок нетрудоспособности оформлены корректно, если заявлены
  (`disability_expertise`/`sick_leave`).

Итог: `overall` = калиброванная (isotonic, §7) свёртка осей с **risk-gate** (§3.3) и
нормировкой по специальности/типу визита (перцентиль в специальности).

## 5. Подготовка данных - фундамент точной и объективной оценки (РЕАЛИЗОВАНО в коде)

Точность оценки упирается в чистые входные данные. Разбор `::` сверен со схемой
`epam/scheme_mis_protocols.docx` (44 индекса) - `RESULT_FIELD_MAP` полон и корректен.
Экспортёр `scripts/export_mis_protocol_month.py` + парсер `clinical_knowledge/mis_protocol_parse.py`
доработаны (перевыгрузка нужна на машине с БД, **VPN выключен** - правило `mis-mariadb.mdc`):

### 5.1. Даты визита - каноническая ISO + валидация трёх источников
Три источника даты, все должны совпадать (различается только формат):
- `visit_date_iso_slot` - слот `::1` (в КЗ врач видит ДД.ММ.ГГГГ);
- `visit_date_iso_db` - `mis_protocol.date` (ISO из БД);
- `visit_date_iso_mis` - `mis_data.vdate` (join).

`to_iso_date()` приводит любой формат (ISO / ДД.ММ.ГГГГ / date-объект) к `YYYY-MM-DD`.
Каноническая колонка **`visit_date`** (приоритет slot → db → mis_data); флаг
**`date_mismatch`** = 1, если источники расходятся (на существующих данных 0 расхождений).

### 5.2. Отбор только КЗ и медосмотров по клиническим специальностям
- `classify_kz_kind` → `kz_kind` ∈ {kz, certificate, diagnostic, non_clinical, empty};
  порядок: диагностика (УЗИ/рентген/лаб.) → неклинич. (медсестра/стоматолог/логопед) →
  справка (pay_type=12) → guard по содержанию → КЗ.
- Флаги в выгрузке: **`is_scored`** (kz+certificate - идут в оценку),
  **`is_clinical`** (врачебная клинич. специальность, включая пустые по содержанию).
- Единый источник правды по неклинич./диагностич. специальностям - `mis_protocol_parse`
  (его переиспользует `clinical_specialties.py`).

### 5.3. Структурный диагноз и коды МКБ (для детектора 3.1.2)
- Слот `22`: `##`/`|` → `diagnosis_list`, `diagnosis_main_index`.
- **`mkb_codes`** - все коды МКБ-10 из inline-текста диагнозов (`K29.3. …` → `K29.3`);
  **`mkb_code_main`** / **`diagnosis_main_text`** - основной по индексу `##[3]`.
- Покрытие на июле: код основного Dx у ~79% строк (остальное - пустой/описательный Dx).

### 5.4. Обогащение из mis_data (перевыгрузить: раньше не тянулось)
join по `visit_id` дополнительно возвращает:
- **`mis_diagnos`** - авторитетный «Диагноз МКБ-10» из mis_data → кросс-чек с inline-кодом:
  **`mkb_code_agreement`** ∈ {match, partial(3-знач.), mismatch, unknown};
- **`patient_bdate`** → **`patient_age_years`** на дату визита (для доз/педиатрии);
- **`mis_vdate` / `mis_vtime`** (третий источник даты/времени);
- сервисы (`service_codes`/`service_names`) и `pay_type`/`filial` - как раньше.

### 5.5. Валидация разбора `::`
- **`parse_ok`** = 1, если число слотов > максимального индекса схемы (строка не обрезана).
- `result_slots` - фактическое число слотов (в живых КЗ ~300).
- meta.json теперь содержит `date_validation`, `mkb_validation`, `parse_validation`,
  `patient_age_filled` - контроль качества каждой выгрузки.

Результат: `data/mis_protocol/mis_protocol_YYYY-MM.{parquet,csv}` (+ meta) - только на
/var/data и локально (ПДн), в git не коммитим.

### 5.6. Гейт «в оценку идут только КЗ» (чтобы не считать мусор)
Ключевое различие, чтобы оценка была честной:
- **Не-КЗ → полностью исключаем из оценки** (не строка врачебного заключения):
  `diagnostic` (УЗИ/рентген/функц./эндоскопия/лаборатория), `non_clinical`
  (медсестра/стоматолог/логопед/регистратор), `empty` (нет никакого клинического
  содержания) и **битые ::-строки** (`parse_ok=0`, строка обрезана при выгрузке).
- **Плохой/неполный КЗ → НЕ исключаем, а оцениваем низко.** Пустой диагноз, отсутствие
  обследования/лечения при клинической специальности - это *дефект качества*, ровно то,
  что мы хотим ловить. Исключать такие = скрывать проблему.

Гейт (enforced в `run_mis_protocol_l1_batch.split_kz_rows`):
`в оценку ⟺ kz_kind ∈ {kz, certificate} И parse_ok≠0`. Всё исключённое учитывается в
`excluded_breakdown` (панель «Гигиена данных»): по видам, по специальностям, `n_corrupt_parse`.

Замер на июле (8 937 строк) - утечки мусора практически нет:
- в оценку идёт **8 716**; исключено **221** (`non_clinical` 219, `empty` 2);
- `parse_ok=0`: **0**; полностью пустых среди оцениваемых (нет Dx И нет жалоб И нет плана): **0**;
- пограничные: без диагноза 14, без плана 218, спец. не распознана 84 - **остаются в оценке
  как низкий балл** (это дефекты, а не мусор), но помечаются в находках (ось A/№55).

Единый источник классификации - `clinical_knowledge/mis_protocol_parse.classify_kz_kind`
(его же переиспользуют `clinical_specialties.py` и кабинет методиста), чтобы правила отбора
не расходились между экспортом, батчем и дашбордом.

## 6. Реализация детекторов (движок)

Новый модуль `clinical_knowledge/kz_deep_eval.py` (stdlib + опц. эмбеддинги), функция
`evaluate_kz_deep(case, protocol_ctx, drug_ctx, icd_client) -> findings + scores`.
Подключается в `run_mis_protocol_l1_batch.py` (флаг `--deep-eval`) и в
`review_one_visit_full` (для полного отчёта одного КЗ).

### 6.1. Диагностические детекторы
- `dx_substantiation(case)` - детерминированно + опц. LLM (логическая связь жалобы→Dx).
- `icd_validate(dx_code, dx_text, icd_client)` - код валиден? название кода ≈ тексту Dx?
- `dx_vs_exams(case, protocol)` - покрытие `required_exams`/`must_have` семантически
  (term_catalog + эмбеддинги).
- `red_flag_scan(case, protocol.red_flags)` - «нельзя исключить»/тревожные формулировки без
  маршрутизации → P0.
- `dx_criteria(case, protocol.diagnostic_criteria)`.

### 6.2. Лечебные детекторы
- `drugs_extract(case)` → список назначенных ЛС (drug_normalizer).
- `tx_vs_protocol(drugs, protocol.treatment)` - соответствие группам протокола.
- `formulary_check(drugs, rb_formulary)` - вне формуляра → флаг.
- `ddi_check(drugs, ddinter)` - взаимодействия (severity) → P0/P1 с механизмом+тактикой.
- `high_alert_check(drugs, high_alert, case)` - доза/длительность/мониторинг обязательны.
- `drug_disease_check(drugs, dx_codes, ddinter_ddsi)` - противопоказания.
- `dose_range_check(drugs, dailymed/formulary)` - доза вне диапазона (best-effort).

### 6.3. Оси и итог
- Ось A: PDQI-9-lite (детерминированные прокси заполненности/согласованности + LLM для
  «синтез/полезность»).
- Ось B: клиническое соответствие (dx_vs_exams + tx_vs_protocol + dx_criteria).
- Ось C: safety (red flags + ddi + high_alert + drug_disease + vitals).
- reg55: как есть.
- overall: калиброванный (axes_thresholds) с risk-gate.

### 6.4. LLM-грейдер (масштабируемый второй ридер, MedCheckLLM-стиль)
`scripts/grade_kz_llm.py` (все LLM-вызовы КЗ - **только через Render**, §2.5):
1. извлечь Dx → выбрать протокол (RAG по protocol_summaries) → взять `kz_checklist`;
2. подать в LLM: текст КЗ + чек-лист (атомарные бинарные пункты рубрики §3.5) +
   явная инструкция проверить **цепочку согласованности §3.4** (жалобы→Dx→обследование→
   лечение, с исходами ok/gap/contradiction) + правило вывода в JSON; few-shot: 1 хороший +
   1 плохой пример; chain-of-thought;
3. LLM возвращает per-item pass/fail + finding(evidence-цитата + source_ref) + confidence;
4. **Двухтировая схема**: `gemini-3.6-flash` - первый проход по всем КЗ (дёшево);
   спорные / низкая уверенность / расхождение с детерминированными детекторами
   эскалируются на **`gemini-3.1-pro-preview`** (судья); остаток с `needs_human=true` -
   в очередь методисту.
Хранить сырые ответы LLM только на /var/data (могут содержать ПДн).

## 7. Gold-выборка и калибровка (валидность)

1. `scripts/build_kz_gold_sample.py` - стратифицированная выборка 600-800 КЗ (специальность
   × банд × pay_type × red-flag), манифест на /var/data.
2. **Двойная человеческая разметка методистами** по кодбуку (PDQI-9 + оси A/B/C + флаг
   «potential harm» + класс ошибки + вердикт) с LLM-предразметкой; арбитраж при
   расхождении > 1 балла; согласие - weighted kappa (цель κ ≥ 0.6).
3. `scripts/calibrate_axes_thresholds.py` - пороги статусов из ROC/квантилей по gold, не
   «90/75/50»; веса осей - ordinal/isotonic регрессия к вердикту методиста.
4. Валидация на held-out 20%: **QWK** (статус vs методист) цель ≥ 0.70; **recall по
   potential-harm** цель ≥ 0.90 (не пропустить опасное важнее точности).
5. После валидации - включить `CONSULT_AXES_OVERALL=1`.

### 7Б.1. Таблица оценок с фильтрами по всем столбцам
Строка = визит/КЗ. Колонки (сортируемые): дата, филиал, врач (ФИО), специальность, тип
(`kz_kind`), основной Dx + код МКБ, overall + статус, оси A/B/C, №55, число находок по
severity (P0-P3), `needs_human`. **Фильтры (многокритериальные, комбинируются):**
- период (`visit_date` from/to) и месяц; специальность; филиал; врач; `kz_kind`
  (КЗ/справка); pay_type;
- банд overall (напр. <50 / 50-75 / 75-90 / ≥90) и статус;
- наличие находок по типу (diagnosis_error / treatment_error / doc_defect / safety) и severity;
- глава МКБ (A00-... по первой букве/рубрике `mkb_code_main`); `mkb_code_agreement`
  (match/partial/mismatch/unknown); возрастная группа (`patient_age_years`: дети/взрослые/
  пожилые); `date_mismatch`; `parse_ok`.
Пресеты одним кликом: «P0 не обработан», «Dx без валидного кода», «лечение вне протокола»,
«обследование не покрывает Dx», «худшие 50 по специальности».

### 7Б.2. Диаграммы (пастельные тона, шрифты без засечек - правило проекта)
- распределение overall (гистограмма) с порогами статусов;
- средний скор и доля «плохих» **по специальностям** (бар, сортировка);
- **тепловая карта специальность × severity находок** (где чаще всего опасные ошибки);
- доля типов находок (diagnosis/treatment/exam/doc/safety) - стек-бар;
- воронка цепочки §3.4 (сколько КЗ теряется на L1/L2/L3/L4);
- топ проблемных кодов МКБ и топ «лечение вне протокола» по Dx.

### 7Б.3. Динамика (тренды во времени)
- overall и оси A/B/C **по месяцам** (янв→июль) - линия с доверит. коридором;
- динамика доли P0/находок на 100 КЗ по месяцам; по специальности (мини-спарклайны в строке
  специальности); по врачу (для разбора роста/падения);
- сравнение двух периодов (уже есть `compare_month`) - расширить на любой диапазон и на
  разрез по осям и типам находок (Δ п.п., ↑/↓/≈).

### 7Б.4. Расширенный отчёт по выбранной позиции (главное)
Клик по строке → полный разбор одного КЗ:
- шапка: пациент(id)/врач/специальность/дата/филиал, тип, overall + статус + перцентиль;
- **по-параметрический скор** (§3.5): каждый из ~25-30 пунктов с значением, весом, evidence-
  цитатой из КЗ и `source_ref` (протокол МЗ/пункт №55/код МКБ/формуляр/DDInter);
- блок **находок** по severity: что не так, цитата-доказательство, ссылка на источник,
  confidence, `needs_human`; отдельно выделены `diagnosis_error` и `treatment_error`;
- цепочка §3.4 визуально (жалобы→Dx→обследование→лечение) с пометками ok/gap/contradiction;
- сырой текст КЗ по блокам (жалобы/анамнез/осмотр/Dx/обследование/лечение) со связью к пунктам;
- действия методиста: согласиться/оспорить пункт, отправить на ручной разбор (пишем в
  feedback_store для калибровки §7).

### 7Б.5. Экспорт
CSV/JSON текущей выборки (с учётом фильтров) и отчёт по одному КЗ (для обсуждения с врачом).
ПДн - только авторизованному методисту (`_require_methodist_auth`), не в git.

## 11. Риски

- **Матч названий ЛС** (свободный текст врача ↔ INN/ATC) - главный технический риск;
  смягчаем нормализатором + RxNorm + синонимами; при неуверенности - `needs_human`.
- **Ложные срабатывания DDI** (назначения в разное время, не одновременный приём) -
  помечать как «проверить», не как факт вреда.
- **ПДн наружу**: диагнозы/ЛС не отправлять во внешние API - ICD-API локально, DDInter
  офлайн, RxNorm - только имена препаратов (без пациента).
- **Смещение LLM**: финальное слово - методист; замер согласия; CoT + рубрика + few-shot.
- **Актуальность протоколов/формуляра**: фиксировать дату версии НПА в `source_ref`.
- **Стоимость разметки**: снижаем стратификацией + LLM-предразметкой.
