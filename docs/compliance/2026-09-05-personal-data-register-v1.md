# Реестр обработки персональных данных Protocol

Статус: draft. Дата: 2026-09-05. Версия: v1.

**Чем этот документ является.** Инженерный реестр: что за данные обрабатывает
система, где они лежат, куда уходят и что уже сделано в коде. Он нужен, чтобы
юрист и ответственный за защиту персональных данных ОДО «Медицинский центр
«Кравира» работали с фактами, а не с предположениями.

**Чем не является.** Это не юридическое заключение и не политика обработки
персональных данных. Формулировки правового основания, текст политики и текст
согласия готовит клиника; здесь только то, что видно из кода и прода, и
перечень открытых вопросов.

## 1. Категории данных

| Категория | Примеры полей | Где хранится |
|---|---|---|
| Идентификаторы пациента | `patient_id`, `patient_key`, `visit_id`, `mis_id` | MariaDB МИС (источник), `warehouse/*.sqlite`, `secure_cases/**/*.jsonl` |
| Специальные персональные данные (сведения о здоровье) | жалобы, анамнез, объективный статус, диагноз и МКБ, обследования, назначения, лабораторные результаты | `mis_zoho.sqlite` (`mis_data`, 4 727 767 строк), `mo_analytics.sqlite`, `mo_lab.sqlite` (`fact_mo_lab`, 449 227 строк) |
| Данные врача | `doctor_fio`, `doctor_specialization`, `specialist_id` | те же склады |
| Документы пациента (B2C) | загруженные PDF и фотографии заключений | загрузка в обработку, архив при `CONSULT_ARCHIVE_ANALYSES=1` |
| Телеметрия | хеши текста, баллы, флаги качества, без клинического текста | `data/ml/feedback/*.jsonl` |

Итого на прод-диске `/var/data/medical_exams` - 2.7 ГБ, 200 файлов `.jsonl`.

## 2. Кто обрабатывает

| Участник | Роль | Территория |
|---|---|---|
| ОДО «МЦ «Кравира» | оператор | Беларусь |
| Собственная VM `protocol-app` (GCE, `europe-central2-a`) | инфраструктура обработки | Польша, ЕС |
| Google (Gemini API, embeddings) | обработчик по поручению | вне Беларуси |
| Google Cloud (диск VM, снапшоты) | инфраструктура хранения | Польша, ЕС |

Ключевой факт для правовой оценки: **сведения о здоровье покидают Беларусь**
дважды - как содержимое запросов к Gemini и как данные на диске VM в ЕС.

## 3. Что уходит в Gemini после правок 2026-09-05

Полный аудит путей выполнен по коду. Было и стало:

| Путь | Было | Стало |
|---|---|---|
| `mis_kz_quality._build_full_llm_prompt` (полный разбор КЗ для методиста) | ФИО врача, `Visit ID`, `Patient ID`, текст КЗ целиком | инициалы врача, псевдонимы `visit-…` / `patient-…`, текст через `redact_text_for_llm` |
| `mo_llm_action_judge.build_prompt_a/_b` (судья очереди действий) | `case_id`, `visit_id`, `mis_id` в мете и в схеме ответа | псевдонимы; `mis_id` из схемы убран |
| `mo_case_narrative.build_narrative_prompt` | `visit_id`, `patient_id`, ФИО врача в JSON brief | `redact_mapping_for_llm` |
| `grade_kz_llm.build_grader_prompt` (ночная оценка) | поля МИС как есть, вместе с шапкой КЗ | `redact_text_for_llm` по каждому полю |
| Баннер демографии в consult-review | точная дата рождения пациента | только возраст в полных годах |

Механика: `clinical_knowledge/phi_for_llm.py`. Псевдоним - HMAC-SHA256 на
ключе `PHI_PSEUDONYM_KEY` (в проде - Secret Manager), первые 8 hex-символов.
Устойчивость псевдонима сохраняет возможность сверки двух разборов одного
случая, но не позволяет восстановить номер без ключа.

Проверки: `tests/test_phi_for_llm.py` - 13 тестов, включая «клиника осталась,
идентификатор исчез» по каждому промпту.

## 4. Что в Gemini всё ещё уходит и почему

| Данные | Обоснование | Возможная мера |
|---|---|---|
| Клинический текст (жалобы, анамнез, статус, диагноз, назначения) | предмет оценки; без него задача не существует | сокращать объём (`CONSULT_REVIEW_CONSULT_CHARS`), не отправлять при выключенных флагах |
| Возраст, пол, специальность врача, филиал | нужны для выбора протокола и трактовки | оставить |
| Изображение документа при OCR (`image_ocr._ocr_gemini_vision`) | распознаётся весь лист, включая шапку с ФИО | **открыто**: либо локальный OCR, либо обрезка шапки до отправки |
| Текст запроса врача в embeddings (`_gemini_embed_one`) | врач может вписать ФИО вручную | **открыто**: обезличивание запроса перед embedding |

Первые два пункта - осознанный минимум. Последние два - незакрытые риски,
вынесены в шаги ниже.

## 5. Открытые вопросы к клинике (не решаются кодом)

1. **Правовое основание** по закону 99-З для передачи сведений о здоровье
 обработчику за пределами Беларуси. Требует решения оператора: согласие
 субъекта, договор или иное основание.
2. **Договор с Google** об обработке по поручению: определить, какие условия
 Google Cloud / Gemini API применяются к учётной записи клиники, и
 зафиксировать их как поручение обработчику.
3. **Политика обработки персональных данных**: в репозитории её нет вообще -
 ни файла, ни страницы в UI. Для B2C-контура это обязательный документ.
4. **Согласие пациента** на загрузку и анализ документа: механизма нет.
 Нужен текст, отметка о получении и её хранение.
5. **Сроки хранения**: в коде нет ни одного правила удаления клинических
 данных. Нужны сроки по каждой категории раздела 1 и процедура удаления.
6. **Уведомление о трансграничной передаче** - в объёме, который определит
 ответственный за защиту персональных данных.

## 7. Что уже сделано по защите данных (для справки)

- Порт приложения закрыт наружу: контейнер слушает `127.0.0.1:8000`, доступ
 только через HTTPS-прокси.
- `ALLOWED_ORIGINS` сужен до `https://protocol.kravira.by`, CSP включён.
- Персональные учётные записи методистов вместо общего токена, ограничение
 попыток входа, сравнение токенов через `hmac.compare_digest`.
- Клинические материалы и ПДн не попадают в репозиторий: pre-commit и
 CI-проверка `scripts/ops/check_no_phi_staged.py`.
- Аудит калибровки пишется с `flock` и `fsync`.
