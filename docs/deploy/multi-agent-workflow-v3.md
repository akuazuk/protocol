# Канон v3: несколько агентов, несколько компьютеров, один прод

Дата: 2026-09-05
Статус: active, canonical
Заменяет: `multi-agent-single-repo-render-runbook-v2.md` (описывал Render как прод)

Короткие обязательные правила - в корневом `AGENTS.md`. Здесь операционный
workflow: почему он такой и что делать в конкретной ситуации.

Документ написан для агента, который открыл проект и не помнит предыдущую
сессию. Если правило кажется избыточным, читай абзац «почему»: почти каждое
появилось после конкретной аварии.

---

## 1. Три инварианта

Всё остальное - следствия.

**И1. Общая мутабельная ветка не существует.** Одна задача - одна ветка - один
владелец - один worktree. `main` меняется только merge PR.

**И2. Пересечение файлов известно до правки, а не при merge.** Конфликт,
обнаруженный в момент merge, уже стоил двух работ. Обнаруженный до правки
стоит одного вопроса.

**И3. Прод меняет один назначенный человек в одно окно времени.** Прод один -
GCE `https://protocol.kravira.by`.

Почему так строго: проект пишет клинические оценки живых врачей. Потерянный при
разрешении конфликта коммит - это не «переделаем», а неверная оценка в отчёте
методиста, которую никто не заметит.

---

## 2. Роли

| Роль | Что делает | Чего не делает |
|---|---|---|
| Владелец задачи | своя ветка, свой worktree, свой PR | не трогает чужие ветки и не деплоит |
| Ревьюер | diff, тесты, ПДн, влияние на соседние PR | не дописывает код в чужую ветку |
| Релиз-координатор | merge SHA -> deploy -> smoke | не мержит второй PR в своё окно |

Один человек может быть всеми тремя по очереди. Нельзя быть релиз-координатором
двух деплоев одновременно.

---

## 3. Уровни риска: где пересекаться дорого

Машинная карта - `.github/CODEOWNERS`. Смысл уровней:

| Уровень | Пути | Цена пересечения |
|---|---|---|
| 1 | `docs/`, `ml/`, `eval/` | текстовый конфликт, чинится за минуту |
| 2 | `clinical_knowledge/`, `corpus_pipeline/`, `services/` | ошибка тихо меняет оценку врача |
| 3 | `frontend/web/` | ломается интерфейс врача или пациента |
| 4 | `.github/`, `tests/`, `ruff.toml`, `scripts/ops/` | ослабление порога снимает защиту со всех задач |
| 5 | `deploy/`, `rag_server.py`, `requirements*`, `AGENTS.md` | прод и правила |
| 6 | `corpus_chunks_parts/`, `data/`, `minzdrav_protocols/`, `config/` | перезапись = потеря текста протокола |

Правила по уровням:

- уровни 2 и 3: **один модуль за PR**, с тестом на инвариант;
- уровень 4: **отдельный PR**, никогда попутно с фичей (иначе review смотрит на
  фичу и пропускает снятый барьер);
- уровень 6: только через скрипты публикации, никогда руками. Причина -
  `docs/plans/2026-09-05-corpus-integrity-v1.md`.

### Самый конфликтный файл проекта

`docs/plans/README.md`. На 2026-09-05 его держат четыре открытых PR
одновременно. Это индекс планов, в него дописывает строку почти каждая задача.

Правило: **добавляй строку в конец своей секции и не переформатируй таблицу.**
Переформатирование делает конфликт неразрешимым автоматически. Проверка
`tests/test_plans_index.py` не даёт индексу разойтись с диском.

## 4. Начало работы

Никогда не начинай с `git pull` в незнакомом checkout: неизвестно, чей он и что
в нём незакоммичено.

```bash
cd /path/to/Protocol
git status --short --branch
git fetch --prune origin
git rev-list --left-right --count origin/main...HEAD
python3 scripts/ops/pr_dashboard.py
```

Последняя команда - главная. Она отвечает, кто какие файлы держит, что с чем
конфликтует и какие PR зависли.

Перед правкой конкретного файла:

```bash
python3 scripts/ops/pr_dashboard.py --files clinical_knowledge/mo_backend.py
```

Выход 1 означает «занят»: согласуй с владельцем или возьми другую задачу.

Свой worktree:

```bash
scripts/ops/git_task_start.sh mo-lab-import --pc=pc1 \
  --branch=cursor/mo-lab-import-agent1-pc1
cd /private/tmp/protocol-task-mo-lab-import-pc1
test -z "$(git status --porcelain)"
git merge-base --is-ancestor origin/main HEAD
```

### Имя ветки

```text
cursor|codex|hotfix|release/<задача>[-agent<N>]-pc<N>
```

Проверяется блокирующе (`scripts/ops/check_pr_hygiene.py`). Имя обязано
называть задачу и компьютер, потому что по нему определяется владелец в
дашборде и в handoff. Запрещены `main`, `master`, `codex/main-sync`,
`cursor/main-sync`: общая мутабельная ветка нарушает И1.

## 5. Размер PR

Один PR - одна причина для review.

| Метрика | Порог | Что делает проверка |
|---|---|---|
| файлов | 40 | предупреждение |
| строк | 1500 | предупреждение |

Пороги не блокируют: программа доведения до прода честно бывает крупной. Но
крупный PR обязан объяснить в описании, почему он не разбит. Причина не в
эстетике: чем шире diff, тем больше соседних задач придётся переносить руками,
и тем менее внимателен review к каждой строке.

Если причины review независимы (фича + барьер CI + рефакторинг) - это три PR.

## 6. Пересечения и синхронизация

Перед правкой и после чужого merge:

```bash
scripts/ops/check_pr_file_overlap.sh
scripts/ops/rebase_task_onto_main.sh
```

`check_pr_file_overlap.sh` отделяет **hard** от **soft**: правка
`rag_server.py`, состоящая только из строки `BUILD_VERSION`, считается soft,
потому что rebase-скрипт снимает такой конфликт сам и заново ставит версию.
Любой другой общий файл - hard.

При hard-пересечении выбери одно и запиши выбор в PR:

1. разделить задачу по непересекающимся файлам;
2. дождаться merge первого PR и создать ветку заново от свежего `origin/main`;
3. назначить одного владельца интеграционного PR.

Чего не делать: разрешать конфликт, выбрасывая чужие блоки; force-push общей
ветки; пересылать незакоммиченные изменения между компьютерами. Общий
checkpoint - только commit в task-ветке на `origin`.

CI устроен так, чтобы вкладки не гасили друг друга: группа concurrency на номер
PR, `cancel-in-progress: false`. После нового push той же ветки **не смотри
старый run**: номер run новый.

## 7. Коммит и PR

```bash
scripts/ops/bump_build_version.sh <slug>   # если изменение попадёт в деплой
git diff --check
# релевантные тесты и линт изменённых файлов
git add <точные-файлы>
git commit -m "type(scope): суть"
git push -u origin HEAD
gh pr create --fill
```

Описание PR заполняется по шаблону `.github/pull_request_template.md`. Поля
`Владелец`, `Зона изменений`, `Зависит от PR` нужны не для отчётности: по ним
соседняя вкладка решает, ждать ей merge или можно править. Незаполненный
шаблон блокирует PR.

Draft PR - способ объявить владение задачей. Открывай его сразу после первого
безопасного коммита.

Обход проверки гигиены - метка `hygiene-ack`. Обход остаётся в истории PR,
поэтому решение видно, а не растворяется.

Запрещено в коммитах, PR и docs: трейлеры `Co-authored-by:` от IDE и агентов,
`Made with`, `Generated by`. Сообщение коммита - только суть изменения.

## 8. Merge

Перед merge заново:

```bash
git fetch origin
git rev-list --left-right --count origin/main...HEAD
python3 scripts/ops/pr_dashboard.py
```

Порядок при жёстких пересечениях: мержить по одному, второй владелец переносит
свои изменения на новый `origin/main`. Два PR, которые жёстко пересекаются, не
мержатся подряд без rebase между ними.

### Как понимать «merged» после squash

После squash GitHub создаёт **новый** commit в `main`. Исходные коммиты
task-ветки не становятся ancestors `main`, поэтому `git branch --merged` и граф
истории дают ложное «ветка не вошла».

Каноническая проверка: PR имеет `merged=true`, merge SHA присутствует в
`origin/main`, diff PR есть в `main`, прод-smoke подтверждает функцию. Только
после этого ветку можно удалять; удаление ветки не удаляет merged код.

## 9. Релиз

Единственный прод-путь:

```bash
bash deploy/gcp-app/deploy_to_gce.sh
curl -fsS https://protocol.kravira.by/health/live
curl -fsS https://protocol.kravira.by/api/version
```

Скрипт отказывается работать, если `HEAD != origin/main`; на VM уезжает
`git archive` релизного SHA, образ тегируется по SHA, при неудачном health или
несовпадении версии выполняется автоматический откат.

Deploy завершён, когда на `protocol.kravira.by` совпали `version` и
`git_commit`, `/health/live` успешен и пройден smoke самой функции.
`BUILD_VERSION` обязателен, но недостаточен: версию можно забыть поднять,
поэтому проверяется функция.

В окне релиза запрещено: merge второго release PR, ручной deploy или restart
другого SHA, изменение env контейнера, перестройка `/var/data/medical_exams`,
правка firewall. Порт `8000` наружу не открывать.

Render продом и откатом **не является**: сервис приостановлен и отдаёт `503`.
Откат - предыдущий образ по SHA плюс снапшот диска `protocol-data`. Подробности:
`docs/deploy/gce-production-runbook.md`.

## 10. Зависшие PR

PR, открытый больше **14 дней**, считается зависшим: его база разошлась с
`main`, и он превратился из работы в источник конфликтов. На 2026-09-05 таких
семь.

Решение по каждому - одно из трёх: домержить, переоткрыть от свежего `main` или
закрыть с записью причины. Держать открытым «на память» нельзя: дашборд
показывает такой PR как владельца файлов, и соседние задачи ждут впустую.

## 11. Восстановление грязного или разошедшегося checkout

Не выполнять `reset --hard`, `clean -fd`, `checkout` поверх изменений. Сначала
зафиксировать факты:

```bash
git status --short --branch
git rev-list --left-right --count origin/main...HEAD
git log --oneline origin/main..HEAD
```

Локальные коммиты сохранить отдельной rescue-веткой и push только после
просмотра diff. Незакоммиченные файлы инвентаризировать отдельно. До решения
владельца продолжать работу в **новом** clean worktree от `origin/main`.

Чужой checkout не чинить и не переключать. Даже если он явно сломан: там могут
быть незакоммиченные результаты чужого прогона.

---

## 12. Что запрещено всегда

1. Push напрямую в `main`.
2. Force-push общей или чужой ветки.
3. Переиспользование `codex/main-sync` и любой общей мутабельной ветки.
4. Разрешение конфликта выбрасыванием чужих блоков.
5. Deploy не из merged `origin/main`, promote task-HEAD.
6. Второй deploy в окне первого.
7. Коммит токенов, `.env`, дампов БД, клинических CSV/parquet и ПДн.
8. Печать клинического текста, токенов и ID пациентов в логах, PR и ответах.
9. Открытие порта `8000` наружу.
10. Ослабление барьера CI попутно с фичей.

## 13. Частые ситуации

**«Соседняя вкладка смержила PR, у меня конфликт»**

```bash
scripts/ops/rebase_task_onto_main.sh
```

Конфликт только в `BUILD_VERSION` скрипт снимает сам. Любой другой - стоп и
разговор с владельцем.

**«Два PR правят один клинический модуль»** Не мержить оба «на глаз». Один
владелец, один PR, второй переносит изменения после merge.

**«Нужно поправить чужой зависший PR»** Не дописывать в чужую ветку. Открыть
свою от свежего `main`, в описании указать `Зависит от PR: #NNN`.

**«CI красный, но не из-за меня»** Отделить baseline-падения от падений diff и
написать это в PR. Merge при красном обязательном CI - явное решение владельца,
не молчаливое.

**«Джоба показана `cancelled` - значит, соседняя вкладка отменила мой прогон»**
Почти наверняка нет. `cancel-in-progress: false` стоит во всех workflow;
GitHub помечает как `cancelled` и джобу, которая **упёрлась в
`timeout-minutes`**. Отличить просто: у отменённой по таймауту длительность
равна лимиту, и «отменён» будет конкретный шаг, а не вся джоба сразу.
Так было 2026-09-05 с `lint-and-test`: 15.2 минуты при лимите 15. Лечится
запасом лимита, а не поиском виноватой вкладки.

**«Проверка гигиены блокирует, а исправить нельзя»** Метка `hygiene-ack` и
причина в описании PR.

```bash

```

## 15. Handoff

В конце сессии - `docs/reports/YYYY-MM-DD-handoff-<topic>.md`: repo, branch,
worktree, base SHA, HEAD SHA, PR; сделано и не сделано; тесты и известные
baseline-падения; был ли merge и deploy и точный прод SHA; `BUILD_VERSION` и
результат smoke; одна безопасная следующая команда; файлы, которые нельзя
трогать параллельно.

Не писать «готово», если коммит существует только локально, PR не merged или
прод не проверен на `protocol.kravira.by`. Эти состояния отмечаются отдельно и
честно.
