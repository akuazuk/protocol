## 1. Контекст: что ломается сейчас

Методист в разборе случая → блок «Протоколы МЗ» → клик по названию / «Карточка» →  
`/proto-viewer.html?path=…` и часто видит:

```text
Клинический протокол
Навигация по протоколу
Структурные выводы по этому протоколу недоступны. Откройте PDF.
[Открыть PDF]
```

Это **не только баг кнопки**. Цепочка:

```text
разбор (mo-app) → viewer_url
       ↓
proto-viewer.html  →  GET /api/protocol-brief
       ↓
build_protocol_brief  →  sections[] пустой  →  тупик «откройте PDF»
```

### Корни (по приоритету)

1. **Brief пустой** - нет Protocol Summary по path и/или нет rich-chunks (RAG не готов / path не в индексе) → `available: false`.
2. **Deep-link мёртв** - `protocol_nav_api_path` умеет `section`/`q`, doctor UI ещё и `page`, но viewer читает только `path`, `q`, `icd`. Параметр `page` игнорируется.
3. **Путаница CTA** - «Открыть КП» ведёт в **поиск каталога**, навигация - только title / «Карточка».
4. **Качество текста** - обрезанные фразы (`…`), legal/boilerplate, title-echo уже частично режутся в `protocol_brief.py`, но при thin summary + слабом fallback пользователь видит либо пусто, либо обрывки.
5. **Два мира UI** - viewer на своём Outfit/mint; МО/кабинет - `mo-tokens`. Ощущение «чужой» страницы.

Измерено ранее: ~9 PDF каталога без summary; stomatology - coverage нормальный. Пустой экран чаще из **runtime brief** (нет chunks), не из «все КП битые».

## 2. Цель (что должно быть у методиста)

За 10-20 секунд после клика:

1. Видит **полное название** КП и рубрику.
2. Слева - **оглавление разделов** (диагноз / обследования / лечение / …), не пустой экран.
3. Справа - **читаемые пункты** без мусора и без обрезки смысла (целые предложения; «ещё» для длинных).
4. У каждого пункта - **«Стр. N → оригинал»**: PDF на **той же странице**, откуда цитата (`#page=N`).
5. Всегда есть запасной путь: **оглавление из текста** + полный PDF, даже если карточка Summary слабая.
6. Визуально - как карточки разбора МО (поверхности, кнопки, чипы, типографика).

Не цель: LLM-пересказ протокола; замена PDF; оценка МО внутри viewer.

## 3. Целевой UX

### 3.1 Из разбора случая (кнопки)

| Сейчас | Станет |
|--|--|
| Название → viewer | без изменения смысла |
| «Открыть КП» → `/doctor/search` | переименовать в **«Поиск в каталоге»** |
| «Карточка» → viewer | переименовать в **«Открыть протокол»** (primary) |
| нет page/section в URL | передавать `page` / `section`, если suggest/zone знает якорь |

Копирайт под блоком: «Открыть протокол - навигация и PDF по страницам; поиск - если нужен другой КП».

### 3.2 Страница навигации (переделка `proto-viewer.html`)

Макет в токенах МО (без отдельного green-kit):

```text
┌─────────────────────────────────────────────────────────┐
│ Клинический протокол · [рубрика] · [чипы источника]     │
│ Полное название КП                                       │
│ [Открыть PDF]  [На странице якоря]  [Полный текст ▾]    │
├──────────────┬──────────────────────────────────────────┤
│ Разделы      │ Пункты раздела                            │
│ · Диагноз    │ • целый текст                             │
│ · Обслед.    │   «цитата» · Стр. 12 → оригинал          │
│ · Лечение    │ • …                                       │
│ · …          │                                           │
│              │ если brief thin: оглавление из source-text│
└──────────────┴──────────────────────────────────────────┘
```

Правила контента:

- Показывать раздел только если есть ≥1 **принятый** пункт (после фильтров).
- Не резать посередине предложения в UI: лимит увеличен / «Показать полностью».
- Legal/admin, title-echo, дубли - скрывать (уже есть в brief; усилить пороги).
- Если `?page=` - сразу открыть PDF во втором табе/панели на странице **или** подсветить пункт с этой страницей.
- Если `?section=` - выбрать раздел в rail при загрузке.
- Баннер `needs_review` - мягкий, как status-chip в МО, не пугать пустотой.

### 3.3 Кабинет методиста / врач

Тот же `proto-viewer.html` (один navigator). Doctor chrome-tabs можно оставить, но **тело** - общие MO-токены, чтобы разбор и кабинет не расходились.

## 4. Данные и API

### 4.1 Каскад контента (главное изменение backend)

Сейчас: summary → (+ rich chunks добить) → иначе **пусто**.

Станет:

```text
L1  Protocol Summary / card sections   (как сейчас)
L2  Rich chunks → points + page_start  (усилить: не требовать 3 пункта,
                                        чтобы «убить» весь раздел)
L3  protocol-summary-nav / source_text  → оглавление разделов PDF
L4  Только PDF + список страниц из locator (last resort)
```

`available: true`, если есть **хотя бы один** из L1-L3. Сообщение «структура недоступна» - только если нет path/PDF.

### 4.2 Ссылка на оригинал

| Поле | Источник | UI |
|--|--|--|
| `page_start` | summary `source_ref` или grounding `page_lookup` / chunk meta | кнопка «Стр. N» → `/api/protocol-pdf?path=…#page=N` |
| `quote` | дословная цитата | под пунктом, мелким текстом |
| `verified` | grounded | чип «страница сверена» / без чипа если нет |

Цель метрики: ≥80% видимых пунктов на топ-КП разбора имеют кликабельную страницу (на контрольном наборе из 20 кейсов).

### 4.3 Эндпоинты

| Endpoint | Роль в v1 |
|--|--|
| `GET /api/protocol-brief` | расширить: never-empty cascade; `page` echo; полнее quotes |
| `GET /api/protocol-source-text` | fallback TOC в том же UI, не отдельный тупик |
| `GET /api/protocol-pdf` | без изменений контракта; всегда CTA |
| `GET /api/protocol-summary-nav` | опционально подмешать TOC labels |
| `protocol_nav_api_path` | добавить `page=`; viewer обязан читать |

Не плодить новый `/api/protocol-nav-v2`, пока cascade не упрётся в контракт.
