## 1. Контекст и проблема

Сейчас в анализ L1/L2 попадают **все строки `mis_protocol` за месяц**, а не только
консультативные заключения (КЗ). Это искажает метрики: диагностические протоколы
(УЗИ, рентген, функциональная диагностика, эндоскопия, лаборатория) оцениваются той же
рубрикой, что клинический приём, хотя у них нет ни жалоб, ни диагноза, ни рекомендаций -
их оценивать нельзя.

Корни проблемы (по коду и схеме, без изменений):

1. **Экспортёр не фильтрует по типу.** `scripts/export_mis_protocol_month.py`:
   `SELECT id, date, visit_id, patient_id, result FROM mis_protocol WHERE date >= ... AND date < ...`
   Поле `type` (в схеме КЗ = 9) не выбирается и не проверяется.
2. **`specialty_id` (слот 2 «Специальность врача») не используется.** Парсер
   (`clinical_knowledge/mis_protocol_parse.py`) его достаёт, но id нигде не резолвится в
   название и не участвует в отборе. Это самый прямой признак «клиника vs диагностика».
3. **`doctor_specialization` лоссовый.** В `mis_data` join берётся `MIN(specialization)`
   по всем услугам визита - на визите «консультация + УЗИ» может выбраться не автор КЗ.
4. **Фильтр специальностей неполный.** `clinical_specialties.py` режет только
   стоматологию/медсестру/логопеда/лабораторию по `doctor_specialization`; диагностические
   протоколы (УЗИ и т.п.) не отсекаются.

Итог: датасет «7916 строк/июль» = КЗ + шум. Нужно детерминированно пометить каждую
строку `kz_kind` и в оценку пускать только настоящие КЗ, а остальное - показывать
отдельно (для прозрачности), но не скорить.

## 3. Целевой отбор КЗ (три уровня, детерминированно)

Каждой строке присваиваем `kz_kind` и `kz_exclude_reason`:

| kz_kind | Что это | В оценку? |
|---------|---------|-----------|
| `kz` | Клиническое консультативное заключение | да |
| `certificate` | Справка/профосмотр (`pay_type=12`) | да, но **отдельная рубрика** (усечённый чек-лист) |
| `diagnostic` | УЗИ / рентген / функц. / эндоскопия / лаборатория | **нет** (показываем отдельно) |
| `non_clinical` | Медсестра / стоматология / логопед / пустая спец. | нет |
| `empty` | Нет клинического содержания (только exam_data / витальные) | нет |

Правила (в порядке применения):

1. **SQL-фильтр `type = 9`** в экспортёре (если шаг 0 покажет не-9 строки). Плюс всегда
   тянуть колонку `type` в CSV/meta для аудита.
2. **Whitelist по `specialty_id`** (из словаря шага 0): клинические специальности → `kz`;
   диагностика/лаборатория → `diagnostic`; неклинические → `non_clinical`. Это заменяет
   лоссовый `MIN(specialization)` как первичный признак автора.
3. **Контентный guard** (fallback, если специальность неизвестна): строка = `kz` только
   если есть диагноз (`clinical_diagnosis`|`diagnosis_list`) И хотя бы один из
   {жалобы, анамнез, объективный статус} И (рекомендации по обследованию|лечению). Иначе -
   `empty`/`diagnostic`.
4. **Фикс автора специальности:** резолвить `doctor_specialization` по `doctor_id`
   протокола (слот 7) через `mis_data.specialist_id`, а не `MIN()` по визиту.

Реализация:
- `clinical_knowledge/mis_protocol_parse.py`: добавить `type` в выгрузку; helper
  `classify_kz_kind(row) -> (kind, reason)`.
- `clinical_knowledge/clinical_specialties.py`: расширить справочник диагностических/
  лабораторных специальностей (`_DIAGNOSTIC_RE`: ультразвук|УЗИ|рентген|лучев|
  функциональн|эндоскоп|лаборат|патоморфолог|цитолог и т.п.).
- `scripts/export_mis_protocol_month.py`: `SELECT ..., type ...`; join автора по
  specialist_id протокола; писать `kz_kind` в CSV + счётчики в meta.
- `scripts/run_mis_protocol_l1_batch.py`: скорить только `kz_kind in {kz, certificate}`;
  прочее агрегировать в отдельный блок `excluded_breakdown` (без скоринга).

## 6. Понятная визуализация оценок и сравнений

Цель - методисту с первого экрана видно: (1) что оценивалось, а что исключено и почему;
(2) распределение качества; (3) честные сравнения (специальности/месяцы), а не «в лоб».

Новое / переработка `mis-kz-quality.html` и вкладки «MIS · КЗ» в `index.html`:

1. **Панель «Гигиена данных» (новое, вверху).** Стек/донат: КЗ / справки / диагностика /
   неклинические / пустые - с числами и % и подсказкой «диагностику (УЗИ и т.п.) не
   оцениваем». Прозрачность отбора - главный ответ на запрос.
2. **Распределение баллов** - гистограмма 0-49/50-59/.../90-100 с медианой и целевыми
   зонами (красная/жёлтая/зелёная), а не голые бары.
3. **Сравнение специальностей - перцентиль, не сырой avg.** Горизонтальные бары
   avg overall по клиническим специальностям + маркер медианы; сортировка по отклонению
   от общей медианы (кто реально выбивается), т.к. дисперсия между спец. велика.
4. **Динамика январь → июль** - уже есть `month_compare`; сделать «диверджент-бары»
   (Δ п.п. по специальностям, ↑ зелёные / ↓ красные), чтобы сдвиг читался мгновенно.
5. **Оси качества (когда включатся, §13 методологии):** три мини-бара
   documentation / clinical_concordance / safety на карточку визита вместо одного числа.
6. **Худшие визиты** - оставить таблицу, но добавить бейдж `kz_kind` и колонку «почему в
   топе» (уже есть comment), плюс фильтр «только КЗ / включая справки».

Технически: лёгкие inline-SVG/CSS-бары (как текущий прогресс-бар), без тяжёлых
чарт-библиотек; тёмные тексты без em/en dash (правило hyphen-dash).

## 7. Риски

- **ПДн:** CSV с `type`/автором - только локально/на /var/data; в git - агрегаты и meta.
- **Нет словаря специальностей в БД:** тогда `specialty_id` мапим эвристикой по названию из

  отсутствуют) - Э0/Э2/Э4 выполняются там.

## 8. Э6 - интеграция Постановления МЗ РБ 21.05.2021 №55 (сделано)

Постановление №55 = официальная методология оценки/экспертизы качества медпомощи РБ:
оценка как набор бинарных критериев «Да/Нет». Организационные критерии (прил. 1) к КЗ не
применимы; взяты пофакторные критерии уровня случая (прил. 2, напр. разд. II п. 4.2).

Сделано (без БД, на текущих данных):

- `data/regulations/mz_2021_55.json` - 9 case-level критериев с привязкой к полям КЗ,
  severity P0/P1/P2/P3 и ссылкой на пункт.
- `clinical_knowledge/reg55_criteria.py` - детерминированный чекер `evaluate_reg55(case)`
  → `regulatory_compliance_pct`, список невыполненных, критические P0. Работает по
  `fields_present` / `block_scores` из cases.jsonl (доступно при rebuild без БД).
- Батч: `avg_regulatory_compliance_pct`, `reg55_p0_defect_n`, `reg55_top_failed` в summary;
  `reg55_pct` / `reg55_failed` / `reg55_has_p0` на каждый worst-visit.
- UI (`mis-kz-quality.html`, кабинет методиста в `index.html`): KPI «Соответствие №55»,
  панель топ-невыполненных критериев (по severity), колонка «№55» в таблице худших визитов
  с тултипом невыполненных и маркером P0.

Результат на январе (Render, 11720 КЗ): **соответствие №55 = 67.7%**, P0-дефектов = 271.
Топ невыполненных: `treatment_per_protocol` 99.3% (P1), `exams_per_protocol` 91.3% (P1),
`follow_up_present` 84.5% (P2). То есть №55 подтверждает те же системные провалы
(лечение/обследование матч + отсутствие наблюдения), но в защитимых терминах НПА.

Отложено:
- Критерий «кодирование по МКБ-10» (п. 4.2.9): код в структурном поле диагноза (поле 22),
  не в свободном тексте - вернуть после пере-экспорта.
- Июль: на Render нет `cases.jsonl` - reg55 не пересобрать; в UI «№55» = « - » до
  повторного L1-прогона июля.
- Взвешивание дефектов по вреду и калибровка порогов статусов на эталоне (Э4).
