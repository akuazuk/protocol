## 1. Зачем отдельные разделы

Сейчас методист и руководитель видят либо **весь поток** (Сегодня / Период / Все случаи),
либо **зоны** (оформление / диагноз / план / риск). Внутри одного МО десятки пунктов:
жалобы, диагноз, план, назначения, анализы, №55. При 100k+ записей невозможно
искать «где плохо с лекарствами» или «где анализы не учтены», кликая случайные замечания.

Нужны **два предметных раздела** - как отдельные «линзы» на тот же склад:

| Раздел | Вопрос пользователя | Единица навигации |
|--|--|--|
| **Лекарства** | Где назначения опасны, дублируются, вне инструкции, без дозы? | Finding-family `drug_*` → список МО → карточка назначения |
| **Анализы** | Где результат есть, но не учтён / отклонение не отражено / КП-обследование пропущено? | Finding-family `lab_*` → список МО → карточка анализа |

Это не возврат старой страницы «Безопасность» (там был только график P0-P3 по дням).
И не дубль вкладки «Инструкции ЛС» (там корпус Rceth). Это **операционные дашборды
по содержанию МО**, с тем же drill, что уже работает: цифра → фильтр → список → разбор.

## 2. Принципы (чтобы потом вошло в общую оценку)

1. **Одни и те же findings**, что уже считает scorer. Дашборд не вводит параллельную
   «оценку руками» - он группирует коды и показывает доли.
2. **Сначала навигация, потом вес в overall.** Пока shadow/gold не закрыты, разделы
   показывают «в апробации» и **не** режут зарплату/аттестацию.
3. **Семейства кодов = контракт.** Каждый finding принадлежит ровно одному семейству
   (`drug` / `lab` / `other`). Общая оценка потом берёт те же семейства как подоси.
4. **Zones-first не ломаем.** В меню появляются два пункта рядом с «Врачи», а не
   возврат четырёх «осей A/B/C/D» на Обзор.
5. **Один клик до случая.** Любая плитка/строка ведёт в `documents` / `queue` с
   `finding_codes=…` (уже есть в API).
6. **Две шкалы на будущее, одна правда сейчас.**  
   - Сейчас: % МО с finding семейства (прозрачно).  
   - Потом: `drug_score` / `lab_score` 0-100 → вклад в clinical / overall через
     явный флаг и калибровку (как `MO_*_PRIMARY`).

```text
                    ┌─────────────────┐
   fact_mo_finding  │  семейства кодов │
                    │  drug_* / lab_*  │
                    └────────┬────────┘
           ┌─────────────────┼─────────────────┐
           ▼                 ▼                 ▼
    Раздел Лекарства   Раздел Анализы    Общая оценка МО
    (навигация)        (навигация)       (позже: вес/оси)
           │                 │                 │
           └──────── drill ──┴──► Все случаи / Очередь / карточка
```

## 3. Целевая IA (информационная архитектура)

### 3.1. Пункты меню

Добавить в левое меню methodist (после «Врачи», до «Отчёты»):

| `data-page` | Подпись | Кому |
|--|--|--|
| `medications` | Лекарства | methodist / lead / admin |
| `labs` | Анализы | methodist / lead / admin |

Не показывать expert-роли (у них только Сегодня + Отчёты).  
Capabilities: `pages.medications`, `pages.labs`, `actions.drugs_labs_kpis` (уже есть).

### 3.2. Общий каркас страницы (одинаковый для обоих)

```text
[ Период ] [ Филиал ] [ Специальность ] [ Врач ]   ← те же глобальные фильтры

KPI-ряд (3-5 плиток)          ← % и число МО, не «средний балл» пока
Структура замечаний (таблица + мини-бары)  ← топ кодов семейства
Разрез: специальность | врач | день
Список случаев (с превью 1-2 findings)
```

Каждая плитка: клик → `navigateFinding` / preset с `finding_codes` + период.

Бейдж на заголовке: **«черновик, не в общей оценке»**, пока primary-флаги off.

### 3.3. Раздел «Лекарства»

**KPI (минимум):**

| Плитка | Смысл | Коды (ядро) |
|--|--|--|
| С замечанием по ЛС | доля МО с любым drug-finding | union семейства |
| Взаимодействия | DDI | `C_ddi` |
| Дубли групп | НПВС + class-dup | `C_nsaid_dup`, `C_ppi_dup`, … |
| Доза / инструкция | high-alert, Rceth, formulary | `C_high_alert_no_dose`, `C_rceth_*`, `C_formulary_unknown` |
| Не по протоколу | лечение вне групп КП | `B_tx_offprotocol` |

**Таблица «что чаще всего»:** код → title_ru → число МО → % → тренд к прошлому периоду.

**Разрезы:** специальность, врач (≥20 случаев для сравнения - уже в risk-adjust), день.

**Превью в списке:** название препаратов из evidence (без PHI пациента в агрегатах).

### 3.4. Раздел «Анализы»

**KPI:**

| Плитка | Смысл | Коды |
|--|--|--|
| Анализы не учтены | unused в Dx или плане | `B_lab_unused_in_dx`, `B_lab_unused_in_plan` |
| Есть на складе, нет в МО | present_not_in_mo | `B_lab_present_not_in_mo` |
| Отклонение не отражено | abnormal ignored | `B_lab_abnormal_ignored` |
| Пропуск по КП | exams gap | `B_exams_gap` |
| Повтор / не разобран | ordered_already_done / ordered_not_used | `B_lab_ordered_*` |

**Дополнительно:** покрытие «есть лаборатория в окне» (из `mo_lab` / reconcile) -
знаменатель честный: % unused считать среди МО **с** лабораторией, не среди всех.

### 3.5. Связь с Сегодня / Период

На «Сегодня» и «Период» - **две компактные полоски** (не отдельные hero):

- Лекарства: N% · топ-1 код  
- Анализы: N% · топ-1 код  

Клик → соответствующий раздел с тем же периодом.  
Обзор зон (оформление/диагноз/план) не трогаем.

## 4. Контракт данных: семейства кодов

Единый реестр (код уже частично в `mo_anomaly_kpis.py` - вынести в канон):

`data/mo_finding_families/families_v1.json`

```json
{
  "families": [
    {
      "id": "drug",
      "title_ru": "Лекарства",
      "codes": ["C_ddi", "C_nsaid_dup", "C_ppi_dup", "...", "B_tx_offprotocol", "C_rceth_*"],
      "feeds_overall_axis": "safety",
      "score_key": "drug_score"
    },
    {
      "id": "lab",
      "title_ru": "Анализы",
      "codes": ["B_lab_unused_in_dx", "B_lab_unused_in_plan", "...", "B_exams_gap"],
      "feeds_overall_axis": "clinical_concordance",
      "score_key": "lab_score"
    }
  ]
}
```

Правила:

- Новый finding **обязан** указать family в labels / реестре.
- Warehouse: опционально колонка `finding_family` при publish (или JOIN по реестру).
- API: расширить `build_mo_drugs_labs_kpis` → `build_mo_family_kpis(family=drug|lab|all)`
  или два тонких endpoint'а, оба на одном builder.

Фильтр списка случаев: `finding_family=drug|lab` (сервер раскладывает в `finding_codes`).

## 5. Путь в общую оценку МО (этапы, без ломки SSOT)

### Этап A - только навигация (этот план, волны UI)

- Два раздела + полоски на Сегодня/Период.
- Findings остаются shadow/primary как сейчас.
- Overall / зоны / №55 **без изменений**.

### Этап B - подоси в карточке случая (после gold)

В разборе случая показать блоки:

```text
Лекарства: 72   (shadow)     Анализы: 58   (shadow)
```

Формула подоси (черновик, калибруется):

```text
drug_score = 100 - sum(penalties по drug-findings primary)
lab_score  = 100 - sum(penalties по lab-findings primary)
```

Потолки как у risk-gate: P0 в семействе → ≤40, P1 → ≤60 **внутри подоси**,
не обязательно сразу в overall.

### Этап C - вклад в clinical / overall (явное решение владельца)

Вариант по умолчанию (совместим со статьёй РЗ):

```text
clinical_pct = weighted(concordance, safety, documentation, lab_score?, drug_score?)
admission   = min(clinical_pct, document_ready_pct)
```

Практичнее для пилота:

| Включение | Условие |
|--|--|
| `lab_score` → concordance | `MO_LAB_UNUSED_PRIMARY=1` + FP≤15% |
| `drug_score` (Rceth/class) → safety | соответствующие `*_PRIMARY=1` |
| Показ на Обзоре как зона «Лекарства/Анализы» | только после этапа B на живом потоке ≥30 дней |

**Запрет:** не смешивать drug/lab в №55 section-pack. №55 остаётся отдельным контуром.

## 8. Что не делать

- Не возвращать старую страницу «Безопасность» как замену.
- Не путать «Инструкции ЛС» (корпус) с «Лекарства» (оценка назначений в МО).
- Не считать % unused от всех МО без лаборатории - искажает картину.
- Не включать семейства в overall без gold и явного флага.
- Не плодить третий склад findings - только `fact_mo_finding` + реестр семейств.

| Меню раздувается | Только 2 пункта; без specialties/diagnoses |
