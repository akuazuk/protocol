## 0. Главная задача владельца (северная звезда)

Две проверки в МО Аналитика - важнее истории пациента и клиники:

| # | Проверка | Провал = |
|--|--|--|
| **1. Диагноз есть в МО** | В документе есть установленный диагноз (текст и/или код) | Пустые слоты диагноза и нет кода/формулировки ни в графе, ни (для кода) в полном тексте |
| **2. Диагноз существует в справочнике МКБ** | Формулировка или код есть в RU-справочнике | Выдуманное название, опечатка до неузнаваемости, код не из справочника |

История визитов пациента - **потом**, чтобы точнее объяснять динамику; она не заменяет эти две проверки.

**Где искать в МО:**

- текст названия: слоты диагноза; если пусто - блок/строка у найденного кода в полном документе;
- код: уже full-document (`resolve_icd_codes_from_mo`) - код в жалобах/статусе/плане тоже считается для «код указан».

**Что уже в коде (shadow, PR #49 + earlier):**

- `B_icd_dir_*` / `B_icd_name_*` - сверка со справочником;
- `B_icd_invalid` / reg55 - формат/наличие кода;
- явного сильного finding «диагноз отсутствует в МО» как отдельной оси ещё мало (часто `skip` если пусто) - **дожать**.

**Порядок реализации под эту цель (не под историю):**

1. Справочник актуален + name_only/directory на текущем визите (в PR).
2. Finding «диагноза нет в МО» (P1/P2) + не `skip` при пустоте.
3. Fallback: текст Dx из full-doc около кода, если графа пуста.
4. Выключить shadow → primary после калибровки.
5. История пациента - отдельным треком после стабилизации 1-2.

### 0.1 По каждому визиту и по истории - как быть

| Уровень | Что считаем | Когда |
|--|--|--|
| **Визит (обязательно)** | «Диагноз есть?» + «Есть в справочнике МКБ?» | При score **этого** визита; findings сохраняются у `mis_id` |
| **История пациента (обзор)** | Не новый прогон справочника по всем текстам | Лента прошлых визитов + **статусы уже сохранённых** оценок МКБ |
| **Текущий визит + история** | Одно доп. МО: тот же код/нозология уже встречалась у врача/специальности | Читает бандл; не заменяет проверки 1-2 |

Правило: сверка со справочником - **всегда per-visit**.  
«По всей истории» в аналитике = **сводка** per-visit результатов на ленте, а не одна оценка «на пациента».

```text
Визит A  →  МКБ: ok / нет диагноза / нет в справочнике   (сохранено)
Визит B  →  МКБ: ok / …
Визит C (сейчас) → считаем заново проверки 1-2
                 → в UI: findings C + лента A,B со своими статусами
```

### 0.2 Визуализация в МО Аналитика

**1) Таблица дня (список визитов)**  
Колонка или чип у строки:

- `МКБ ✓` - диагноз есть и в справочнике;
- `нет Dx` - диагноза в МО нет;
- `не в МКБ` - формулировка/код не из справочника;
- опционально серый `история: N` - число прошлых визитов пациента (не результат сверки).

**2) Разбор случая (главный экран)**  
Два блока рядом, не смешивать тексты:

| Блок | Содержание |
|--|--|
| **Оценка этого визита** | Findings: нет диагноза / не в справочнике / слабое название; evidence из **этого** МО |
| **История пациента** | Лента визитов: дата · код/короткий Dx · чип МКБ-статуса того дня · балл МО · открыть |

Пример ленты:

```text
История пациента (до этого случая) · 4 визита
2026-05-01  N30.0  Острый цистит     МКБ ✓    82%  [открыть]
2026-06-12  —      (пусто)           нет Dx   41%  [открыть]
2026-07-03  ZZ99   выдумка           не в МКБ 38%  [открыть]
```

**3) Не делать**

- одну «оценку МКБ на всего пациента» вместо оценки визита;
- пересчитывать все прошлые визиты при каждом новом дне (только явный re-score);
- прятать проверку справочника внутри истории без отдельного finding на текущем визите.

**4) Что видит методист за 5 секунд**

1. У сегодняшнего случая - красный/жёлтый finding по МКБ (если есть).  
2. В ленте - были ли такие же проблемы раньше у этого пациента с этим врачом/специальностью.  
3. Клик в прошлый визит - его собственная оценка, не «перенесённая» с сегодня.

## 1. Продуктовое правило

| Ось | Вход | Что сравниваем | Коды МКБ |
|--|--|--|--|
| **v1 directory** | Dx ± код | код есть в справочнике; overlap текста с `ru_title(code)` | да |
| **v2 name_only (это)** | свободный текст Dx | формулировка ↔ лучшее `title_ru` в справочнике | **нет** - коды из текста вырезаются перед match |
| **История пациента (отдельный план, сначала)** | визиты пациента | полки: этот врач / другие этой специальности → бандл + **одно** МО | потом анализаторы читают бандл |
| **Клиническая согласованность (дальше)** | Dx + слоты КЗ | формулировка Dx ↔ жалобы, анамнез, статус, обследования, план | нет |

Подбор КП по-прежнему **только по тексту диагноза** (v1 product rule). Name_only - дополнительная оценка качества формулировки относительно справочника (опечатки, «не та нозология», пустой/мусорный Dx).

## 2. Зачем общий слой текста сейчас

Сейчас строим **одну** нормализацию и similarity для Dx ↔ `title_ru`. Тот же контракт потом кормит сравнение Dx с клиническими слотами без переписывания матчера:

```text
patient_history_bundle       ← фундамент (сначала; отдельный план v2)
  same_doctor[] / same_specialty[] / summary
       │
       ├─ одно МО по истории пациента
       └─ feature для всех анализаторов ниже

clinical_text_similarity
  normalize_for_match / strip_icd_codes / token_jaccard / fuzz_ratio / combined_score
       │
       ├─ mo_icd_name_match (фаза B): Dx → каталог title_ru
       └─ mo_clinical_section_align (фаза D, позже): Dx → complaints|anamnesis|exams|recs|treatment
```

Правила переиспользования:

1. Сначала бандл истории пациента; анализаторы не ходят в CSV сами.
2. Не смешивать «история пациента», «есть в справочнике МКБ» и «клиника поддерживает диагноз» в один finding.
3. Пороги калибровать отдельно; бандл меняет **веса**, не клонирует замечания.
4. Не гонять LLM на bulk match - только lex + token + SequenceMatcher (stdlib).
5. В evidence не тащить PHI сверх короткого snippet (как в других shadow findings).

### B. Name-only match (shadow) - сделано (код в PR; калибровка - C)

Helper: `clinical_knowledge/mo_icd_name_match.py` + shared `clinical_text_similarity.py`.

Алгоритм:

1. Собрать текст Dx из слотов (как directory eval).
2. `strip_icd_codes` + `normalize_for_match`.
3. Кандидаты: `suggest_icd_from_russian` (top N) + при слабом hit - token-prune по каталогу.
4. Для каждого кандидата: score по **очищенному** `title_ru` (без ведущего кода).
5. Verdict: `ok` / `review` / `fail` по `combined_score` (token Jaccard + difflib ratio).

Findings (shadow default):

| code | Когда |
|--|--|
| `B_icd_name_no_match` | нет кандидата выше review |
| `B_icd_name_weak_match` | лучший hit в зоне review (опечатка / неточная формулировка) |

Флаги: `MO_ICD_NAME_MATCH=1` (default on), `MO_ICD_NAME_IN_PRIMARY=0` (default off).

Пороги (стартовые, калибровка на gold):

| | combined |
|--|--|
| ok | ≥ 0.42 |
| review | ≥ 0.28 |
| fail | &lt; 0.28 |

Метрики B:

| | Было | Цель |
|--|--|--|
| Ось name_only в case detail | нет | shadow findings |
| Ложных fail на «Острый цистит» | n/a | 0 на эталоне |
| Ложных ok на мусоре | n/a | 0 на эталоне |
