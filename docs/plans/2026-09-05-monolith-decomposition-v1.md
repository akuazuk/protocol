# Разбор монолита: rag_server.py, скоринг, фронтенд

Статус: active. Создан 2026-09-05 в рамках программы production readiness
(фазы 6.1, 6.2, 7). Предшественник: `docs/reports/2026-09-05-prod-state-snapshot.md`.

## Зачем отдельный план, а не правка в один заход

`rag_server.py` - 15 003 строки и 149 маршрутов, `index.html` - около 32 тысяч
строк вместе с инлайновыми CSS и JS. Это переписывается не за один заход, и
дело не в объёме работы, а в способе проверки.

Система считает оценки качества медицинской помощи. Если при переносе
маршрутов или скоринга поведение изменится, это проявится не падением тестов,
а другими числами в оценках - причём на данных, которых в тестах нет.
Единственный честный способ такого переноса: маленькие шаги, каждый из
которых можно сверить «до/после» на реальных данных и откатить по отдельности.

Поэтому здесь зафиксированы очередь шагов и обязательная проверка на каждом.
Сделанное в один заход и уже в проде - в разделе «Что уже сделано».

## Шаг 1. Маршруты: вынос по домену без изменения поведения

Распределение 149 маршрутов: `/api/methodist` - 85, `/api/patient` - 13,
`/api/consult-review` - 5, `/api/search` - 4, `/api/expert` - 3,
`/api/clinical-knowledge` - 3, остальные по одному.

Порядок выноса - от наименее связанного к самому связанному, чтобы каждый шаг
был маленьким:

1. `/health*`, `/api/version` - без зависимостей;
2. `/api/patient/*` - отдельный контур пациента;
3. `/api/protocol-*` - чтение корпуса;
4. `/api/consult-review/*`;
5. `/api/methodist/*` - последним и по частям (85 маршрутов: МО, калибровка,
   экспорт, учётки - каждая группа отдельным шагом).

Требование к каждому шагу:

- `APIRouter` в `backend/routers/<домен>.py`, `rag_server.py` только
  подключает роутер;
- **список маршрутов и их сигнатуры не меняются**. Проверка - снимок
  `app.routes` до и после (путь, методы, имя функции, модель ответа) должен
  совпасть побайтово. Это автотест, а не ручная сверка;
- общее состояние (`_chunks`, `_model`, семафоры) не переезжает вместе с
  маршрутами: сначала оно выносится в отдельный модуль, потом маршруты.
  Иначе получится циклический импорт и два экземпляра состояния.

Не делать: переименование маршрутов, смену кодов ответов, «попутный» рефакторинг
логики. Любое такое изменение - отдельный коммит после переноса.

## Шаг 2. Конфигурация: чтение окружения не на импорте

Сейчас 20 инструкций верхнего уровня читают окружение на импорте (CSP, CORS,
rate-limit, таймауты Gemini, семафоры). Практическое следствие уже видно в
тестах: `tests/test_security_headers.py` вынужден поднимать отдельный процесс
на каждый сценарий, потому что поменять CORS или CSP после импорта нельзя.

Целевое состояние: `backend/settings.py` с одним объектом настроек, который
читается один раз и передаётся явно. Порядок:

1. вынести security-настройки (CSP, CORS, rate-limit) - они уже покрыты
   тестами, поэтому перенос проверяем;
2. таймауты Gemini;
3. семафоры и лимиты параллелизма.

Проверка: `tests/test_security_headers.py` перестаёт запускать подпроцессы и
работает через переопределение настроек. Пока тест не переписан - шаг не
закрыт.

## Шаг 3. Функции больше 250 строк

Разбирать только те, которые придётся менять по другим задачам. Разбор ради
разбора на клиническом коде даёт риск без выгоды: длинная, но работающая и
покрытая тестами функция безопаснее свежеразрезанной.

Порядок для каждой: сначала тест на текущее поведение, потом разрез.

## Шаг 4. Скоринг: четыре системы к одной рубрике (фаза 6.2)

Здесь риск выше, чем у маршрутов: меняются числа, которые видит методист и на
которые ссылается статья РЗ.

Обязательная последовательность:

1. **Сначала описание, потом код.** Для каждой из четырёх систем -
   что считает, на каких данных, где пороги. Без этого «свести к одной» значит
   молча выбрать одну и потерять остальные.
2. Пороги из кода в конфиг **без изменения значений**. Проверка: полный
   пересчёт периода даёт те же оценки до и до последнего знака.
3. Только после этого - сведение рубрик, и каждое изменение оценки должно быть
   объяснимо методисту, а не быть побочным эффектом рефакторинга.
4. `except: pass` (109 мест) разбирать вместе с той логикой, которую они
   прячут. Массовая замена на `raise` уронит ночные прогоны; массовое
   логирование забьёт логи. Каждый случай - решение по существу.

Не начинать шаг 4, пока не закрыт шаг 1: скоринг придётся трогать в тех же
файлах, что и маршруты.

## Шаг 5. Фронтенд (фаза 7)

`index.html` - около 32 тысяч строк, включая инлайновые CSS и JS. Отсюда же
следует, что CSP не может обойтись без `'unsafe-inline'`.

Порядок:

1. вынести JS в файлы **как есть**, без сборщика и без правок кода - только
   перемещение и `<script src>`;
2. после этого снять `'unsafe-inline'`/`'unsafe-eval'` из CSP: до выноса это
   невозможно, и именно поэтому они сейчас в политике;
3. `innerHTML` с данными - на `textContent`. Разбирать по одному: часть
   вставок намеренно содержит разметку;
4. только затем сборщик (Vite), фиксация версий CDN, дизайн-система, a11y.

Пункт 2 - главный выигрыш шага, поэтому пункт 1 не стоит смешивать с
переписыванием кода.

## Риски

- **Перенос меняет оценки.** Снимок `app.routes` и пересчёт периода с
  побайтовой сверкой - обязательны, иначе изменение заметит методист, а не CI.
- **Циклические импорты** при выносе маршрутов раньше состояния. Отсюда
  требование выносить состояние первым.
- **Конфликты с открытыми PR.** На 2026-09-05 открыто 9 PR, часть трогает
  `rag_server.py`. Начинать шаг 1 после их разбора
  (`docs/reports/2026-09-05-git-hygiene-and-pr-triage.md`), иначе перенос
  маршрутов сделает их неразрешимыми.
