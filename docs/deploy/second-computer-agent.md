## 2. Первый запуск на новом компьютере

Нужны: `git`, `gh` (авторизация в `akuazuk/protocol`), `python3`, при работе с VM - `gcloud` в проект `protocol-home-e1`. Секреты, `.env`, пароль МИС и ключ Gemini в репозиторий не копировать. На VM они уже лежат в Secret Manager и `/opt/protocol/.env.mis`.

```bash
git clone https://github.com/akuazuk/protocol.git
cd protocol
git status --short --branch
git fetch --prune origin
git rev-list --left-right --count origin/main...HEAD
python3 scripts/ops/pr_dashboard.py
```

Ожидание после чистого clone: ветка `main`, расхождение `0 0`, рабочее дерево пустое. Если дерево не пустое или `main` не совпадает с `origin/main` - остановиться и завести worktree, этот каталог не чинить.

Прочитать по порядку:

1. `AGENTS.md`
2. этот файл
3. `docs/plans/README.md` - только чтобы выбрать одну строку со статусом `active`
4. последний handoff именно по выбранной задаче в `docs/reports/`
5. `docs/deploy/multi-agent-workflow-v3.md`, если задача дольше одного PR

Дальше не работать в `main`.

```bash
scripts/ops/git_task_start.sh <короткий-slug> --pc=pc2 \
  --branch=cursor/<короткий-slug>-agent2-pc2
cd /private/tmp/protocol-task-<короткий-slug>-pc2
test -z "$(git status --porcelain)"
git merge-base --is-ancestor origin/main HEAD
python3 scripts/ops/pr_dashboard.py --files <пути-которые-будешь-менять>
```

Выход 1 у `--files` значит «файл занят». Взять другую задачу или дождаться merge. Не править занятый файл «параллельно понемногу».

Имя ветки проверяется блокирующе:

```text
cursor|codex|hotfix|release/<задача>[-agent<N>]-pc<N>
```

Запрещены `main`, `master`, `codex/main-sync`, `cursor/main-sync`.

## 3. Как делить работу с другим агентом

Один агент - одна задача - одна ветка - один worktree - один PR.

Общая память - только GitHub: commit, `git push origin` своей ветки, описание PR. Незакоммиченное между компьютерами не пересылать и не класть в чат клинический текст.

Перед первой правкой и после чужого merge:

```bash
scripts/ops/check_pr_file_overlap.sh
scripts/ops/rebase_task_onto_main.sh
```

Конфликт только в строке `BUILD_VERSION` в `rag_server.py` rebase-скрипт снимает сам. Любой другой общий файл - стоп, не выбрасывать чужие блоки.

Черновик PR открывать сразу после первого безопасного коммита: так дашборд показывает, какие файлы заняты.

Описание PR - по `.github/pull_request_template.md`. Пустые угловые скобки шаблона блокируют PR. Поля «Владелец», «Зона изменений», «Зависит от PR» нужны соседнему агенту, чтобы решить, ждать merge или можно править.

В коммитах и PR не писать `Co-authored-by` от IDE, `Made with`, `Generated by`.

## 4. Куда можно вставать параллельно

Карта: `.github/CODEOWNERS`. Смысл уровней - в `docs/deploy/multi-agent-workflow-v3.md`, раздел 3.

| Уровень | Куда | Правило для второго агента |
|---|---|---|
| 1 | `docs/`, `ml/`, `eval/` | можно отдельной задачей, если файл не в чужом PR |
| 2 | `clinical_knowledge/`, `services/`, `corpus_pipeline/` | один модуль на PR и тест на инвариант |
| 3 | `frontend/web/` | один модуль на PR |
| 4 | `.github/`, `tests/`, `ruff.toml`, `scripts/ops/` | отдельный PR, не вместе с фичей |
| 5 | `deploy/`, `rag_server.py`, `requirements*`, `AGENTS.md` | только если это и есть задача; деплой - не твоя роль по умолчанию |
| 6 | `corpus_chunks_parts/`, `data/`, `minzdrav_protocols/`, `config/` | не руками, только скрипты публикации |

Самый конфликтный файл - `docs/plans/README.md`. Если твоя задача обязана в него попасть: одна новая строка в конец своей секции, таблицу не переформатировать.

Порог размера PR: предупреждение от 40 файлов или 1500 строк. Крупный PR в описании объясняет, почему он один.

## 5. Коммит, версия, конец сессии

Если изменение поедет в прод (код, UI, runtime, осмысленные docs):

```bash
scripts/ops/bump_build_version.sh <slug-из-2-4-слов>
git diff --check
# тесты по затронутым файлам
git add <точные-пути>
git commit -m "type(scope): суть"
git push -u origin HEAD
```

Версия - UTC до секунды, формат `YYYY-MM-DD-HHMMSSZ` или с хвостом `-slug`. Старый `rN` не использовать.

Прямой push в `main` запрещён. `main` меняется только squash/merge PR на GitHub.

В конце сессии - `docs/reports/YYYY-MM-DD-handoff-<тема>.md`:

- repo, branch, worktree, base SHA, HEAD SHA, номер PR;
- сделано и не сделано;
- тесты;
- был ли merge и был ли deploy (для docs без runtime deploy обычно не нужен);
- `BUILD_VERSION`;
- одна следующая безопасная команда;
- файлы, которые нельзя трогать параллельно.

Не писать «готово», если PR не влит или, когда задача меняет прод, `https://protocol.kravira.by/api/version` не совпал с merge SHA.

## 6. Прод, МИС, Gemini

Деплой делает один назначенный человек, одним окном, только когда `HEAD` равен свежему `origin/main`:

```bash
bash deploy/gcp-app/deploy_to_gce.sh
curl -fsS https://protocol.kravira.by/health/live
curl -fsS https://protocol.kravira.by/api/version
```

Второму агенту это не запускать, пока владелец явно не назвал его релиз-координатором на конкретный SHA. Во время релиза не мержить второй runtime-PR, не рестартовать `protocol-web`, не менять `/var/data`, firewall и env контейнера.

Порт `8000` наружу не открывать.

MariaDB МИС и любой ad-hoc SQL - только с VM, не с Mac:

```bash
bash deploy/gcp-app/mis_sql_smoke_on_gce.sh
```

Ночной LLM, action-judge, ICD review, `grade_kz_llm` - только:

```bash
bash deploy/gcp-llm/run_on_gce.sh YYYY-MM-DD [YYYY-MM-DD]
```

С Mac Gemini режет по геолокации и пишет в grades строки `{visit_id, _error}`, файл выглядит полным, оценки битые.

Клинические тексты, токены, ФИО и идентификаторы пациентов не печатать в логах, PR, handoff и ответах. Для списка достаточно даты и короткого фрагмента без персональных данных.

Не деплоить и не рестартовать `protocol-web`, пока на VM идёт Rceth `running` или ночной прогон. Проверка без вреда:

```bash
gcloud compute ssh protocol-app --zone=europe-central2-a --command='
python3 -c "import json; d=json.load(open(\"/var/data/rceth/_sync/status.json\")); print(d.get(\"status\"), d.get(\"phase\"), d.get(\"updated_at\"))"
'
```

## 7. Docker на GCP - не замена второго компьютера

Образы Docker в репозитории - это прод и фоновые job, не среда для агента.

| Образ | Файл | Роль |
|---|---|---|
| Web + пайплайн МО | `deploy/gcp-app/Dockerfile` | контейнер `protocol-web`. База `python:3.11-slim`, зависимости из `requirements-rag.lock` под 3.11 |
| Ночной LLM | `deploy/gcp-llm/Dockerfile` | Gemini на VM, где геолокация проходит |
| Старый мост МИС с Mac | `deploy/mac-bridge/Dockerfile` | не использовать: SQL только с GCE |
| Контур BY-home | `deploy/by-home/Dockerfile` | не рабочее место агента |

Почему не сажать второго агента внутрь `protocol-web` или в новый контейнер на той же VM:

- на VM один диск с живыми оценками и ночным cron;
- деплой заменяет контейнер из `git archive` релизного SHA, а не из чьего-то рабочего дерева;
- shell в прод-контейнере может рестартовать приложение и испортить `/var/data`;
- lock зависимостей собран под Python 3.11. Мажорные PR Dependabot на `python:3.14-slim` закрыты 2026-09-30 (#194-#197). В `.github/dependabot.yml` для Docker-образа `python` игнорируется `semver-major`, чтобы они не открылись снова.

Как второму компьютеру пользоваться GCP, не становясь прод-контейнером:

1. Код и PR - в своём worktree на этом компьютере.
2. SQL, Gemini и проверка job - готовые скрипты `*_on_gce.sh` и `gcloud compute ssh` на `protocol-app`.
3. Смотреть UI - браузер на `https://protocol.kravira.by`, не локальный форк прода.

Отдельная непродакшен VM или Cloud Workstation имела бы свой диск и не монтировала бы `/var/data/medical_exams`. Такого контура нет. Заводить его - отдельное решение владельца, не шаг онбординга. Пока его нет, чистый clone плюс worktree на втором компьютере безопаснее, чем агент внутри Docker на прод-VM.
