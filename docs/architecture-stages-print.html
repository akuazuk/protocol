Protocol: архитектура по этапам

Навигатор клинических протоколов Минздрава РБ и ориентировочная проверка консультативных заключений (КЗ).

Документ описывает текущую реализацию (MVP), целевую интеграцию с МИС и Минздравом через стандарт FHIR BY / ЦИСЗ, а также предложения по масштабированию на тысячи КЗ в сутки.

Версия документа: 2026-06-24 · Сборка приложения: 2026-06-24-r5-arch-docs-update · Не является ТЗ и не заменяет нормативные акты Минздрава.

1. Назначение и границы системы

MVP Protocol - веб-сервис и API для двух сценариев:

  1. Поиск протоколов - подбор официальных КП Минздрава РБ по диагнозу, МКБ-10, жалобам и рубрикам каталога.
  2. Проверка КЗ - ориентировочная сверка консультативного заключения с фрагментами протоколов и формализованными правилами; отчёт для врача и методслужбы.

Не входит: установление диагноза, замена очного приёма, МЭЭ, юридически обязательная экспертиза, прямая запись в медицинскую карту (на этапе пилота).

Два контура intelligence: (1) LLM - языковая модель для синтеза, уточнения запроса и дополнения ответа; (2) детерминированный слой clinical_knowledge/ - парсинг, правила из протоколов, scoring без «магии» модели.

2. Этап 0. Корпус протоколов и справочники

2.1. Источник данных

Официальный каталог PDF на minzdrav.gov.by (раздел «Стандарты обследования и лечения»). Синхронизация скриптом download_minzdrav_protocols.py в каталог minzdrav_protocols/ (~478 PDF, 24 рубрики).

2.2. Индекс каталога

index.csv - метаданные: рубрика, год в имени файла, признак постановления МЗ. Используется для UI-бейджей, статистики презентации и фильтрации.

2.3. Справочники

  • protocols.json, protocol_meta.json - реестр путей и метаданные.
  • data/catalog/ - 85 нозологий, 482 автоизвлечённых правила, отчёт покрытия 100% PDF.
  • data/protocol_summaries/ - YAML/JSON карточки протоколов (~465 summaries) для навигации и расширения правил.
  • config/ - требования к КЗ, веса scoring, red flags.

3. Этап 1. Подготовка корпуса для RAG

3.1. Два пути сборки (legacy и новый)

ПутьСкриптыРезультат
Legacyextract_corpus.py → build_chunks.py → split_chunks_jsonl.pycorpus_chunks_parts/*.jsonl
Новыйcorpus_pipeline/run_pipelineСекции, таблицы, entities → output/chunks/

3.2. Чанки RAG

~55 000 фрагментов текста с разметкой разделов (диагноз, лечение, обследование). Хранятся в corpus_chunks_parts/ (JSONL) или на Persistent Disk (RAG_CHUNKS_DIR). На production (Render): lazy chunk store - manifest corpus_path_manifest.jsonl, чанки подгружаются с диска по пути PDF, без полной загрузки в RAM при старте (RAG_STARTUP_MODE=manifest, RAG_LAZY_CHUNK_STORE=1).

3.3. Индексы поиска

При загрузке или по требованию: path-scoped lex shards (RAG_PATH_LEX_SHARDS), BM25 (retrieval_bm25.py), опционально vector prefilter (vector_index.py), маршрутизация по симптомам (symptom_routing.json). Полный лексический индекс может откладываться (RAG_LEX_INDEX_DEFER=1) - L2-lite и поиск работают на суженном подмножестве путей.

5. Этап 3. Runtime: rag_server.py (FastAPI)

5.1. Стек

Python 3.11+, FastAPI, uvicorn. Учётные данные для вызова языковой модели задаются только в конфигурации сервера (переменные окружения или защищённое хранилище секретов) и не передаются в браузер.

5.2. Загрузка при старте

Фоновый поток load_data(): manifest/lazy chunks, protocols, meta, summary chunks, path lex shards. GET /health/live - liveness без ожидания полного RAG; GET /health - готовность индексов и флаги consult L2. На Render: Persistent Disk 10 GB (/var/data), plan Standard 2 GiB RAM.

5.3. Гибридный retrieve

Функция retrieve(): лексика + BM25 + routing boost + фильтр аудитории + опциональный embed-rerank через LLM. Результат - топ фрагментов по протоколам.

6. Этап 4. Проверка КЗ (pipeline)

Модуль consult_review_pipeline.py - оркестрация с SSE-прогрессом для UI. Маршрутизация уровней: consult_tiering.py.

6.1. Уровни L0 / L1 / L2

УровеньAPIСодержаниеProduction (Render)
L0/api/consult-compliance-screen, tier=L0Парсинг + 8 блоков + send_gate + cisz_readiness< 2 с, без RAG/LLM
L1/api/consult-review/tier L1Structured + alignment cards + СОП Кравира + rich chunks по matched PDFРекомендуемый в UI (~5-15 с)
L2/api/consult-review, streamL2-lite: L1 + evidence pack + L2-fast; опц. L2+ narrative~15-30 с, без retrieve по всему корпусу
L2 fulllocal, CONSULT_RENDER_L2_LITE=0RAG retrieve + LLM synthesize + hybrid score30-90 с (не default на Render)

6.2. Конвейер L1 (основной для врача)

PDF / FHIR Bundle / текст → извлечение и парсинг → ConsultationDocument → МКБ-10 + match_protocol_cards (allowlist) → analyze_consultation_text → 8 блоков + evidence_map → consult_alignment: карточки «КЗ ↔ КП ↔ СОП №2 Кравира» → consult_criteria_enrichment: выдержки и покрытие по блокам → compliance_gate: gate_score = min(гибрид, структурный, cisz) → cisz_readiness + send_gate + HTML/MD отчёт

6.3. Конвейер L2-lite (облако)

L1 structured + alignment (skip_alignment=false) → preload чанков только по matched paths (consult_memory) → consult_evidence_pack: выдержки КП с фильтром качества → build_l2_fast_review (CONSULT_L2_FAST=1) ИЛИ LLM synthesize → опц. consult_criteria_narrative (CONSULT_CRITERIA_NARRATIVE) → кэш CONSULT_REVIEW_CACHE, cisz_readiness

Флаги Render: CONSULT_RENDER_L2_LITE=1, CONSULT_REVIEW_FORBID_FULL_CORPUS=1, CONSULT_ALIGNMENT_ENABLED=1. При нехватке RAM (CONSULT_RENDER_L2_SKIP_LLM=1) L2 деградирует в L1 с пометкой в ответе.

7. Этап 5. Frontend

Два клиентских shell в production: B2B index.html (~29k строк) и B2C patient.html (~1,1k строк + patient-ui.js). Inline CSS + vanilla JS, без bundler.

7.1. index.html (B2B)

  • Липкая шапка: минилого protocol-logo-mini.svg + вкладки при прокрутке (как в B2C).
  • Вкладки: «Проверка КЗ» (#consult-review), «Поиск протоколов» (#search), «Статистика»; hash сохраняется при F5.
  • Методслужба: ?mode=methodist + токен - workbench, очередь (#methodist-queue), ML-дашборд (#ml-dashboard), B2C-тарифы (#b2c-monetization).
  • Structured analysis: 8 блоков compliance, alignment, evidence pack; SSE для потоковой проверки КЗ.
  • Footer: единая сетка материалов (презентация, буклет, архитектура, patient B2C, кабинет методиста).

7.2. patient.html (B2C «Проверь КЗ»)

  • Отдельная PWA: загрузка PDF/фото КЗ, отчёт простым языком, tier-цены, white-label клиники.
  • API: POST /api/patient/review, sanitize без полей B2B; см. docs/architecture-b2c-patient.md.

Подробная архитектура проверки КЗ перед отправкой в Минздрав: architecture-kravira-fhir-mis-print.html. Также: docs/mvp-presentation.html, docs/pre-sign-checklist-print.html, docs/project-docs-maintenance.md.

8. Сводная схема текущей архитектуры

┌─────────────┐ ┌──────────────────┐ ┌─────────────────────┐ │ Браузер │────▶│ rag_server.py │────▶│ LLM API (сервер) │ │ index.html │◀────│ FastAPI + RAG │ └─────────────────────┘ └─────────────┘ └────────┬─────────┘ │ ┌────────────────┼────────────────┐ ▼ ▼ ▼ corpus_chunks_parts clinical_knowledge minzdrav_protocols/ data/catalog consult_review_pipeline protocol_summaries

8.1. Поток «Поиск протоколов»

Запрос → МКБ (icd_mkb.py + LLM на S2) → retrieve (lazy, allowlist на Render) → список протоколов с confidence → protocol-detail / practical / summary-nav. Уровни S0 (только МКБ), S1 (retrieve без полного assist, default), S2 (полный ответ модели).

8.2. Поток «Проверка КЗ»

Файл или Bundle → L0/L1/L2 → детерминированный compliance + alignment + (на L2-lite) evidence pack → gate_score и send_gate → отчёт с цитатами из официальных PDF. Итог для МИС: gate_score = min(клиника, cisz_score).

10. Масштабирование: тысячи КЗ в сутки

При полной проверке каждого КЗ с LLM + RAG нагрузка растёт линейно. Ниже - меры ускорения и снижения стоимости.

10.1. Технические оптимизации

МераЭффект
Детерминированный fast pathСначала rule_checker + requirement_checker без LLM; LLM только при пограничных баллах или по запросу
Кэш consult-reviewCONSULT_REVIEW_CACHE - повторные проверки того же текста/хеша
Очередь + воркерыCelery/RQ: асинхронная обработка пакетов; API возвращает job_id, МИС опрашивает статус (аналог poll ЦИСЗ)
Отключение embed-rerankНа batch-режиме: только lex + BM25 (уже есть флаг в CI)
Предварительный digestСокращение текста КЗ до ключевых секций перед LLM (уже частично в pipeline)
Горизонтальное масштабированиеНесколько инстансов API за балансировщиком; корпус read-only на shared disk
Инкрементальный corpusНе перезагружать весь RAG при деплое - hot-reload index.csv

10.2. Ориентиры производительности (пилот)

  • Детерминированный разбор одного КЗ (без LLM): секунды.
  • Полная проверка с LLM: десятки секунд - минуты (зависит от длины и fast mode).
  • Целевой batch: 100% КЗ - только детерминированный скоринг; 5-15% - углублённо с LLM.

12. Методика выборочного контроля качества КЗ

Цель: выявить врачей/подразделения с систематически слабыми КЗ без проверки каждого документа LLM.

12.1. Уровни выборки

УровеньОхватМетод
L0 - скрининг100% КЗPOST /api/consult-review/tier tier=L0 или /api/consult-compliance-screen. < 1 с, без LLM/RAG.
L1 - выборка10-20% КЗtier=L1: structured + alignment + СОП + rich chunks; без полного corpus RAG.
L2 - углублённо2-5% КЗtier=L2: на Render - L2-lite (evidence pack + L2-fast); локально - full RAG + LLM.
L3 - ручной аудит0.5-1%Эксперт методслужбы по списку «красных» врачей из L0-L2.

12.2. Критерии отбора «проблемных» врачей

  • Средний балл L0 за месяц < 70% при n ≥ 10 КЗ.
  • Доля КЗ с критическими issues (red flags) > 15%.
  • Тренд: снижение балла 3 месяца подряд.
  • Выбросы: единичные КЗ < 50% при обычно нормальном профиле - в L2, не автоматическая санкция.

12.3. Агрегаты для Минздрава (без ПДн)

Учреждение, рубрика, период, средний % по блокам, доля «зелёных/жёлтых/красных» зон. Без ФИО пациентов; идентификатор врача - только внутри контура учреждения.

12.4. Хранение результатов

Таблица kz_quality_scores: hash текста, author_id (из токена МИС), timestamp, L0_score, flags, optional L2_job_id. Retention по политике ИБ.

13. Вариант: блокировка ЭЦП до нормы соответствия

Опция для МИС Не юридическое требование Protocol, а настраиваемая политика учреждения, согласуемая с Минздравом и юристами.

13.1. Режимы (config в МИС)

РежимПоведение
informТолько предупреждения; ЭЦП всегда доступна (текущий пилот).
soft_gateПри балле < порога (напр. 70%) - диалог «Подписать всё равно?» + запись override в журнал.
hard_gateКнопка ЭЦП неактивна, пока L0 ≥ порога или методист не снял блок (workflow).
critical_onlyБлок только при critical red flags (безопасность, противопоказания).

13.2. Техническая реализация в МИС

  1. МИС вызывает POST /api/consult-review?mode=fast или лёгкий POST /api/consult-compliance-screen (только L0).
  2. Ответ: overall_compliance_pct, blocks, critical_issues[], gate_allowed: bool.
  3. МИС применяет локальную политику → разрешает/блокирует вызов ЕСИФЮЛ.
  4. При override - запись в audit log (врач, время, причина).

13.3. Риски и смягчение

  • Ложные срабатывания - порог только по L0; спорные случаи - soft_gate.
  • Юридическая нагрузка - формулировка «ориентир методслужбы», не МЭЭ.
  • Сопротивление врачей - пилот в одном отделении, обучение, прозрачные критерии из протоколов с цитатами.

14. Тестирование и качество

  • CI: Ruff + pytest (~70+ модулей), миникорпус tests/fixtures/chunks.mini.jsonl.
  • Eval: eval/search_quality_eval.py, eval/golden_queries.jsonl → data/quality_benchmark.json.
  • Regression KZ: tests/test_consult_alignment.py, test_consult_criteria_enrichment.py, test_consult_evidence_quality.py, fixtures в tests/fixtures/consultations/.

15. Заключение

Protocol сегодня - монолитный MVP с тремя контурами оценки КЗ: детерминированный compliance (8 блоков + send_gate), alignment cards (КЗ ↔ КП ↔ СОП Кравира) и опциональный LLM для поиска и углублённого L2. Корпус привязан к официальным PDF Минздрава РБ; на production - lazy chunk store и L2-lite без полного RAG по ~55k чанкам.

Интеграция с МИС через FHIR BY логична до подписи ЭЦП: ЦИСЗ проверяет упаковку данных, Protocol - клиническое соответствие протоколам. Масштаб на тысячи КЗ достижим за счёт L0-скрининга, выборочного L2 и очередей; блокировка ЭЦП - опциональная политика учреждения, не обязательная часть MVP.
