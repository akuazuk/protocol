**Статус:** active  
**Дата:** 2026-07-22  
**Тема:** переработка оценки консультативных заключений (КЗ) на базе реальных данных MIS

## 1. Контекст и зачем это нужно

Сейчас основная оценка - детерминированный **L1** (`compliance_engine` → `scoring.compute_overall`),
веса из `config/compliance_weights.yaml`. По июлю (8123 уникальных визита):

- avg overall **69.1%**, core (без exams/treatment) **65.6%**, медиана **69.6%**;
- распределение статусов: `compliant` **3**, `mostly_compliant` 2007, `partially_compliant` **5522**,
  `non_compliant` 183, `manual_review_required` 148, `not_assessed` 165;
- блоки: complaints 65.8, objective 71.8, anamnesis 57.4, diagnosis 60.1,
  **exams 16.0**, **treatment 20.3**, follow_up 73.0 (но заполнен лишь у 21%);
- заполненность полей MIS высокая: complaints 97%, diagnosis 99.8%, exams 87%, treatment 77%.

**Диагноз проблемы.** Оценка сейчас меряет не то и не так:

1. **exams/treatment проваливаются не из-за пустых полей**, а из-за жёсткого строкового
   матча текста врача с требованиями протокола (`consult_alignment._item_mentioned`,
   `_coverage_pct`). Врач пишет «ОАК, УЗИ ОБП», протокол требует «общий анализ крови,
   ультразвуковое исследование органов брюшной полости» - совпадения нет.
2. **Нет клинической валидации**: шкала 0-100 не привязана к суждению методиста, порог
   `compliant≥90` практически недостижим (3 из 8123). Шкала не откалибрована.
3. **Все ошибки весят одинаково.** Пропуск дозы антикоагулянта и отсутствие даты явки
   дают сопоставимый штраф. Это противоречит цели - ловить опасное.
4. **Огромная межспециальностная дисперсия** (Гинеколог 75.8 ↔ стоматолог-терапевт 50.2,
   Офтальмолог core 51.9, Ревматолог core 51.4) не нормируется - сравнивать врачей
   «в лоб» некорректно.
5. **Справки/профосмотры** (`pay_type=12`, core 58.6, 1085 визитов) оцениваются той же
   рубрикой, что полноценный клинический приём - это шум.
6. **kz_checklist в протоколах МЗ пуст на 100%** - главный источник «что обязательно
   должно быть в КЗ по этому диагнозу» не заполнен, движок опирается на общий req-чек-лист.

## 2. Мировой опыт: на что опираемся

Проектируем по проверенным инструментам аудита медицинской документации и безопасности:

- **PDQI-9** (Physician Documentation Quality Instrument, Stetson et al.) - 9 атрибутов
  качества записи: актуальность, точность, полнота, полезность, организованность,
  сжатость, синтез, внутренняя согласованность, «up-to-date». Золотой стандарт для
  human-rating заметок. → берём как рубрику документационного качества.
- **QNOTE** - операционализация PDQI для амбулаторных заметок по элементам.
- **National Academies «Improving Diagnosis in Health Care» (2015)** + **SaferDx**
  (Singh, Baylor/Houston VA) - фреймворк выявления диагностических ошибок и триггеров.
- **CRICO Strategies / The Doctors Company** (данные исков): диагностические ошибки -
  #1 источник тяжёлого вреда; «Big Three» = **онкология, сосудистые катастрофы,
  инфекции/сепсис**. Это ровно наши `red_flags` (possible_malignancy, thrombosis,
  severe_infection, gi_bleeding_anemia).
- **ISMP High-Alert Medications** - высокорисковые препараты (антикоагулянты, опиоиды,
  инсулин, метотрексат…): для них доза/длительность/мониторинг обязательны.
- **NICE safety-netting** и **test-result follow-up** - ненавешенная сеть безопасности
  (что делать при ухудшении, кто отслеживает результаты) - системная точка провала.
- **SOAP/E** и E/M documentation (CMS) - базовая структура записи.

**Вывод для дизайна:** оценка должна быть (а) многоосевой, (б) взвешенной по риску вреда,
(в) откалиброванной по человеку-эксперту, (г) нормированной по специальности/типу визита.

## 3. Что наиболее важно ловить (приоритет по тяжести последствий)

Ранжирование ошибок КЗ по потенциальному вреду (для весов и «critical gates»):

| Приоритет | Класс ошибки | Пример | Как ловим |
|-----------|--------------|--------|-----------|
| **P0 (harm-critical)** | Red flag без действия | «нельзя исключить малигнизацию» без маршрутизации | safety_checker + per-condition red_flags → hard cap |
| **P0** | Подозрительный диагноз без дообследования | Dx «?» без плана обследования | requirement_checker `suspected_diagnosis` |
| **P0** | High-alert препарат без дозы/длительности/контроля | антикоагулянт без МНО/срока | ISMP-список + medication_safety |
| **P1 (clinical)** | Диагноз ↔ обследования не бьются | Dx требует обязательного метода, его нет | required_exams (обогащённые) семантически |
| **P1** | Диагноз ↔ лечение не соответствует протоколу | нет обязательной группы препаратов | treatment block протокола |
| **P1** | Аномальные витальные без реакции | t 39.5 / АД 190 без действий | новый vitals-check |
| **P2 (documentation)** | Нет объективного статуса/жалоб на первичном | пустой osмотр | requirement_checker |
| **P2** | Нет плана наблюдения при хроническом Dx | ХОБЛ без явки | follow_up + dispensary |
| **P3 (formal)** | Нет даты/ФИО/кода МКБ | формальные реквизиты | data_quality_issues |

P0 - не усредняются в общий балл, а **ограничивают его сверху** (cap) и всегда попадают
в очередь методиста. P3 не должны «топить» клинически хорошую запись.

## 4. Целевая модель оценки (3 оси + risk gate)

Вместо одного взвешенного среднего - **три субоценки** и предохранитель:

```
KZ_score = calibrate(
    w_doc  * Documentation   +      # PDQI-9-lite, детерминированно
    w_clin * ClinicalConcordance +  # диагноз↔обследования↔лечение по протоколу
    w_safe * SafetyNetting          # red flags, high-alert, витальные, follow-up
) ⨯ RiskGate                        # P0 → hard cap (уже есть apply_safety_cap_to_score)
```

- **Documentation (ось A):** заполненность + качество полей MIS, нормировано по типу визита
  (первичный/повторный/справка). Основано на PDQI-9 (полнота, согласованность, синтез).
- **ClinicalConcordance (ось B):** покрытие обязательных обследований и лечения из протокола
  МЗ **семантически** (эмбеддинги + лексикон синонимов), плюс диагноз↔МКБ↔рубрика.
- **SafetyNetting (ось C):** обработка red flags, high-alert-препаратов, аномальных
  витальных, наличие сети безопасности/явки для рисковых Dx.
- **RiskGate:** любой необработанный P0 → cap (45-55%) + `manual_review_required`.

Веса `w_*` и порог статусов подбираются **на размеченном эталоне** (см. §6), а не вручную.
Итог отдаём и как **непрерывный балл**, и как **перцентиль внутри специальности×тип визита**.

## 5. Разметка данных - ядро проекта (основная оценка = по этим данным)

Данные уже есть (8123 визита). Чтобы оценка стала валидной, нужен **эталон (gold set)**.

### 5.1. Формирование выборки
- **Стратифицированная выборка ~600-800 КЗ**: по специальности (все клинические из охвата),
  по бэндам L1
  (0-49/50-59/60-69/70-79/80+), по типу оплаты (вкл. справки), по наличию red-flag.
- Отдельная under-sampled страта «potentially harmful» (есть признак red flag) - там
  цена ошибки выше.

### 5.2. Протокол разметки (двойная + арбитраж)
- Каждое КЗ размечают **2 аннотатора-методиста** независимо по единому кодбуку:
  - PDQI-9 (9 шкал 1-5);
  - чек-лист по осям A/B/C;
  - флаг «potential harm» (да/нет) + класс (Big Three / meds / follow-up);
  - итоговый вердикт: соответствует / в основном / частично / не соответствует / ручной разбор.
- Разногласия > 1 балла → **арбитраж** третьим экспертом.
- Метрика согласия: **Cohen's/weighted kappa** (цель κ ≥ 0.6 до старта калибровки).

### 5.3. LLM-ассист разметки (масштаб)
- LLM (`review_one_visit_full`) даёт **предразметку** по той же схеме → человек
  подтверждает/правит. Ускоряет x3-5. LLM НЕ финальный судья, а «второй ридер».
- Уже есть очередь `kz_l1_2026-07_llm_queue.json` (80 визитов) - расширить до gold-выборки.
- Храним разметку в `data/ml/kz_gold/` (ПДн → только на /var/data, в git только агрегаты).

### 5.4. Что делаем с эталоном
- **Калибровка весов и порогов**: ordinal logistic / isotonic regression - маппим 3 оси
  и признаки в вердикт методиста; пороги статусов - из ROC/quantile, а не «90/75/50».
- **Валидация**: held-out 20%, метрики - **QWK (quadratic weighted kappa)** L1 vs методист,
  MAE балла, recall по «potential harm» (важнее precision - не пропустить опасное).
- **Мониторинг дрейфа**: ежемесячно пересчитывать на новой выгрузке, сверять с эталоном.

## 7. Технические доработки движка

1. **Семантический матч exams/treatment** (устраняет провал 16/20%):
   - лексикон синонимов + эмбеддинги rich_chunks; `_coverage_pct` считать по семантике,
     а не подстроке; порог покрытия калибровать.
2. **Нормировка по специальности×типу визита**: перцентиль/z-score поверх сырого балла;
   отдельная рубрика для `pay_type=12` (справки) - усечённый чек-лист.
3. **Vitals-check**: аномальные t/АД/ЧСС/ЧД/SpO2 без реакции в тексте → ось C.
4. **High-alert-препараты**: расширить `medication_safety` списком ISMP; для них
   доза+длительность+мониторинг обязательны (иначе P0).
5. **Test-result follow-up**: если назначено обследование/есть отклонение - проверять
   наличие плана отслеживания результата (safety-netting).
6. **Разнести баллы**: `documentation_score`, `clinical_concordance_score`,
   `safety_score` как явные оси в `ScoreBreakdown` + отдать в summary/дашборд.
7. **Explainability**: к каждому баллу - список конкретных «gap» с привязкой к протоколу
   (для методиста и врача), уже частично есть в alignment_cards.

## 9. Дорожная карта (согласованный порядок 2026-07-22)

Решения обсуждения: старт - обогащение протоколов; охват - **все клинические
специальности (~20), исключаем только неклинические**; разметка эталона -
**LLM-предразметка + двойное подтверждение методистами + арбитраж**.

**Охват специальностей (26 всего в базе, 8123 визита).** Режем по типу, не по частоте:
- **Исключаем (~3.3% визитов):** медицинская сестра (73, нет врачебного заключения),
  стоматолог-терапевт (91, отдельный домен стоматологии), Логопед (23),
  нераспознанная/пустая специальность («—» 69, « - » 14).
- **Обогащаем (~96.7%):** все клинические, включая низкочастотный, но
  высокорисковый хвост - Проктолог (184, avg 60.9), Педиатр (183), Детский хирург (171),
  Ревматолог (126, core 51.4), Детский невролог (84), Онколог (32, «Big Three»),
  Флеболог (21, тромбозы), Хирург (21), Психотерапевт (14, core 38.2 - суицид-риск).
- Стоматология - отдельный трек позже (свои протоколы/рубрика).

- **Э1 (СТАРТ) - обогащение протоколов (все клинич. специальности):** заполнить `kz_checklist` (0→100%),
  `red_flags` (+cap), словарь синонимов обследований/препаратов.
  **Первая итерация - машинная: LLM-генерация + `quote_validator` (машинная проверка
  опоры на цитату), без ручного подтверждения.** Ревью методистом - следующая итерация.
  Все сгенерированные поля помечаются `review_status="not_reviewed"`. См. §11.
- **Э2 - семантический матч exams/treatment:** синонимы + эмбеддинги вместо подстроки;
  быстрый эффект на всей базе без разметки (чинит exams 16 / treatment 20).
- **Э3 - структурные items в alignment + движок 3 осей + risk-gate:**
  **(приоритет, из вывода Э2)** источник exam/treatment пунктов для сверки -
  `ProtocolSummary.required_exams[].name` + `kz_checklist` (Э1), а не обрывки чанков
  (`profile["diagnostics"]`); тогда каталог синонимов (Э2) начнёт давать эффект и
  exams/treatment (16/20) вырастут. Далее: `documentation_score` /
  `clinical_concordance_score` / `safety_score` в `ScoreBreakdown`; per-condition
  red_flags → cap; vitals + high-alert + safety-netting.
- **Э4 - gold + калибровка:** стратифицированная выборка 600-800 → `data/ml/kz_gold/`;
  LLM-предразметка + двойное подтверждение методистами + арбитраж; kappa; пороги из ROC;
  held-out валидация (QWK, recall по harm).
- **Э5 - прод:** нормировка по специальности × тип визита; отдельная рубрика справок
  (`pay_type=12`); дашборд с осями/перцентилем/gaps; мониторинг дрейфа ежемесячно.

## 11. Этап 1 детально - обогащение протоколов (все клинич. специальности)

**Цель:** дать движку диагноз-специфичный «ключ ответов». Без него оси A/B/C нечем питать.
**Охват:** все клинические специальности (см. список исключений в §9), эффорт
приоритизируется по частоте реальных диагнозов в 8123 КЗ.

### 11.1. Что заполняем (по каждому `ConditionSummary` в охвате)
- **`kz_checklist`** (сейчас 0%): `must_have` (обязано быть задокументировано/сделано по
  этому Dx), `should_have`, `conditional` (если X → нужно Y), `warnings` (red flags).
  Каждый пункт - с `source_ref` на место в протоколе.
- **`red_flags`** (44→100% для рисковых Dx): + `expected_actions` + `cap_if_unhandled`.
- **Словарь синонимов** обследований/препаратов (для Э2): ОАК↔общий анализ крови,
  УЗИ ОБП↔ультразвук органов брюшной полости и т.д. - строится из корпуса rich_chunks
  + курируемый seed; хранится отдельным справочником с привязкой к терминам протокола.
- Дозаполнить пробелы `required_exams` / `diagnostic_criteria` / `treatment` где пусто.

### 11.2. Как генерим (1-я итерация - машинная, без человека) - ВЫПОЛНЕНО
Реализовано **детерминированной сборкой** вместо LLM-прохода: каждый пункт
`kz_checklist` выводится из уже извлечённых и **привязанных к цитате** полей
(`diagnostic_criteria`, `required_exams`, `conditional_exams`, `treatment`,
`follow_up`, `routing`, `hospitalization`, `red_flags`, `diagnosis_structure`).
1. Модуль `clinical_knowledge/protocol_summary/kz_checklist_builder.py` -
   раскладывает поля в `must_have` / `should_have` / `conditional` / `warnings`
   (обязательные exams+критерии → must; recommended/лечение → should; `required_if`
   и маршрутизация → conditional; red flags → warnings).
2. Скрипт `scripts/enrich_kz_checklists.py` - применяет по всем клиническим карточкам
   (стоматология исключена), пишет `kz_checklist` в `json/*.json` + отметку в
   `extraction_metadata.notes` (`kz_checklist=auto_derived_v1@...`).
3. **Guardrail от галлюцинаций:** источник каждого пункта - поле протокола, у которого
   уже есть `source_ref.quote` (прошёл `quote_validator` на этапе извлечения). Новый
   свободный текст не генерируется → опора на цитату по построению, LLM не нужен.
4. `review_status` карточки не трогаем; пометка о машинной генерации - в notes.
   **Ручное ревью методистом - следующая итерация.** Для 93 conditions с пустым
   извлечением checklist оставлен пустым → очередь на дозаполнение (LLM-проход / ре-экстракция).

### 11.3. Приоритет внутри охвата
По частоте конкретных диагнозов в реальных 8123 КЗ (не по алфавиту протоколов) -
сначала самые частые Dx. Низкочастотный, но высокорисковый хвост (онко, ревма,
проктология, психотерапия) обязателен к покрытию несмотря на малый N.

### 11.4. Как это сразу меняет оценку (даже до Э3)
- `kz_checklist.must_have` подключается к documentation/exam-покрытию → блоки перестают
  быть «общими»; появляются конкретные gap со ссылкой на протокол.
- Обогащённые `red_flags` → расширяют safety-cap за пределы 6 глобальных флагов.

## 12. Этап 2 - семантический матч exams/treatment (ВЫПОЛНЕНО)

**Проблема:** блоки exams (16%) и treatment (20%) проваливались из-за подстрочного
матча: врач пишет «ОАК/УЗИ ОБП/ФГДС», протокол - полные названия → совпадения нет.

**Решение (без ручной разметки, эффект на всей базе):**
- `clinical_knowledge/term_catalog.py` - грузит `data/catalog/exam_drug_synonyms.json`,
  строит индексы variant↔canonical + токен-индекс; `expand_term()` даёт все формы термина
  (канон + аббревиатуры). Чистый stdlib, `lru_cache`, дешёвый на батче.
- `semantic_rule_fallback._aliases()` теперь подмешивает синонимы каталога (в обе стороны:
  «общий анализ крови» ↔ «оак»). Матч аббревиатур из 3 букв - по границе слова (`_alias_hit`),
  без ложных подстрок. Работает для `required_exam` И treatment `keyword_presence`.

**Метрики Э2 (offline-тест `scripts/test_semantic_exam_match.py`, 17 кейсов, изолированно):**
| Конфигурация | recall exam/treatment | false+ |
|--|--|--|
| только токены | 0% (0/15) | 0/2 |
| старый `_ALIAS_MAP` | 47% (7/15) | 0/2 |
| **только каталог (Э2)** | **100% (15/15)** | 0/2 |

Исправлен баг каталога: 2745 названий обследований из протоколов добавлялись как
каноны БЕЗ вариантов и через точное совпадение затеняли курируемые записи
(«общий анализ крови развернутый» перебивал «общий анализ крови»→«оак»). Теперь в
индекс идут только записи с ≥1 вариантом (38 exam + 14 групп препаратов).

**Верификация на реальных 8123 КЗ (A/B в одном процессе, `measure_semantic_match_delta.py`,
sample 300):** дельта exams/treatment/overall = **+0.0**. Каталог корректен, но на проде
эффекта нет.

**Причина (диагностика 25 КЗ, 560 сверок item↔КЗ):** движок сверяет текст врача не с
чистыми названиями обследований, а с **обрывками прозы протокола** из чанков
(`profile["diagnostics"]`): «КЛИНИЧЕСКИЙ ПРОТОКОЛ», «„О правах ребенка"», «исходы
заболевания…». Только **3%** таких «пунктов» - реальные названия обследований →
синонимам нечего сопоставлять (0 flip'ов OFF→ON). Низкий exams=16/treatment=20 -
следствие мусорных входов, а не подстрочного матча.

**Вывод и рескоуп:** каталог синонимов - необходимая инфраструктура, но выигрыш
gated на подаче в alignment **структурных `required_exams` / `kz_checklist` (Э1)**
вместо обрывков чанков. Это переносится в **Э3** (подключение структурных полей к
движку): источник exam/treatment items = `ProtocolSummary.required_exams[].name` +
`kz_checklist.must_have/should_have`; тогда каталог начнёт давать эффект.

**Артефакты Э2:** `term_catalog.py`, `scripts/test_semantic_exam_match.py`,
`scripts/measure_semantic_match_delta.py`, правки `semantic_rule_fallback.py`,
чистый `data/catalog/exam_drug_synonyms.json` (52 записи с вариантами).

## 13. Этап 3 - структурные items + 3 оси + risk-gate (В РАБОТЕ)

### 13.1. Структурные items в alignment (ВЫПОЛНЕНО, разблокировка Э2)
`consult_alignment._structured_items()` берёт пункты для сверки из
`ProtocolSummary.required_exams/conditional_exams` (exams) и `treatment.drugs/
drug_groups/procedures/surgery/non_drug` (treatment) вместо обрывков чанков.
`_exams_card`/`_treatment_card` предпочитают их (env `CONSULT_STRUCTURED_ITEMS`,
default ON; fallback на прежний путь по чанкам).

**A/B на реальных 8123 КЗ (`measure_structured_items_delta.py`, sample 300):**
| Конфигурация | exams | treatment | overall |
|--|--|--|--|
| baseline (как на проде) | 17.7 | 20.5 | 68.2 |
| + структурные items | 22.6 (+4.9) | 20.6 | 68.2 |
| + структурные + каталог (Э2) | **23.5 (+5.8)** | 21.0 | 68.2 |

Каталог синонимов теперь **даёт эффект** (+0.9 к exams поверх структурных). Лечение
почти не двигается (+0.4): матч свободного текста назначений врача с названиями
препаратов протокола - отдельная задача (нормализация препаратов/доз).

**overall не изменился:** `overall_score` считается из `ScoreBreakdown`
(rules-based), а не из alignment-карточек. Улучшение блоков дойдёт до overall
только после 13.2 (3 оси).

### 13.2. Три оси в ScoreBreakdown (СЛЕДУЮЩЕЕ)
`documentation_score` / `clinical_concordance_score` (из alignment-блоков
diagnosis+exams+treatment+follow_up) / `safety_score`; overall = взвешенная сумма
осей × risk-gate.

### 13.3. Risk-gate (СЛЕДУЮЩЕЕ)
per-condition red_flags → cap; vitals-check (t/АД/ЧСС/SpO2 без реакции);
high-alert ISMP (доза/длительность/мониторинг обязательны).
