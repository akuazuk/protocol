## 1. Задача и метод

Вопрос владельца: что в кабинете медленно, что неинформативно, что бесполезно для оценки
качества МО по истории визитов, анализам, назначенным лекарствам и реестру протоколов;
как перепроектировать навигацию, фильтры и дизайн.

Метод аудита (выполнен 2026-09-25):

1. Тайминги 40 вызовов API из контейнера на GCE (`127.0.0.1:8000`, токен из окружения,
   тела ответов не печатались).
2. Профиль склада SQL: наполненность колонок `fact_mo_case`, состав `fact_mo_finding`,
   использование CRM, журнал доступа.
3. Инвентарь фронтенда: каждый `data-page`, контрол, график, таблица, блок drawer,
   вызов `request()` в `mo-app.js` (5717 строк) и `mis-kz-quality.html`.
4. Инвентарь бэкенда: 52 маршрута `/api/methodist/mo/*`, источник данных, полная ли
   загрузка месяца в Python, кэш.

Что не делалось: скриншоты прода под учёткой методиста (аудит 2026-09-19 уже снят),
опрос методистов, слепая разметка выборки. Это шаги раздела 5.

## 2. Факты

### 2.1 Скорость (GCE, внутри контейнера, сентябрь, тёплый процесс)

| Вызов | Время | Что внутри |
|--|--|--|
| `/overview?month` | **14.8 с**, повтор 9.8 с | полная загрузка месяца + `GROUP_CONCAT` всех findings + агрегаты в Python; кэша нет |
| `/cases?month` первая страница | 2.6 с холодная, 0.43 с тёплая | полный месяц в RAM, затем срез 50 строк; `lru_cache(24)` на `_pipeline_records_for_month` спасает повтор |
| `/cases?queue_only=1` | **5.0 с** | `_needs_review` по каждой строке + CRM + findings |
| `/cases?q=I10` | 0.78 с | |
| `/facets?month` | 3.7 с | `_filter_records` дважды |
| `/trends`, `/reports`, `/data-quality`, `/freshness` | 3.1-3.5 с каждый | полная загрузка `_records` ради маленьких сводок |
| `/drugs-labs-kpis` drug / lab | 1.5 / 1.1 с | SQL + ATTACH `mo_lab.sqlite` |
| `/score-dashboard`, `/timeseries`, `/breakdown`, `/heatmap`, `/findings` | 0.01-1 с | уже на SQL |
| `/cases/{id}` | **0.15 с** | план latency 2026-08-10 сработал |
| `/cases/{id}?live=1` | 2.8 с | live concordance / ICD / rceth |
| `/cases/{id}?prior=1` | **10 с** | скан CSV 90 дней |
| `/cases/{id}/protocol-suggest` | 3.6 с холодный, 0.11 с тёплый | повторный `build_case_detail` + реестр КП |
| `/dimensions/doctor`, `/daily-report?period=yesterday` | 422 | контракт параметров расходится с тем, что зовёт UI |

Экран «Период» открывается за 10-15 с, экран «Очередь» за 5 с. Разбор случая после
починки открывается быстро, но вкладка подбора КП добавляет 3.6 с при первом заходе.

## 4. Диагноз: медленно, неинформативно, бесполезно

### Медленно

1. Обзор месяца 10-15 с: полная загрузка + агрегаты в Python при наличии готовых
   `fact_mo_daily` / `fact_mo_doctor_daily`.
2. Очередь 5 с: `_needs_review` по каждой строке вместо предвычисленного флага.
3. Facets 3.7 с: двойной проход; можно `GROUP BY` на складе.
4. Четыре служебных вызова по 3 с (`trends`, `reports`, `data-quality`, `freshness`) при
   каждом заходе на Отчёты.
5. Подбор КП 3.6 с холодный при каждом первом разборе.
6. `?prior=1` 10 с - флаг остаётся в UI как «показать прошлые визиты».

### Неинформативно

1. Шкала `overall_grade` на 95 % состоит из `fair` и `poor`. Пять слов, работают два.
2. `zone1` «слабо» у 71 %: строка №55 почти у каждого. Зона не сообщает ничего нового.
3. `zone2b` «нет оценки» у 63 %: две трети плана не оценены, кольцо плана - в основном серое.
4. Две шкалы «критично»: плитка (P0/P1 findings) и фильтр (`overall_grade`). Числа не сходятся.
5. Legacy `status` (good 79 %) в колонке рядом с `overall_grade` (good 3.7 %).
6. Findings: 3 из 4 карточек в «Что не так» - контекст (история, №55-пункт, rceth-сверка).
7. Проценты «полнота проверки», «надёжность», «сводный индекс deep» - не объясняются
   ни одним действием методиста.

### Бесполезно для оценки качества по истории, анализам, лекарствам, реестру

1. **История**: 58 % случаев имеют prior, история хранится в кеше, но показана как три
   числа. Нельзя увидеть: тот же диагноз у того же врача месяц назад с тем же планом;
   смену диагноза между специалистами; назначенный тогда анализ, который сейчас не
   прочитан. Finding истории - «первый контакт» у 75 %.
2. **Анализы**: связка по `patient_key` есть у 100 %, окно -14/+1 день, реконсиляция
   считается. Но все выводы помечены «черновик, не входит в оценку» и стоят под
   таблицами значений. Отклонения не подсвечены относительно текста МО.
3. **Лекарства**: список назначений врача в разборе не показан. Rceth-сверки (65 %
   случаев в сумме) заглушают DDI / дубли НПВП / STOPP-Beers (3 %). Прецизионность
   `C_rceth_off_label` не измерялась.
4. **Реестр КП**: у 63 % случаев КП не подобран, и зона плана пуста. Пока это так,
   любой дашборд «План по протоколу» описывает треть выборки.
5. **CRM-контур** (очередь, статусы, ответственные, bulk, споры, saved views, экспорт-
   задачи): 0 использования за месяц, 2 экрана и десятки контролов.

### 6.4 Шкала и замечания: чтобы «Хорошо» и «Критично» существовали

1. Контекстные коды (`B_patient_history_context`, `B_exams_gap_advisory` с `passed=1`)

4. Лабораторные `B_lab_*` P1 и лекарственные `C_ddi` / `C_nsaid_dup` / STOPP / Beers -

5. После 1-4 пересчитать `overall_grade` за сентябрь и проверить §5.3: если два верхних
   значения всё ещё ≥ 75 %, пересмотреть пороги лестницы в `mo-grade-ladder-v1` отдельным

6. Плитка «критично» на Обзоре и фильтр «Критично» читают один столбец `overall_grade`.
7. Legacy `status` из таблиц и API-ответов списка убрать.

### 6.5 Инспектор случая: «Пациент во времени» вместо трёх счётчиков

Правая колонка сверху вниз:

1. **Шапка** из строки списка (визит, дата, врач, спец., МКБ, оценка) - до ответа detail.
2. **Итог разбора** - `review_brief` одной-двумя фразами.
3. **Что не так** - только дефекты, отсортированы: Риск → Диагноз → План → Оформление.
   Контекст свёрнут в одну строку «контекст: первый визит к врачу, №55 п.20».
4. **Пациент во времени** - одна лента, новый компонент:
   - прошлые визиты за 180 дней (дата, врач, спец., МКБ, оценка); текущий выделен;
     клик открывает тот визит в том же инспекторе;
   - анализы в окне -14/+1 день как точки на той же оси; отклонения красным; клик -
     значения; пометка «упомянут / не упомянут в МО» из reconcile;
   - назначения из «Рекомендации по лечению» текущего визита списком с пометкой риска
     (`C_ddi`, дубли, STOPP/Beers); без Rceth-«требует сверки», пока shadow;
   - если прошлый визит с тем же корнем МКБ у того же врача - строка «повтор: план тот же /
     изменён» (после §5.5).
5. **Протокол МЗ** - одна строка статуса сразу из столбца склада («КП …, план по КП:
   слабо» / «КП не подобран: нет протокола по коду»); details - предложенные КП и
   несделанные пункты.
6. **Решение методиста** - 3 вердикта (Оформление / Диагноз / План), комментарий с
   prefill из brief, кнопка «Сохранить», «МО в PDF». Статус CRM, ответственный, срок,
   теги - убрать из формы; история пакетов - внутри details.
7. **Проверка** (details) - критерии зон, №55, shadow Dx/Plan, LLM-судья, служебные метрики.

Инспектор - split view на ≥ 1280 px, строка списка остаётся выделенной; prev / next по
текущей выборке. Пустые поля МО скрываются. PHI не логируется.

### 6.6 Экран «Пациент»
